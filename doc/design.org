* Modules

=drover-filter.el= provides the categorical filters' searchable checklists, called by the shared menu in =drover-keys.el=. A checklist borrows the existing menu window at its current size, restoring the menu on apply or cancel; long lists scroll there, and searching never resizes it. Their drafts live only in the temporary picker buffer; =drover-core.el= matches inclusion and exclusion selections, and =drover-ui.el= describes them.

* Backends describe, drover arranges

A backend owns its sessions and their state; drover asks it for =drover-session= records and keeps them only as it reported them last, in an index current through its reports (see [[*Thousands of sessions][Thousands of sessions]]).  The record is a snapshot with one status, so every view ranks, groups and sorts sessions the same way, through =drover-sort=, =drover-tree=, =drover-group-trees= and =drover-sort-trees=.  The only records drover keeps are older sessions a backend fetched on demand (see below), and only while they are shown.  What costs a request to know, such as a context size, a record may lack: views ask the backend for it, for the sessions they show, with =drover-prefetch= (=:prefetch=), and redraw as it reports the answers (see [[*Details fetched on demand][Details fetched on demand]]).  The recap of a session's last turn, which an expanded session shows, a view asks for (=:recap=) and keeps until the session changes (see [[*The last turn, fetched as a session expands][The last turn]]).

Backends report changes with =drover-backend-changed=, naming the session changed when they can.  A turn streams many events, so changes are coalesced: =drover-changed-hook= runs once the backends have been quiet for =drover-refresh-delay= seconds, =drover-changed-sessions= telling which sessions changed, and views follow from it.  A session's buffer opening or closing is a change too, since the colour of a title tells whether the session has a buffer (=drover-session-buffer=, see [[*Where sessions are][Where sessions are]]): the OpenCode backend follows =opencode-session-buffer-functions=, which opencode.el runs as it registers and unregisters a session buffer, its registry not changing then; the other backends' sessions are their buffers, whose creation and killing they already report.

* What sessions run

A record tells what its session runs as data, not as one preformatted string, so that a list draws it alike for every backend, and in its own faces, which font lock keeps: =model=, the model's compact name, such as =Opus 5.5=, by which views also group, sort and filter; =effort= and =effort-default=, the effort it runs and whether it is the model's default rather than a choice, which the list dims as the prompt dims what a new session inherits; =provider=, a compact display such as an icon, and =provider-name=, which tooltips and details read; =context-tokens=, =context-limit= and =context-tier=, the size of the context, the model's, and the long-context price tier it nears or passes as (STATE SIZE LABEL), and =context-estimated=, non-nil while the size is the service's estimate after a compaction, which the next step measures: lists show it after a =~=, its tooltip says so, and its tier is an estimated one; =cache-tokens= and =cache-prompt-tokens=, the share of the last prompt its prompt cache holds; =agent=, the agent's name, by which views group, sort and filter, and =agent-display=, the agent as the backend's own interface draws it, in its faces.  Any may be nil: a backend fills what it knows cheaply.

The list draws the agent as =@name=, the =@= in the name's face, so that it reads as one word, as an agent mentioned in a prompt is spelt, and as the OpenCode mode line draws it, which has no =@=: bold, in the agent's colour.  A backend without a display of its own gets a face of =opencode-agent-faces= by a digest of the name, stable from one Emacs to the next: the faces opencode.el gives its own agents by their place among the agents of a location.

** Details fetched on demand

The registry knows the context size of the sessions it saw take a step, but not of those it loaded on connecting, a hundred by default: =opencode-state-context= fetches one in the background the first time it is asked, a few at a time, and runs the update hook when it arrives.  Asking for every session of the registry from =:sessions=, which every view and the mode-line count call, would fetch the sizes of a hundred sessions nobody looks at, on every connection, each answer a whole step with its tool outputs.  So records carry the size the registry knows, the entry's =:context=, and the backend's =:prefetch= asks for those of the sessions a view shows; the registry then costs nothing for a size known, being fetched or failed.  The list asks, once per drawing, for the sessions of its expanded groups while columns may show the context, for those it draws in place as they come or change, and for those of a group expanded later after the command (=post-command-hook=, =drover-list--prefetch=): the Idle group, collapsed by default, holds most sessions.  In two lines the context shows as a pie, asked for alike while =drover-list-fields= places it there, whether a row has a context yet or not: none has until it is fetched (=drover-list--prefetch-wanted-p=).  What sessions changed is asked for alike, a kind of its own (=drover-prefetch='s KINDS, =details= and =changes=), while the list may show its column, and for a session expanded whatever the column: the list asks only the kinds it may show (=drover-list--prefetch-kinds=), so that hiding the context asks no backend for it.

** The last turn, fetched as a session expands

A session's section body recaps its last turn: the list's line already shows its status, age and what it runs, so the body tells what the line cannot: its title when the line cuts it; what it waits for and the error that ended its turn, in full, but an error the line shows whole already, or how it stands when the line leaves out its summary; the user's last prompt and the agent's newest reply since, a few lines each (=drover-list-recap-lines=), wrapped in pixels to the window; the files all its turns changed, a line each (see [[*What sessions changed][What sessions changed]]); and the fields of =drover-list-fields= its line does not show whole.  Which those are is the row's own, not the layout's: a field the layout places may show cut, as an icon alone (the harness's in a narrow column, the context's pie, a task's pill), as a background (the prompt cache), under the title only for the sessions that need the user (the summary in two lines), or not at all when the title takes its room on the title's line.  So the drawing of a heading (=drover-list--column-line=, =drover-list--narrow-line=) tells the fields it showed whole, or had nothing to show for, kept with the heading (=drover-list--heading=), and the details leave out those and the field the session's group names, such as its project (=drover-list--row-whole=).  A session whose line shows all it would tell has no details.  The prompt, reply and changes cost a backend requests or a file read, so they come from an optional operation, =:recap=, through =drover-recap=:

The list asks for a recap only as a session's body is drawn, that is once it is expanded, since Magit draws a collapsed body when it is first shown, and keeps it by session (=drover-list--recaps=) with the session's last activity, =updated=, and what it changed, =changes=, at the asking (=drover-list--recap-stamp=): it is fresh while those are the session's, and fetched again otherwise, so that the files read once a turn ended show.  A session at work changes many times a second, so an expanded one is fetched again at most every =drover-list--recap-interval= seconds, a timer drawing the list once more when a fetch was put off; meanwhile the stale recap shows, and =loading…= only before the first one.  An answer arriving after the asking draws the session's details again, in place, if they show; one arriving during the asking, as a backend reading local state answers, is drawn by the asking.  Each fetch carries a token, so that an answer to a fetch a refresh (=g=) forgot is dropped.

** What sessions changed

The column =changes= tells what a session changed in all its turns, such as =+42 −7 · 3 files=, its counts past a thousand lines in thousands, =+45k −6.1k=, as sizes of contexts are told (=opencode-format-tokens=), and its files a count and an f, =409f=, since five digits each and the word took the column to twenty-odd characters, and its expanded session the counts whole and the files, a line each, their counts kept whole as the name is cut.  Engines tell them already, for reviews (=:changes= of =drover-register-engine=, the scope =session=): OpenCode's service diffs the snapshots it took, a request; Claude Code's and Codex's edits are read from the whole transcript or rollout, in slices.  No model is asked.  Too costly for every session listed, every time a list draws, they are read by =drover-changes.el= only for the sessions views show, as views ask what records lack (=drover-prefetch=, of the kind =changes=, through =drover-changes-prefetch-function=), and only once a session settled: never while it works, =drover-changes-delay= seconds after its turn ends, a change meanwhile putting it off, two at once, the most recently active first, each given =drover-changes-timeout= seconds.  A session asked for is followed through =drover-changed-hook=: seen at work, it is read again once settled; its time of last activity moved, it is read again.  One that could not be read is read again only once that time moves.

What was read is kept by conversation, engine and engine identifier, so that front ends showing one conversation share it: the counts, the time of last activity it describes, and the first files, a hundred at most and 8000 characters of names, every file counted.  Records take the counts in, in =drover--bound-record=, through =drover-changes-function=, as briefs are taken in (see [[*Summaries written by a model][Summaries written by a model]]): the slot =changes=, =(ADDITIONS DELETIONS FILES)=, the copy made once per record and entry, so that records listed again compare alike; a change of the counts takes the records in again (=drover-take-in-again=), the index asking their backends for them, the older and archived sessions fetched taken in from the records kept, so that lists draw them in place and the remote layer serves them.  Recaps take the files in, =:files=, in =drover-recap=, through =drover-changes-files-function=, the list's details reading them there: a session's recap is fresh while its counts are those it was asked at.  A session whose engine tells none, or not yet, shows its last turn's files, as its backend's recap tells them.  The file =changes.eld= of =drover-state-directory= keeps the newest 1000 conversations, written a few seconds after a read and as Emacs exits; one that does not read is reported once, and written over only once something was read anew.  Another host's sessions carry the counts and files their owner read (capability =changes=, see =doc/remote.org=).

** Summaries written by a model

=drover-summary-mode= has a cheap model write, as a session's turn ends or it waits for the user, one line on where it stands, a recap of the turn in a few lines, and a paragraph on the whole session, after a line of dashes: =brief=, =brief-recap= and =brief-session=, the last slots of the record.  The line is five words at most, =drover-summary-line-length= characters: the sidebar, 36 columns, shows about 227 pixels under a title, some 40 characters of a proportional font, and the lines first asked for, 80 characters at most, came 58 to 94 long, every one cut there.  Asked for six words and 40 characters, the model still wrote 44 and 45 now and then, 252 pixels: a line longer than asked keeps its leading clauses that fit, cut at a semicolon, a comma or a dash (=drover-summary--fit=), rather than where the list cuts it.  The paragraph, two or three sentences and =drover-summary-session-length= characters at most, begins with the session's subject, as its first prompt set it, then how it went, then where it stands; asked for 500 characters, the model wrote 506 to 673, too long to read at a glance above the input, so a paragraph past a third more than asked loses sentences from its middle, its subject and where it stands kept (=drover-summary--fit-session=).  Written after the last turn, the first paragraphs began with it, "The agent fixed the five issues…", which recalled nothing of what the session was about to someone back to it, with that turn right below.  Records get them as drover takes them in, in =drover--bound-record=, through =drover-brief-function=, set by the mode: a lookup in the summaries kept by conversation (engine and engine identifier, so that front ends showing one conversation share it), the copy made once per record and summary (a weak table), so that records listed again compare alike, and the brief changes the record, which lists draw in place and the remote layer serves.  =drover-session-summary=, which the list's column, the sidebar, tooltips and the search read, prefers the brief, else tells the request or the detail as before; the list's details show the recap first (=summary= in =drover-list-recap-lines=), the line too when the layout leaves out the summary's column.

A summary describes the session as it stood: its turn ended (idle or done), failed, or waiting for the same requests.  It goes as the session works again, and does not come back for the next turn, which needs its own: it shows while its time of last activity is the one summarized, or, once this Emacs saw the session stand so since, whatever that time becomes, as a title renamed or the session marked seen moves it.  The mode follows =drover-changed-hook=: a settled session whose activity or requests changed since last seen is summarized =drover-summary-delay= seconds later, a change meanwhile putting it off, never one at work, so that the events of a turn, coalesced already, ask nothing; sessions found as Emacs starts only when recently active (=drover-summary-catch-up=).  Asking reads the backend's recap of the last turn (=drover-recap=, as an expanded session does), and makes of it the text the model reads (=drover-summary-input=): how the session stands, the requests waiting, the prompt's head, the reply's head and end, the files changed, the error, redacted, 4000 characters at most; and of the session as a whole (=drover-summary-context=): its title, its first prompt, which the recap tells (OpenCode's =:first-prompt=) or the engines recording the conversation (=:search-text=, its first), and the paragraph written after the turn before, a thousand characters each at most, so that each paragraph builds on the last.  The digest of the instructions, the turn's text and the first prompt is the summary's key, neither the title nor the paragraph before, which change with renames and summaries: a turn read again, after a rename, a mark seen or the next Emacs, needs no model; a turn needing none keeps the paragraph written before; a turn of one short reply is its own summary, a turn of nothing gets none.  Two are asked at once, the others waiting their turn; each is given up after =drover-summary-timeout= seconds.

The model answers through OpenCode's service, =POST /api/experimental/generate/text= with this host's cheap model, or the next of its chain while one is unavailable (see [[*The cheap model of a host][The cheap model of a host]]), or the one =drover-summary-model= names, and its variant: one stateless generation, which stores no session and publishes no usage event, so that summaries neither show among the user's sessions nor count in the usage of sessions; drover counts them per day in =summary-usage.eld= (=drover-summary-usage=), and stops at =drover-summary-daily-limit=, said once that day.  OpenCode's own titles choose a provider's small model, its =gpt-luna= family first, then =claude-haiku=: for Copilot, =gpt-6-luna= and =claude-haiku-5.5= cost alike, $0.10 a million tokens read and $0.50 written, and answered a summary in 1.3 s each; Haiku followed the format more closely, so it is the best tier of cheap model, at =low=, the least effort its variants offer, which a cheap model runs when it offers it.  The first summaries of real turns said only that a turn ended, the outcome in the recap: the instructions ask for the outcome, concrete enough to tell sessions apart, never that alone.  The service is asked only while it runs, as its registration and process tell: summaries never start it.  A service before 2.2, such as Core's 2.1.4, knows the route by its former path alone, =/api/experimental/generate=, which later ones keep as an alias: a 404 without an error's tag, a route missing rather than a model, has the summary asked there, and the next ones (=drover-cheap--former-path=).  A summary is given up once each model it may ask had =drover-summary-timeout= seconds, its request cancelled.  A failure leaves the session as it showed, and is said once, until a summary is written again; for =drover-summary-rest= seconds after it, nothing is asked of the model but what the user asks (=drover-summarize=), so that a provider not signed in, as Copilot on Core, does not cost a recap and a request at every turn's end.  Where no cheap model resolves, the generation answers so (=:none=) without a request: that is said once, no summary needing a model is asked for, not even after a rest, while =drover-model-cheap= resolves none, and those needing none are still written; summaries resume once the catalogs offer one.

Another host's sessions carry their owner's summaries in their records, =brief=, =brief-recap= and =brief-session= on the wire, a host running an older drover ignoring the last, decoded and bounded as the other fields: a host summarizes its own sessions alone, so that the text of a turn leaves its host only through its owner's model.

** The cheap model of a host

Summaries were written by a model named in drover's options, Copilot's Haiku, which Core's service was not signed in to: Core summarized nothing, its configuration turning summaries off there.  The model is now each host's own, resolved from its service's catalogs by the user's preference (=drover-cheap.el=): a host summarizes with what it may use, and a host where nothing resolves says so once.  Each resolves its own, with its own kind, set by its configuration (=drover-cheap-host-kind=), since summaries run on their owner.

The catalogs give each model its provider, its family (=claude-haiku=, =gpt-luna=, =deepseek-flash=, =glm-flash=…), its release date and costs, and each provider its integration; the provider catalog lists providers the service is not signed in to too, such as Copilot on Core, whose generations fail for a missing Authorization header.  So how the service is signed in comes from its integrations (=/api/integration=, kept reduced to the identifier and the kind of each connected one): a connection by OAuth is a subscription, by key or environment an API; a provider with a key in its settings is signed in by it, one of no integration, as the MongoDB relay's on Core, by its plugin; one of an integration not connected is never used.  A service without the route counts every provider of an integration signed in by key.  The integrations are read again after =integration.updated= and =server.connected= events and a changed provider catalog, the model resolved again once a catalog, the integrations or an option changed (=drover-cheap--key=), so that a summary asks nothing more of the service than its generation.

The rule ranked providers first, then tiers: within the first class of the host's order with a provider offering any cheap model, the best tier those providers offer, the latest of that tier.  Walking tiers first, Haiku on any provider of the order before Luna, would have given Core the relay's Haiku rather than ChatGPT's Luna, which the subscription pays for already.  But a class whose only Haiku was old won over a later class offering the current one: Reaver without Copilot took the Grove gateway's Haiku 4.5, the ProdSec gateway offering 5.5.  So models are first current or outdated, each family's current version the newest the usable providers offer, then providers, then tiers.  The version is read from the identifier, never the release date: providers date one model differently, the gateway's Haiku 4.5 a month after Copilot's, and the ProdSec gateway dates none; a model whose identifier tells no version, as Fireworks' routers to the latest, is outdated beside one that tells it, and a family where none tells one has none outdated.  Outdated models are demoted, not dropped: they still answer when nothing current does.  Within a tier, the newer version of a family, then the release date, between families: a model without a date takes the date the catalog gives its name on another provider.  Ties go to the edition not premium, ChatGPT listing =gpt-6-luna-fast= beside =gpt-6-luna= on the same day, then the cheaper.  Spot capacity (=-spot=), cheaper but taken back at the provider's will, is never chosen (=drover-cheap-excluded-models=).  The legacy Grove gateway on Azure (=grove-*=) offers no cheap model on either host, and is no class of theirs any more.

Small requests go to the chain, the best model of each provider in that order, not every model ranked: a quota, a login or an outage is a provider's, so its other models would fail alike.  =drover-cheap-generate= asks the first, and the next only on an error of availability (=drover-cheap-fallback-p=): a provider's error of authentication, rate limit, overload or of its own, a model or provider the service does not know or cannot run, the service unable to reach one, no answer in time; content a provider's filter refused, a request a provider or the service found invalid, or the service refusing the request would fail with any model, and end it.  The reason of a provider's error, and the field of an invalid request, are in the error's object, which opencode.el keeps (=opencode-error-data=); a service before 2.2 tells every provider failure as unavailable and a model it cannot select as an invalid request, both then leaving the next to answer.  Attempts are bounded (=drover-cheap-attempts=, 4).  The route takes no system prompt, so instructions come first in the prompt, a blank line before it.  The configuration's other small requests, commit messages and summaries of package updates, go there too, so that each host's cheap models are chosen in one place, from what its OpenCode service may use.

OpenCode titled sessions with a model of its own choosing: GitHub Copilot's free =gpt-4o-mini=, which named a session after the session its first prompt quoted rather than after what it asked, or else a small model of the session's provider.  =drover-cheap-title-mode= names the cheap model for OpenCode's title agent instead.  The service takes a model for an agent only from its configuration, and its one route writing configuration (=PATCH /api/experimental/config=) patches the shell alone, into the document of highest precedence, here =opencode.jsonc=, which Org tangles; an agent file in =agent/= would set the agent's instructions too, its body empty.  So drover owns a file of its own, =opencode.json= in the service's global configuration directory, which the service loads below =opencode.jsonc= and watches; it is written whole, through a file renamed over it so the service never reads half of it, only when it changes, and never when it holds more than what drover writes there.  The model is written by provider and identifier, not as =PROVIDER/ID=, since identifiers hold slashes.  It is named again as the integrations and catalogs change, as the model is resolved again, and after the service connects, a second after the last change.  The title gets a single model, not the chain: when it fails, OpenCode asks the session's own.

** Briefs in the buffers of sessions

Claude Code shows, once its user comes back to a settled session, a dimmed line as the last of its transcript, just above its prompt: =※ recap: …=, a recap of the session in a sentence or two.  Drover's briefs say the same of every session, so the buffers of sessions show them there too, while the session is idle: opencode.el's through =opencode-session-summary-function=, which drover sets when nil, for this host's buffers and those of another host's service alike, the latter's brief its owner's, from its record; agent-shell's through an overlay of =drover-agent-shell.el= at the start of the line of the live prompt (=comint-last-prompt=, =agent-shell--live-input-prompt-p=), shown while the shell is ready, before the labels its chat mode draws there.  Claude Code's terminals show their own recap, and the mirror of another host's shell the overlay its owner drew, which spyglass mirrors as any overlay's string.

A buffer shows the paragraph on the whole session rather than the line on its last turn: lists, where sessions are told apart, show the line, but a buffer shows its last turn right above, and what it lacks is the context, what the session set out to do and where it stands; a summary written before the paragraph existed shows its line and recap.  A front end asks for a buffer's brief with =drover-brief-of-buffer=, giving the function that shows it anew; =drover-brief.el= keeps each buffer with the key of the session it showed, in a weak table, and calls that function from =drover-changed-hook= for the buffers of the sessions that changed: a brief written, or gone as the session works again.  The brief is the indexed record's, which took it in, else the record the buffer tells, as another host's.  Nothing is asked at redisplay: opencode.el asks as the session settles at its prompt, and when told anew.

* One status per session

| Status     | Meaning                                                     |
|------------+-------------------------------------------------------------|
| =waiting=  | A permission request or question waits for the user         |
| =failed=   | A turn failed while the user was not looking at the session |
| =done=     | A turn ended while the user was not looking at the session  |
| =retrying= | The running turn waits to retry a failed request            |
| =working=  | A turn runs                                                 |
| =idle=     | Nothing to do                                               |

The first three need the user (=drover-attention-statuses=).  Among them, the session waiting longest comes first: =since= is when the status began.  Seen and unseen are the backend's to track: for OpenCode, the service records when a client viewed a session, so a turn read in any client is no longer =done=.

A disconnected Agent Shell stays =failed= even once the user has seen its last turn: seeing an error does not reconnect the adapter. Its =:connection-error= and =:connection-since= describe that connection independently of the turn's outcome. During =:connection-retrying= initialization it shows =working=; only successful initialization clears the connection error. The configuration's ACP lifetime hook supplies these fields even when an adapter exits between requests, which Agent Shell's busy flag alone cannot distinguish from ready.

Claude Code's terminal can finish a reply while a background shell still runs: its OSC status says done, then disappears once acknowledged, while its live process record in =~/.claude/sessions/PID.json= says =status: shell=. The claude-code-ide backend combines both: requests first, the terminal's giving the details when present, then terminal errors, then work, then the terminal's own completion and acknowledgment. The process record is read only for a live terminal's PID, validated as for its session identifier, and cached until the file changes. One timer follows the live terminals every =drover-claude-code-ide-status-interval= seconds, two by default, hidden terminals included; only changes are reported, through the usual coalescing, and the timer stops when no terminals remain or the backend is uninstalled. No screen needs rendering and no CLI process is started. The CLI's =claude agents --json= uses =status= for interactive sessions, =state= for background agents: both are read, with =shell= counted as working as =busy= is.

Claude Code compacts a conversation of its own as it sits idle, shortly before its prompt cache expires (see [[*After a compaction][After a compaction]]), and its terminal tells that as a turn: work, then done again, with the message of the turn before.  The terminal made the session an hour younger and its turn unseen, so that a session read before showed done again, and pushed to the phone.  So work beginning while no turn runs notes how the terminal stood, its state's start, its last activity and whether its turn was seen (=drover-claude-code-ide--work=), and work ending has its transcript looked at at once (=drover-claude-code-transcripts-check=, read in the next slice, 0.05 s, before the list's 0.1 s): when the transcript tells no message since the work began, and a compaction the CLI ran of its own ending during it (=drover-claude-code-transcripts-work-between=, ten seconds of slack between clocks), the terminal stands again as it did (=drover-claude-code-ide--settle=), from the session's next record, which the transcript's change has made anew (=drover--index-followers=).  A turn records its prompt as it starts, so it never reads as a compaction; a request to the user drops what was noted, and so does another conversation.  The CLI's process record tells nothing more: it reads =busy= for a compaction as for a turn.  Until the transcript tells either, the session works on, for 2 s at most (=drover-claude-code-ide--settle-wait=), its transcript looked at again then and the session listed anew: no unseen done shows meanwhile, nor reaches the phone, which a push 2 s after a change would.  After the wait, it was a turn, as before.  The 54 minutes of an idle compaction leave no doubt between the turn before and the work.

* Actions go through the backend

Every action takes a session and calls the matching function its backend registered; an action the backend lacks is a =user-error=, and views can test =drover-supports-p= to hide it.  Whether an operation applies may depend on the session, not only on its backend: an agent-shell shell forks only when its agent can, a Claude Code terminal compacts only while it lives.  So a backend may register =:supports=, a function of a session and an operation, which =drover-supports-p= consults and =drover-backend-call= obeys, and the menus grey out what does not apply rather than offer what fails.  A backend may also tell which buffer shows a session (=:buffer=, read through =drover-session-buffer=), so views can mark the session the user is looking at.

Opening is the one action whose outcome depends on windows, which drover chooses rather than the backends: =drover-open= selects the window, then calls =:open= with no OTHER-WINDOW, so that it shows the session in the selected window.  Without OTHER-WINDOW, the window is where the current buffer sends sessions (=drover-main-window-function=, the main window beside a list in a side window), else the selected one; with it, =drover-other-window= picks another window than that one, the one showing the session's buffer, else the one used last, else a new window split from it, and never a side window, a dedicated one or one of drover's views.  The backends showed OTHER-WINDOW each its own way, through =pop-to-buffer= with or without inhibiting the selected window, and a list in a side window passed them none, so that =o= opened where =RET= did; one choice in drover makes =RET= and =o= mean the same for every backend.  =:open= keeps its OTHER-WINDOW for the backends' own callers.

** Burying the sessions that do not need the user

=drover-bury-quiet-sessions= (=B=) puts away the buffers of the sessions that do not need the user, so that those that do stay at hand.  Quiet is the opposite of =drover-attention-statuses=: idle, working or retrying.  It reads the records of the index, unmerged (=drover--index-records=), as backends last reported them, and those of the sessions drover archived whose buffers close once their turns end (=drover--closing=), since two front ends may show one conversation in two buffers, each to bury; but a conversation one backend tells needs the user keeps all its buffers, whatever another tells, and so does a buffer a backend tells shows a session needing the user too.  Sessions of other hosts have no buffer here and are never touched, and drover's lists and prompt are left out, whatever a backend reports.  Whether any quiet session has a buffer is read once, as the menu's scope (=:quiet=), as the rest of what applies.  It listed every backend's sessions then, and again to tell whether the session at point has subagents (=c=): 5 to 50 ms over 2510 sessions on Core, most of what opening the menu cost but transient's own work.  The index answers both now, the menu's question stopping at the first quiet buffer (=drover--quiet-buffers= with ANY, =drover--has-subagents-p=).

Buffers go to the end of the buffer list, windows untouched; a window showing one is quit as =quit-window= quits it, through =quit-restore-window= and its =quit-restore= parameters, so that a window or frame made for the session goes and another window shows what it showed before.  It never kills: =quit-window= would, under =quit-window-kill-buffer=, and a terminal killed ends its agent.  A window going back to another quiet session is quit again, at most once a buffer.  A frame made for the session is deleted rather than hidden as =frame-auto-hide-function= would iconify it: putting the session away is what the user asked for.  =quit-restore-window= also deletes the last window of a frame not made for the session, when it is dedicated or has nothing else to show, and closes its tab without running =window-deletable-functions=, so that hook cannot spare it: such a window is only restored from its parameters, or switched to its previous buffer, by drover itself.  Restoring follows the parameters whatever =switch-to-prev-buffer-skip= says, so the parameters naming one of drover's views already shown in another window are cleared first, as =drover-kill-buffer= keeps a view from showing twice (=drover--prev-buffer-skip=).

=quit-restore-window= selects the window that was selected when the quit one was made: other windows are quit within =save-selected-window=, as =quit-windows-on= quits them, and the selected one last, so that selection goes where quitting it sends it, not to a window quit after.

** Sessions handed their turn

Once the user gave a session what it waited for, a prompt or the answer to a request, nothing is left to do in its buffers until its turn ends, and the user's configuration may put them away.  =drover-handed-off-functions= tells of it, with the session, its buffers here, how (=prompt=, =start=, =build=, =answer=) and from where (=drover= or =front-end=).  It began as the prompt's own hook, =drover-prompt-sent-functions=, which left out =<tab>=, answers, and everything typed in a front end's own buffer; one hook for all of them keeps one function in the configuration, and one place deciding what counts.

Drover's own sends report themselves: the prompt's (=drover-prompt--sent=), =drover-build-and-go= once its backend took the text, past the agent's switch, and an answer =drover-respond= reads here for a session of another host.  An answer to a session of this host is given in its front end, which alone knows when, so each backend reports what the user gives in its front end (=drover-note-handed-off=), whether =drover-respond= opened it or not.
- OpenCode: opencode.el runs =opencode-handed-back-functions= as input leaves a session buffer's prompt and as a permission or a form is answered, there or in place; not for a plain rejection, which ends the agent's step, nor for a dismissed form, nor for drover's own sends, which go through =opencode-session-send=.  An answer drover gives here for another host, through =:answer=, is that host's (=drover-opencode--answering=).
- agent-shell: its =input-submitted=, =permission-response= and =elicitation-response= events, when a command runs them: a prompt agent-shell takes from its queue as a turn ends, an answer of =agent-shell-permission-responder-function= or another host's arrive out of commands, and the cancellations an interrupt sends say so.  Drover's own send binds =drover-agent-shell--submitting=.
- claude-code-ide: the CLI tells nothing but its state, and drover reads that late, from Ghostel's program status or the process records polled every =drover-claude-code-ide-status-interval= seconds.  So RET pressed alone in a terminal, or a digit while it asks something, is noted from =pre-command-hook=, and work starting within =drover-claude-code-ide--handed-wait= seconds past the interval is the turn the key gave: an answer when the terminal asked, else a prompt.  A digit typed in a prompt, work the CLI starts of its own, as a compaction, and a key the terminal binds typed after, the user going on there, give none; keys bound elsewhere, as those selecting another window, leave the key noted, and drover's own keys, a longer sequence, are not the terminal's.

The functions run from a timer, after the command and its windows settled, once per session however many reports came meanwhile: drover's send to agent-shell is one, not two.  The buffers are the session's, and for an answer those of the sessions above it, since a subagent's request is answered from the parent the user looks at; the buffer the user acted from follows when it is another, as an agent-shell viewport, and never one of drover's lists, which tell a session at point too.

* Front ends drover requires, and those it does not

Drover requires opencode.el (its =Package-Requires=), and neither agent-shell nor claude-code-ide.  A package manager compiles drover with its required packages alone on the load path, as elpaca does, so the backends of the optional front ends must compile without them: =drover-agent-shell.el= and =drover-claude-code-ide.el= require no front end at top level, which would fail to compile and leave them loading uncompiled.  They declare the functions and variables they use (=declare-function= with an =ext:= file, =defvar=, so that a front end's option they bind, such as =claude-code-ide-cli-extra-flags=, is bound dynamically and not as a lexical variable), use no macro of the front end, nor the =setf= of a structure's accessor, which would need its definition at compile time, and load their front end when they activate, from a function (=drover-agent-shell--activate=, =drover-claude-code-ide--activate=) that the byte compiler does not run.  =drover.el= still loads each backend once its front end is loaded, and a function of a backend autoloaded by the user's configuration loads the front end with it.  =make compile= checks this: =compile-standalone= compiles a copy of the sources with the required packages alone, warnings as errors, and its compiled definitions must match those compiled with the front ends present. The comparison reads and reprints them without evaluating them, removing generated symbol numbers and docstring positions; reprinting also canonicalizes shared-object reader labels, whose numbers alone can differ between identical builds.

* Starting backends

=drover-start= runs each backend's =:start= once, and from then on starts every backend as it registers: a front end loaded after drover started, such as opencode.el loaded lazily, joins without another call.  Views and the attention mode call it when they open, so the first view opened starts everything.  The first start also loads the modules keeping work across Emacs sessions, goals, fan-outs and wrap-ups (=drover--kept-modules=), when their files exist, each turning its mode on while some of its work is not over, then runs =drover-start-hook=, for what follows the sessions, such as =drover-summary-mode=, to come up with drover rather than with Emacs: a module never used is never loaded as Emacs starts, nor its file read.

* Subagents under their parents

=drover-tree= nests each subagent under its parent, and every view draws trees.  A tree ranks by the most urgent status within it, so a parent whose subagent waits for the user is listed with the sessions that need the user, its subagent beneath it.  =drover-tree-visible= drops the subtrees of subagents to hide and ranks each tree again by what remains, so a hidden subagent never places its parent in a group its own icon does not explain.  Subagents whose parent is not listed are trees of their own, and so is each cycle of parents, so no session disappears; =drover-tree-visible= still treats them as the subagents they are, the parent archived, deleted or not loaded, so =drover-show-subagents= hides them as it hides any other, under a filter too (see below).  Trees and siblings that rank alike keep the backend's order.

Which subagents show is one of three modes, =drover-show-subagents=: =all=, =active= (the default) or =none=.  /Active/ is a status of =drover-active-statuses=: working, waiting to retry, or waiting for the user, a turn in progress.  It is not /needing the user/: a subagent whose turn ended unseen is =done= or =failed=, which used to keep it, and its parent, among the sessions needing the user long after the parent went on; it is not active, so it hides.  A subtree shows in =active= mode when a session in it is active, a quiet subagent standing for the path to an active one.

Whether its subagents are active a session tells whether or not they are shown: =drover-tree-active-subagents= maps each session to its active subagents at any depth, from the trees of every session, before filtering and hiding, and the list draws them beside the status (=opencode-subagent-icons=), waiting ones and working ones apart, as still icons without a count: a count drawn beside an icon competed with it, and an animated icon beside an animated status read as a blink; the tooltip names them and tells how many.  So the user's session, idle while a subagent of its works, says so even with =none=.

A subagent's glyph stands under its parent's title: each row's indentation is its parent's title position (=drover-list--tree-rows=), which counts the parent's indicator, rather than a fixed step per level, which put subagents under the indicator.  Below =drover-list--max-depth=, a subagent stands under its parent's glyph instead, so titles keep room in a narrow window.

** Outside the list

The mode-line count, =drover-next= and =drover-select= used to see every live session: the count said =75= done while the list, hiding the subagents whose turn ended, showed 8, and =drover-select= in =none= hid a subagent asking a question, which blocks its parent until answered.  They now share =drover-surfaced-sessions=: the sessions the lists draw, the trees of the live sessions as =drover--view-trees= leaves them under the filter and =drover-show-subagents=, the way to an active subagent included, and every subagent waiting for the user in a tree the filter keeps, whatever the mode and whether it matches the filter or not: it is answered from the top of its tree, which the list draws, the subagent's icon beside its status.  The filter applies to the count and to =drover-next=, not to =drover-select=, which looks a name up wherever its session is (=drover-surfaced-sessions= UNFILTERED).  It applied to none of them at first, since it narrows a list for a while and was not to hide a session needing the user from the mode line.  But a filter says what the user is working on: under =:host (:exclude "reaver")=, =drover-next= opened first a session of that host, whose prompt cache was to expire soonest, the 98 sessions the filter hid making a fifth of the round.  The count follows the filter with it, since its tooltip lists what =drover-next= visits and its mouse-1 runs it, the tooltip naming the filter while one is set.  So the project =drover-select-project= sets narrows the count and =drover-next= to it until the filter is cleared, and a filter of statuses counts what the list draws: the matches, and the sessions drawn above them as the way to them.  What counts as needing the user does not change, =drover-attention-statuses=; =drover-mark-all-seen= still marks every session, hidden subagents and those the filter hides included, since catching up means them too.

The count is one number after one glyph, =drover-attention-glyph=, in a face telling the most urgent status counted, its tooltip listing the sessions in the order =drover-next= visits them (see below): one count per status drew a row of icons, each read as a status the list's header already tells.  It reads as the other indicators of a mode line, such as a mail count: a plain Unicode symbol, the robot emoji, one plain space and the number, one face over the whole string, nothing before it.  It was a Nerd Font robot in outline after two spaces, the second a stretch measured to the pixel, and a stretch after the glyph: in a mode line of emoji and symbols the icon looked foreign and its spacing differed from its neighbours'.  Parting the count from what comes before is the mode line's to do: a status composer joining =global-mode-string= entries puts its own separator between them.  The face tells the status by colour alone, as a mail count's tells unread mail (=drover-attention-face=: =drover-attention-waiting=, =drover-attention-failed=, =drover-attention-done=, each taking the colour of its status).  The count took the faces lists give statuses, which make a waiting session's bold so that its row stands out: in a mode line whose other indicators tell their state by colour, the count was the one bold among them, and only while a session waited.

=drover-next= visits sessions in the order of =drover-visit-order=: first those with a live prompt cache, whether they need the user or not, the one to expire soonest first, then the others needing the user in the order the lists draw them, then the idle ones (see below).  It visited them by urgency, as =drover-sort= ranks them, waiting before failed before done, the longest wait first: a cache about to expire waited behind older questions, and the turn the user then sent paid for the whole conversation again.  A cache is live as the lists show it, =drover-session-shown-cache-fraction=, which the list's bar draws from too: a subagent's never is, since the user sends to its parent, and one past its expiry is none.  A subagent waiting for the user ranks by the cache of the top of its tree (=drover-attention-cache=, =drover-attention-target=), and =drover-next= visits that session for it, once for the whole tree (=drover-attention--targets=): its buffer answers the subagent (=drover-session-to-answer=), and the answer resumes its turn, which reuses its cache.  A subagent waiting ranked by its own cache, none, after every session with a live one: a session whose subagent asked for a permission came after every cached session that had merely ended, though its own cache expired sooner, and =drover-next= landed on one of those instead.  The others follow the lists rather than urgency, since the user arranged those for reading (=drover-group-by=, =drover-sort-by=, the order of groups, each subagent under its parent): it is the order of =drover-view-groups= computed anew, by the lists' own functions (=drover-tree=, =drover--filter-trees=, =drover-tree-visible=, =drover-view-arrange=), not read from a list's drawing, so that it needs no list shown nor loaded, and is as current as the sessions.  Both lists draw that order, the view settings being shared; =drover-list-test-attention-order-follows-both-lists= compares it with the order the sidebar and the list in an ordinary window draw, under several settings, and the trees that rank alike keep the order of the index, as the lists take it (=drover--listed-sessions=).  The sessions the lists do not draw still need a place: a subagent waiting that =none= hides is shown for the order, as a match of the filter is (=drover--view-positions=), its tree ranking as it would rank shown.  A subagent waiting that the filter leaves out of a tree it keeps takes the place of the top of that tree, which is visited for it (=drover-visit-order=, from the places the filter's trees take, which =drover--view-positions= counts): the list draws that row, where it ranks without the subagent, and the order follows the list's rows.  Revealing the subagent there as =none='s are would have ranked its tree as waiting, ahead of where the list draws it.  For =drover-select=, which offers the sessions the filter hides, those come after the ones the lists draw, in the order they would draw them without the filter.  Caches expiring alike keep the lists' order too.

The round is a queue fixed at the first press: the sessions of the round then (=drover-attention--round-sessions=), in that order, a tree once (=drover-attention--targets=), kept as keys (=drover-attention--queue=); each press after it visits the next, the first again after the last, the echo telling the place, =3/5=.  The first press visits the queue's first even when the window shows it already.  Nothing that happens to sessions during the round changes the queue: statuses changing, as those of the sessions visited do, caches renewed by a turn or expiring as the user reads, sessions coming to need the user.  Ordering again at each press would visit a session twice or skip one.  A session gone since the first press is passed over silently, its place still counted; a round whose sessions are all gone begins anew.

A round goes on as long as nothing but =drover-next= runs between presses, as =undo= chains: any other command ends it, and the next press lines the sessions up anew, as they then stand.  =undo= reads =last-command=, which cannot tell it here: through the menu, =drover-dispatch= runs between two presses.  While a round runs, a function on =post-command-hook= judges each command as it ends (=drover-attention--after-command=, =drover-attention--chains-p=), and ends the round on any but these: =drover-next=, however run, from its key, the mode line, M-x or the menu's =j=; the menu itself and Transient's own commands, the menu shown, closed (=C-g=, or the key that opened it) or refusing a key it does not bind (=transient-undefined=); and the commands run on no intent of the user's, by pressing a mouse button, whose release runs the click's command, as the mode line's =mouse-1= runs =drover-next= after its press ran =mouse-drag-mode-line=, by moving the mouse, or by switching frames, windows or focus.  The hook is there only while a round runs, so that no command pays for it otherwise.  It judges =this-command= after the command rather than before: M-x sets it to the command it ran, and the menu to the suffix pressed or clicked.  The commands typing M-x's command name run in the minibuffer, deeper than the last press (=recursion-depth=), and are M-x's, judged as it ends; the hook run for no command, as the command loop runs it as it starts, ends nothing.  A session's buffer showing once its backend fetched it runs no command, and ends nothing either.

Once no session needed the user, a press said so and visited nothing, while the user, done answering, went on to the sessions idle, waiting for their next prompt: the round now takes them too, after the sessions needing the user, so that one key walks every session the user may send to.  A live cache comes before all, whatever the status: the next turn costs less while it lives, whether the session asked for something or ended a turn the user read, and a cache behind a long queue of sessions needing the user expired before its turn.  The idle sessions open in a buffer come before the others, which their backends resume to show, a Claude Code or Codex conversation starting its CLI: pressed on past the open ones, the round resumes closed conversations one at a time, as =RET= on their rows would, but only after every session that shows at once.  Sessions in the middle of a turn are left out, their cache live or not: there is nothing to send them until their turn ends, when they come to need the user.  So are idle subagents, which the user sends to through their parent, as their caches show none (=drover-session-shown-cache-fraction=).  =drover-visit-order= ranks, after the caches, three tiers: the sessions needing the user, the idle ones with a buffer (=drover-session-buffer=, asked only of the sessions without a cache and needing nothing, the only ones it ranks), and the others; =drover-attention-order= is its order of the sessions needing the user alone, which the tooltip and =drover-select= keep.  With hundreds of conversations listed, the first press orders them all, the tree of the sessions as before and a buffer looked for each, some 200 ms for 480 sessions; the presses after walk the queue.

The round was cleverer before, and the user found it too clever.  It went on while the user stayed on the session visited, whatever they did there, in the window of the visit or on the prompt reached from it, judged from the window's buffers (=window-prev-buffers=); a round five minutes old began anew (=drover-attention-round-lifetime=); sessions coming to need the user during a round joined it, right after the session visited; a new round on the session shown began with the second, unless the first waited for the user; and a press while a session its backend fetched was still opening waited for it, ten seconds at most (=drover-attention-open-patience=).  Each rule answered a case met, and together they made the next press hard to foresee.  The rule is now the user's own, which a press always follows: the queue of the first press, in order, until another command.  The two options went with their rules, days after they came.

The mode line's tooltip lists the sessions needing the user in that order, which is the round's among them, the time left of each live cache after them (=cache 4m=), 20 at most, rather than by status, so that it tells what mouse-1 visits of them, its last line saying that live caches come first and idle sessions after; =drover-select= offers the sessions needing the user first in that order, then the others most urgent first, completion grouping them by status.  The order costs a tree of the sessions, made when the command runs or the tooltip shows, never as sessions change; =make bench= times both.

=drover-next= tells only where it is in its round, =1/3= (=drover-attention-echo=): it once echoed the session's icon, title, place and summary, =1/1 󰗠 Fix the login redirect  drover:main=, which the buffer it displays already shows, and which filled =*Messages*= with a line per visit.  What the buffer does not show it names: a session that did not open, on one line with the reason, =2/5 Fix the login redirect did not open: …=, the error caught rather than left to Emacs, which printed it whole and no place.

A session its backend fetches before showing it, as a session of another host or an OpenCode session without a buffer, shows once fetched, in the window of the visit, whatever that window shows then.  Pressed again before, =drover-next= visits the next session, which the session fetched may then cover as it shows: the press asked for the next one.  It once waited for the session fetched, saying it was still opening, which made a press do nothing the user could see.

* Thousands of sessions

A registry holding every unarchived OpenCode session lists thousands of them: 2510 for a user of a few months, 967 at the top of their trees and 1543 subagents.  The list used to be drawn whole on every change, a tenth of a second after the last event of a burst: over a second for 2510 sessions, most of it in Magit's sections, whose markers made every insertion slower than the one before, in cutting titles to their columns by bisection, and in collecting the garbage of it all.  While a turn streams, Emacs did little else.  A change of a session now costs a millisecond or two, whatever the number of sessions, and drawing the list whole a few tens of milliseconds.

** The index of sessions

Listing every session cost a record per session on each change.  =drover-core= keeps instead an index (=drover-index=): the records =drover-sessions= lists, unmerged, by key, in the order first listed, with the tree each session is in, its parent's key and its subagents' keys, and who names whom a parent, by key or by engine, so that a session coming finds its subagents.  A backend reporting a change of session ID (=drover-backend-changed= with both arguments) has its =:session= asked for that record alone, a cheap function of an identifier; without =:session=, or reporting without a session, its sessions are all listed again and compared with what the index holds.  The hook then runs with =drover-changed-sessions=, the keys whose records or places changed, or t when anything may have: view settings, a backend reported without a backend, records of several backends showing one conversation (which =drover-sessions= merges by the buffers the user selected last, a choice the index does not follow) and parents forming a cycle, after which the index is made anew.  The OpenCode backend's =:session= reads the registry's entry; it reports the sessions opencode.el reports, by identifier.  A backend listing conversations as their engine recorded them never shares one with a front end in the index: its record gives way to the front end's, and comes back once the front end lets the conversation go, in the same pass (see [[*Front ends win][Front ends win]]).  The index keeps besides the time each session sorts by in the order of last activity, which only its taking a record in moves, so that every view, drawn whole or in place, places the session alike (see [[*Last activity, and sessions running together][Last activity]]).

Some details change without a report, such as a branch: =drover-index-refresh= lists the sessions again and runs the hook with what differs.  The list's age timer does so every minute, and a refresh right after drawing (=drover-list--relist-soon=), so that =g= shows the list at once, from what was reported, and what was not a moment later, in place.  A backend reporting every change but branches says so (=:reports-changes=), as the OpenCode backend does: the minute's refresh then compares the branch of each directory its sessions run in with what their records hold (=drover--index-unreported=), and asks =:session= again only for the sessions of a directory whose branch changed; =g= still lists every session (=drover-index-refresh= with FULL).  Listing the 2519 sessions of OpenCode's registry made 2519 records anew, catalog displays and branches included: about 200 ms a minute, in batch over 600 ms, now 11 ms when nothing changed, 28 ms when a worktree's branch did, its 48 sessions asked again and drawn in place.  Branches come from =drover-git-branch=, which reads =HEAD= without running Git and keeps what it read of each directory until the next refresh (=drover-git-look-again=) or =drover-branch-ttl= seconds; then it compares the status of =HEAD= (time, size, inode: Git renames a lock file over it), and reads it again only once it changed: a file status per directory per refresh, 53 for those 2519 sessions, however many sessions run there.  The attention count follows the index too: a session changed and those above it are looked at again (=drover-attention--follow=), and while the filter is set its whole tree (=drover-attention--follow-trees=): a match keeps the top of its tree and the way to it, and a session coming to match above a match hides it again under =none=, so a change anywhere in a tree may change what the list draws of all of it.  The tree's sessions are found as =drover-surfaced-sessions= finds them, but by a walk of the tree in the index (=drover-attention--tree-surfaced=), up for what the filter keeps and what is active, down for what shows, rather than by making its trees, filtering and sorting them: 5 ms for a tree of 200 subagents, as a fan-out makes, against 1.5 ms, most of it matching the filter.  =drover-attention-test-tree-surfaced-as-trees-say= holds the walk to =drover-surfaced-sessions= over random trees, every mode and several filters.  A tree none of whose sessions needs the user nor was counted is passed over, as while sessions work.  A session gone leaves its parent among the sessions changed (=drover--index-link=), so the tree it left is looked at again.  The count remembers the filter it was made under (=drover-attention--filter=), and is made anew under another one, however it was set, and when drover is loaded anew over a count made by another version.  Its tooltip is a function, made when shown, so that the count's string compares alike whatever the sessions it lists: mode lines are forced to be drawn again (=force-mode-line-update=, every window's) only when that string reads otherwise.  Forcing them on every change cost about 45 ms with 25 windows in 22 frames, many times a second while sessions streamed or the registry loaded; most changes leave the count as it was.  Settings changed force the mode lines of views alone, which hint at them, and a choice made in the prompt those of its buffer.

OpenCode reports many changes without the sessions they concern, as a batch of entries arriving or the prompt caches listed again (=opencode-state-updated-functions= with nil), after which drover lists the backend whole.  The backend keeps the record it made of each registry entry with what it made it of (=drover-opencode--made=): the entry, its prompt cache, the service's projects, the branch of its directory and how many times catalogs changed (=opencode-catalog-generation=), which displays of models, providers and agents read; a record of the same inputs is the same record.  The registry replaces an entry that changes rather than change it, so most compare by identity: listing the registry whole, then comparing it with the index, cost 160 ms in a graphical Emacs, and costs 6.5 ms.  The table drops records of another layout of =drover-session=, and is emptied as the file loads again.

** What the list drew

A drawing keeps its model (=drover-list--model=): its groups, each a vector of its trees in the order drawn; each tree's rows, its node as drawn, as the filter cut it and whole, and the place its top session was listed in; each row's session, inputs, measures, heading and section (linked, see "Structures print in proportion to what they hold"); the counts of each group; the summary of the rows the layout follows: for each field, how many rows have a text of each width, so that the widest is known as rows come and go without measuring the others.  Rows are reused: a row made of the same inputs, the same record (the index replaces the record of a session that changed), place, active subagents, ages as they read, live cache, frame of animation and measures, is the row of the drawing before, its heading drawn already when the layout is the same.

The order of trees in a group is total, so that where a tree goes is found from its neighbours (=drover-list--drawn-before-p=): views sort trees by urgency, by what each tree shows, then by what the filter leaves of it, then by the whole tree, then in the order sessions are listed, each sort keeping the order of the one before for ties, and then by =drover-sort-by=, ties keeping that order.  Groups come in an order of their own: statuses in =drover-status-order=, archived last; times newest first; otherwise in the order of their most urgent trees.

** Drawn in place

A change (=drover-list--follow=) makes anew, from the index, the trees of the sessions changed, as they stand and as they stood (=drover-index-tree-sessions=, =drover-tree=, the view's filter, subagents and grouping), and takes them into the model: a tree keeping its group and the shape of its rows, between the same neighbours, has the lines of its rows that changed drawn again, in place (=drover-list--redraw-row=), and its details, if expanded; another leaves its place, its sections deleted, and its rows are inserted in the new one, before the next tree drawn; groups emptied go, groups needed come in their place, and the headings of the groups touched are drawn again where their text changed.  The list is drawn whole instead when the layout would change (a text wider than its column's widest, or narrower than it), when groups would change order, when settings changed, older or archived sessions show (the index does not hold them), the index cannot be followed, or more sessions changed than =drover-list--pending-limit=, 64, past which drawing them in place costs what drawing whole does: the first look at thousands of transcripts reports them all at once.  Sessions leaving cost much less in place, the trees they leave too: while more leave than change, the change is drawn in place, unless as many leave as the list holds rows, which drawing whole empties at once (=drover-list--draw-whole-p=).  Of 2510 sessions, 967 rows, ungrouped, 300 leaving cost 12 ms in place and 88 ms drawn whole, 64 leaving (their subagents moving up, past the limit) 4 ms and 108 ms; 2507 leaving, 17 ms in place and 8 ms whole; 1000 leaving, about 65 ms either way.  Point, the mark and the windows' points and starts are kept as a drawing whole keeps them (=drover-list--anchor=).  The tests draw sessions changing at random, in place, and compare text, properties and sections with the list drawn anew after every change, and the marks the list follows in its text, the caches drawn, their overlays and the animated glyphs, by position (=drover-list-test-marks=).

The trees changed go into their groups in one pass (=drover-list--place-all=), rather than each in a copy of its group's vector, and a group made for one of them holds those going there after it: two sessions starting turns while no group Working showed made two groups of one value, and the list was drawn whole.  As time passes, the rows whose ages read otherwise are drawn in place (=drover-list--refresh-times=): each row tells when one of its texts next changes (=drover-list--times-due=, from the units of =opencode-format-duration= and when its prompt cache expires), so that the minute's refresh formats the ages of those rows alone, rather than five ages of every row, 13 ms over 967 rows in batch.

** Drawn whole, and collapsed groups drawn later

A drawing whole inserts sections with positions rather than markers, and turns them into markers once drawn (=drover-list--use-markers=): every marker of a buffer moves on every insertion before it, so thousands of sections inserted with markers made each insertion slower than the one before, and markers of a drawing gone, still alive until collected, slowed the next one; those are detached before the buffer is erased.  Sections are pushed rather than appended to thousands of siblings, and Magit's heading insertion, which copied and scanned each heading, is done directly.  The tree is made once per drawing, hash tables sized, and the garbage kept low: Emacs collects it once the heap grew a tenth, and in a graphical Emacs a collection costs tens of milliseconds.

A collapsed group's rows are drawn later, as Magit draws a collapsed body, its washer drawing them as the group is expanded: Idle, collapsed by default, holds most sessions.  Isearch draws them as it starts (=isearch-mode-hook=), so that it finds them as hidden text, and so does copying a region.  Otherwise, once Emacs is idle for =drover-list-deferred-delay= seconds while the list shows, they are drawn =drover-list--deferred-chunk= trees at a time, stopping as input comes, so that Occur, Consult and other packages reading the buffer find them: the trees drawn come first, those left after, and a change places a tree among those left without drawing it.

Every list, not the sidebar alone, now draws the rows of its first screens at once and leaves the others for later (=drover-list--rows-left=, =drover-list--undrawn=), drawn as the sidebar's are: while Emacs is idle, for Isearch, copying a region, moving to the last session (=drover-list--draw-undrawn=), and as a command brings a window of the list within two screens of where they go (=drover-list--draw-near-end=, on =post-command-hook=), so that scrolling down does not meet the list's end early.  Drawing 3537 rows whole, ungrouped with the closed conversations, cost 320 to 350 ms, 6 to 7 collections of 27 ms for the 26 MB it allocated: the text properties of each line's 14 runs, copied with their lists as a line is inserted (7.4 MB), then the section and the heading's keymap given to each run (3.2 MB), Magit's sections, their markers and overlays, and the trees and rows, made anew.  Drawing every row could not come under 150 ms, garbage being 7 ms a megabyte at =gc-cons-percentage= 0.1.  Besides, what every drawing makes costs less: a tree keeping its subagents, as most do, is the same tree, not made again by =drover-tree-visible= nor by =drover-sort-trees=, which sorts without a closure per tree (2.2 MB rather than 4.9 for 3537 trees); a session's place in the index is read from its table, not through =drover-index= for each session; the rows of a tree are gathered without a closure per tree (=drover-list--push-rows=); a collapsed session's details are drawn by one washer shared by every session (=drover-list--wash-session=), not two closures per section; and checking a structure's layout allocates nothing (=drover-layout-matches-p=).  In batch, the 3537 rows draw whole in 87 ms rather than 352, the default view's 1001 rows in 48 ms rather than 159, the first drawing measuring every text in 355 ms rather than 914, every drawing the same as drawn anew.

** Cutting text in pixels

Cutting a text to its column measured candidates by bisection, about seven per row: the search now starts where the text's average character width puts the cut, and gallops from there, and what a text is cut to in some room is known as widths are, from one drawing to the next (=drover-list--truncate=).  Widths are kept while the faces' fonts, the remapping, the frame and the measuring functions stay the same, and measured anew otherwise.

** Two lists, the sidebar and the other

The sidebar of =drover-list-side= and the list of =drover-list= are two buffers, =*drover sidebar*= and =*drover sessions*=, so that both show at once: a sidebar of 36 columns draws two lines per session while the list beside it draws columns, and each keeps its point, window start, region, sessions expanded, groups collapsed (=drover-list--visibility=), follow mode, model and drawing deferred; =drover-list-collapsed-groups= only tells how each begins.  The view settings stay global, as for every view.  Each buffer is drawn for the width of its own window; a list moved between an ordinary and a side window was drawn for one width at a time.

Both follow the same index, and a change costs each only what its own lines need.  A list shown follows it in place; a hidden one notes the keys changed (=drover-list--pending=), draws nothing, and follows them in place once shown again (=drover-list--refresh-if-needed=), its ages as the time passed then, or draws whole past =drover-list--pending-limit= keys, or after anything that draws whole, such as a setting changed.  Neither draws the collapsed groups of a hidden list while idle.  What does not depend on a list's layout is made once for both: the sessions listed and their trees, all of them for lists drawn whole, those a change touches for lists drawing it in place, with their active subagents, view and groups, and where buffers show (=drover-list--sharing=, =drover-list--shared=, bound while =drover-changed-hook= runs); the rows, a row of the other list made of the same inputs being copied with its texts and measures (=drover-list--peer-rows=), so that the sidebar opened beside a list measures only what its narrower room cuts; the widths measured (=drover-list--peer-widths=), when both measure in the same context.  Headings, sections, positions and everything a layout decides stay each list's own.

The sidebar folds nothing (=drover-list-sidebar-mode=, =drover-list--folds= nil): its sessions have no body, its groups never collapse, whatever =drover-list-collapsed-groups= says, and the commands folding sections are remapped to =ignore= in its keymap, those a heading's keymap binds included, as =RET= on a group's heading and Magit's double click, so that no key, click nor indicator (=magit-section-visibility-indicators= is nil there) expands or collapses anything.  A remapping applies to a click only while the sidebar's window is selected: Emacs looks the click up in the keymaps where it lands, but remapped Magit's double click on a group's heading through the selected window's buffer, which toggled a section of that buffer, or failed there.  The keymap of a group's heading binds the double click and the click in the margin to =drover-list-mouse-toggle-section=, Magit's toggle anywhere but in the sidebar.

A click on a session's row of the sidebar opens it, as =RET= there does: =drover-list-sidebar-click= selects the sidebar's window, moves point to the row and runs =drover-open-at-point=, so that the session opens where =RET= opens it, in the window where you work, whether the sidebar was selected or not.  A click on a group's heading, or below the rows, does nothing, as =RET= on a heading does, and selects nothing.  The sidebar binds =down-mouse-1= to =ignore=, so that no region is dragged, its rows' text being nothing to select with the mouse (a region selects rows, with the keys), and the drag, the double and the triple click too: Emacs runs an unbound double click as a single one, which would open the session twice, and its heading's keymap binds no single click.  Rows take no =mouse-face=: Emacs draws the text under the mouse in the default face merged with the =mouse-face= alone, one face for the whole run of an =eq= value, so a highlight of the row would drop the colours of its title, which tell where its session is, and the faces of its icons, and the glyphs drawn in another font would move; per run, with each run's own face under it, the highlight would cover the run under the mouse only, not the row.  The session clicked opens in the window where you work, selected then, and its title takes the face of the session there (=opencode-session-active=), which tells which row was clicked: the highlight of the row at point, where the click moved it, shows only while the sidebar is selected (see below).  =*drover sessions*= keeps Emacs's clicks.  Its groups all shown, it would draw every session as it is drawn whole, where the list leaves those of collapsed groups, Idle's among them, for later: it draws the rows of two screens at once (=drover-list--first-rows=, of the tallest of its window and frame), the first trees of each group in order, and leaves the others for later, as a collapsed group's (=drover-list--undrawn=, =drover-list--deferred-p=): drawn while Emacs is idle, a few trees at a time (=drover-list--draw-some=), or at once for Isearch, copying a region or moving to its last session; a group drawn in part has its heading and its first trees, and ends, its blank line after, as its last trees come.  A change follows it in place as it follows a collapsed group drawn in part: a tree coming among those left stays left.  A sidebar of 36 columns shows a line or two per session; the recap it once drew under one squeezed into it, and expanding it there and in the list fetched it once for both, through a recap shared between the lists, gone with it: the list alone expands sessions, and =v= previews one from either.  So its lines need no invisible character before them (see [[*Lines begin with an invisible character][Lines begin with an invisible character]]), nor room for Magit's ellipsis after them, and begin at the window's edge: its layout's =:lead= is 0 where the list's is its margin.  Rows still place the sessions at the top of a tree at the margin, so that both lists share them (=drover-list--peer-rows=): the sidebar's lines draw them =drover-list--shift= further left, the line beginning with the status glyph rather than a space aligned to 0, so that point at the start of a session is on its glyph.  Its side window has no fringes: =drover-list--set-up-side-window= sets them to 0 on the side window, with the other settings it is displayed with (strongly dedicated, its width preserved, =drover-list--side-window-parameters=), as the sidebar shows there (=drover-list--show-side=, and the sidebar's =window-buffer-change-functions=) and whenever it draws, wholly or in place, or is brought up to date (=drover-list--set-up-side-windows=), each time before measuring the width they leave, so that a side window shown by an older drover, or whose settings something else changed, gets them at the next drawing; only what differs is set.  The fringes are set not persistently, so that =set-window-buffer= gives a window the fringes of its buffer again as it shows another one, and the sidebar's buffer shown in an ordinary window keeps that window's.  A buffer-local =left-fringe-width= would have taken them off any window showing the sidebar's buffer.

The sidebar shows no cursor (=cursor-type= and =cursor-in-non-selected-windows= nil there): its rows are its unit, and the highlight of the section at point shows where point is.  =C-n= went to the end of the next line: =line-move-visual= takes the goal column from =posn-at-point=, and Emacs places a character displayed as a space, =(space :width ...)=, at the end of its line while =bidi-display-reordering= is nil (=pos_visible_p= looks for the character after a replacing display property while the iterator's scan direction is 1 or -1, and without reordering it is 0, so it reads to the end of the line), as =drover-list--reorder= has it in a list without right-to-left text; the sidebar's lines begin with such a space, the left of the status glyph's cell.  =next-line= and =previous-line= are remapped there to =drover-list-next-row= and =drover-list-previous-row=, which move between the starts of rows, sessions and headings (=drover-list--row-start-p=), with shift selection; and after any command but in the middle of a search, the sidebar's =post-command-hook= takes point, and the mark when a region is active, to the start of its row (=drover-list--sidebar-settle=), before Magit highlights the section at point.  A region then selects the rows of its ends and those between, as it shows.  =*drover sessions*= keeps its cursor and Emacs's own moves, its lines beginning with an invisible character, where the goal is right.

Without a cursor, the highlight alone shows point, so it stands out a little more there: the sidebar remaps =magit-section-highlight= to the face =drover-list-sidebar-highlight=, for the user, over a background =drover-list-sidebar-highlight-contrast= times as far from the default background as Magit's, colour by colour (=drover-list--highlight-background=), computed from the theme's colours and again whenever a theme is enabled or disabled (=drover-list--theme-changed=), or the option set.  The remapping changes no width: the measures leave it out of their context (=drover-list--measure-context=), so that both lists still share widths and rows.

As the cursor it stands for, the row at point stands out only in the window where the sidebar is selected: Magit's overlays belong to the buffer and showed it from every window, where no key goes to the sidebar.  The rule is Emacs's for the region (=redisplay--update-region-highlight=): the selected window, or while the minibuffer is selected, the window selected before it, so that a command reading there still shows the row it acts on (=drover-list--shows-highlight-p=).  The rows a region selects stand out from every window, as in Magit's buffers: while =drover-list--selected-sections= returns rows, every window showing the sidebar shows the highlights.  Face remapping is the buffer's, but a face spec =(:filtered (:window PARAMETER VALUE) SPEC)= applies only in the windows whose parameter is =eq= to VALUE: the sidebar's relative remapping of =magit-section-highlight=, and the bases of that face and of =magit-section-heading-selection=, which Magit draws the headings a region selects in, are filtered on the window parameter =drover-list-selected= being t (=drover-list--highlight-filter=), so that elsewhere neither draws anything, and Magit's overlays stay as Magit makes them.  =drover-list--set-highlight-windows= sets the parameter of each window showing the sidebar, as the selected window or a window's buffer changes (global =window-selection-change-functions= and =window-buffer-change-functions=, run during redisplay before windows are drawn, a frame selected included), as a region starts or ends (the sidebar's =activate-mark-hook= and =deactivate-mark-hook=), and after each drawing, which may leave a region selecting other rows or none.  A window that stops showing the sidebar keeps its value, read by no other buffer, and gets a new one as it shows the sidebar again.  Emacs draws a whole frame anew, its faces realized again, as a parameter a filter names changes (=window-auto-redraw-on-parameter-change=), and not a terminal's: only the sidebar's windows depend on this one, so its =:filtered= property is =ignore=, and drover draws anew, with =force-window-update=, the window whose value changed alone.  The second face's remapping changes no width either, and the measures leave it out too.  A sidebar made by an older drover gets the remapping and the hooks as this one loads.

The sidebar beside the list repeats it, so it steps aside (=drover-list--place-sidebar=): while an ordinary window of its frame shows the list at the side of the frame's main window where the sidebar is (=drover-list--beside-p=, by pixel edges), the sidebar's window goes, its side, slot and width kept in the frame's =drover-list-sidebar-aside=; once no window shows the list at that side, it is displayed there again with them.  The test is the same whether the sidebar shows or not, the list's edge against the main window's, so that it never comes back to step aside again at once.  Windows changing run it (=window-buffer-change-functions=, for a buffer replaced or shown, =window-configuration-change-hook=, for a window deleted or moved), through a timer of no delay, so that it runs once windows settled (=drover-list--place-soon=), and =drover-list= at once, before drawing for the room the sidebar leaves.  The user's choice wins: =drover-list-side= showing the sidebar beside the list keeps it there until the list leaves (=drover-list-sidebar-kept=), and hiding it, by =drover-list-side= or =q=, forgets where it was, so that it does not come back.  Frame parameters, not a variable, since each frame has its sidebar; another frame showing the list leaves this one's alone.

Frame parameters are not part of a window configuration, so windows restored behind drover's back could leave them telling what the windows no longer show.  A minibuffer restores the windows of its frame as it exits (=read-minibuffer-restore-windows=), after whatever the user did meanwhile: =consult-buffer= previews the buffer at point in the user's window, and the sidebar coming back for the preview of another buffer than the list, its =aside= forgotten, was deleted again by the restore, with nothing left to bring it back once that buffer was chosen.  So while a minibuffer is active, the windows are provisional (=drover-list--windows-provisional-p=): placing waits until it exits, through =minibuffer-exit-hook=, which runs before the restore, and the timer, which runs after the command that read, and its final =switch-to-buffer=.  Other restores, such as =winner-undo='s or a tab's, are followed as they are: a sidebar they show is no longer aside, so that deleting it then does not bring it back, and one they took away while it showed stays hidden.  drover undoes only what it did, its own stepping aside: a sidebar brought back whenever its window went missing would fight the layouts others make, as =tab-bar-new-tab= deletes side windows, =display-buffer-in-side-window= takes the slot of one for another buffer, and =winner-redo= could not remove what =winner-undo= brought back.

Switching the main window to the list beside the sidebar, as =consult-buffer= or =switch-to-buffer= does, drew the list whole twice: as windows changed, its window's change functions drew it for the room it had beside the sidebar, then the timer had the sidebar step aside, and the list, wider, was drawn whole again, 223 ms over 2510 sessions on Core.  It now waits (=drover-list--steps-aside-for-p=, =drover-list--awaiting-place=): its window's change functions draw nothing while the sidebar is about to step aside, and =drover-list--place-sidebars= brings it up to date once the sidebar went, for the room it leaves, before Emacs displays it; for that one redisplay, the window shows what the list drew last.  Placing the sidebar from the change functions themselves would have spared that redisplay, but Emacs records the windows as they are once those functions ran (=run_window_change_functions=), so that the windows the sidebar's going resized would never run theirs, a terminal's among them.  While the windows are provisional, the minibuffer active, the sidebar stays until it exits, and a list previewed meanwhile is drawn for the room it has.

A list whose width alone changed, as the sidebar shows or hides beside it, keeps what it drew (=drover-list--relayout=): its groups, trees and rows depend on neither the width nor the widths measured, so its layout alone is chosen anew from the summary of its rows (=drover-list--layout-of=) and its rows drawn in it, the changes noted while it was hidden drawn in place after; listing the sessions, making their trees and rows were most of drawing it whole.  It is drawn whole when its rows were made with other measures (=drover-list--metrics-stamp=), or when it is stale.  Titles take the faces of where their sessions are (see [[*Where sessions are][Where sessions are]]) once while windows show the same buffers (=drover-list--restyled=): windows changing ran =drover-list--restyle-titles= three or four times a redisplay for each list shown, each over every row drawn, about 1.5 ms per thousand rows; rows drawn since took the faces of where buffers were as they were drawn, and a session buffer killed where no window showed it forgets what was seen, the places being the same.  Only the buffers that may be sessions' count (=drover-list--may-show-session-p=): not drover's lists and prompt, nor minibuffers, nor internal buffers, whose names begin with a space, as transient's menu, but those lists drew a session in; a menu opening and closing, the prompt or the minibuffer restyle nothing, which looked up the buffer of every session drawn, 12 ms in the user's sidebar.

The summary line that began the list, how many sessions need the user per status, how many are listed, archived and hidden, is gone: the user reads the list for its sessions, the mode line counts what needs them, and each group's heading counts its sessions.  A list with none says why, =No sessions.=, =No session matches the filter.=, or, when only subagents the mode hides are left, at the top of trees of their own, =Every session is a hidden subagent.= or =Every session the filter keeps is a hidden subagent.=, rather than stay blank.

** Acting on thousands at once

Archiving a selection of 2202 sessions, all a list showed, kept Emacs for over two minutes: =drover--act= acted on each in turn in the command, opencode.el then starting a =curl= per request, and the answers all came back at once, each closing its buffer and reporting on its own. * Out of commands

Drover runs much of its code out of commands, and once ran a running Emacs into the ground from there.  Its files were loaded anew into an Emacs running the version before: the index of sessions, made by that version, had one slot fewer than the new accessors expected, and the next change, from a timer, read past its end.  Emacs reports a timer's error with its data printed whole, in the echo area: =Error running timer 'drover--run-changed': (args-out-of-range #s(drover--index …))=, the index of thousands of sessions written out, two million characters, which every redisplay measured again to size the echo area, laying the line out bidirectionally, for minutes, at 100% of a processor and 5 to 8 GB, on every change.  Three things went wrong, and each is now guarded against on its own.

** Errors are told on one line

Every function drover runs out of a command runs its body in =drover-with-reporting=: timers and idle timers, process sentinels and filters, the callbacks it gives front ends and services (OpenCode's, ACP's, the prompt's continuations, recaps and previews), its functions on the hooks of Emacs (windows, themes, fonts, buffers killed, =kill-emacs-hook=, =after-load-functions=) and of other packages (opencode.el's, agent-shell's, claude-code-ide's terminals'), and help-echo functions.  An error is reported by =drover-report-failure=: one line, =Drover CONTEXT: SYMBOL: MESSAGE=, its data printed briefly by =drover--brief= (strings cut at 40 characters, records, hash tables and functions named by their type, lists and vectors cut after 8 elements, 2 levels deep), at most =drover-error-length= characters, then, for an error reading a file, the end of its name.  The same error out of the same code is told once in =drover-error-interval= seconds: a timer failing at every tick says so once a minute.  =debug-on-error= enters the debugger first, as for any error.

=drover-changed-hook= runs each of its functions on its own (=drover-run-hook-reporting=), so that a view failing leaves the others drawing; the index failing to take changes in is dropped, and the views draw everything anew from one made again.  An index of transcripts failing on a file goes on with the others, and looks again at its time.  What drover signals itself carries no structure: a structure is checked before its accessors read it (below), rather than let =aref= signal with it; =drover-error-message= replaces =error-message-string= wherever an error becomes text, and =drover-warn= and =drover-message= bound what they show (=drover-format-message=).

** Asking nobody

What drover does for a user not at this Emacs, another host's (see remote.org) or an agent's (=drover-anvil.el=), runs in =drover-quietly=: buffers show in no window, =inhibit-interaction= makes a question signal, which its caller hears as a failure, =drover-error-message= saying =it asked a question, which nobody is there to answer=, and =use-dialog-box= is nil.  A question asked out of a command, from a timer or a process's filter, takes a dialog box whenever the last event was no key, as a file notification leaves it, and a dialog box ignores =inhibit-interaction=; on Windows it stops Emacs whole until answered, its timers, its processes and its connections to other hosts too.

That happened.  A prompt typed in Reaver's mirror of a shell on Core while its turn ran went to agent-shell's queue there; interrupting the turn from the mirror, agent-shell, reading the cancelled turn's end in its process filter, asked whether to send the prompts queued, in a dialog box on Core's screen, where nobody was.  Core stopped; Reaver, opening the session again, waited for Core's answer in the command until the heartbeat dropped the connection.  Asking is agent-shell's, and late, out of any action of drover's, so drover's interrupt of a shell (=drover-agent-shell--interrupt=), from a list, a mirror or an agent, sets the queued prompts aside before the turn ends (=drover-agent-shell--hold=), and those queued meanwhile as its =turn-complete= event comes, before agent-shell looks at its queue; once agent-shell is done with the turn, from a timer, they are queued again ahead of any queued since (=drover-agent-shell--release=), sent when the agent ended the turn before the interrupt took, as agent-shell would, else left queued and shown with how to send or remove them, as answering no leaves them.  drover asked already, if anyone: its interrupt is confirmed.  A request of the shell failing while it holds them gives them back only once no turn runs; a shell closed meanwhile puts them in the kill ring, as its other unsent text.  The other side of it, a host waiting for a peer in a command, is in remote.org's =Never blocking=.

** Text from outside is bounded as it comes

What drover shows comes from outside: titles, prompts, replies, the summaries of requests, errors backends tell, file names.  A first prompt pasting a log is a line of hundreds of kilobytes, which measuring in pixels lays out whole, as drawing does.  So drover bounds texts where it takes them in, once, rather than where it shows them, in many places:

| What                                                              | Where                                                                            | Bound                                                                                        |

| A record's title, agent, model, effort, provider, project, branch | =drover--bound-record=, from =:sessions=, =:session= and fetches                 | its first line that is not blank, =drover-line-limit= (300) characters, =…=                  |

Bounding returns the string itself when it is within bounds, and a record itself when all its texts are, so that records compare alike and nothing is allocated for the common case; =drover-bound-line= looks at no more of a line than it keeps.  A title is its first line: a title of several lines read as several titles.

A transcript's first prompt on a line longer than the window the reader reads, 64 kB, is cut by it, and does not parse: Claude Code titled such a conversation by nothing, and drover left it out.  The reader then reads the prompt from the start of its record, =drover-transcript-string-prefix= decoding the start of a JSON string cut anywhere (within an escape, a surrogate pair or a character's bytes), Claude Code's records of a prompt and Codex's events alike.  JSON strings are scanned by a loop rather than a regexp, whose matcher overflows its stack on strings of tens of kilobytes.

** Structures print in proportion to what they hold

Emacs prints a value whole wherever nothing bounds it: an error's data in a command, what =format= and =prin1-to-string= are given, a value evaluated.  A profile of the list's first drawing, its entries formatted with =%s= to write it out, printed the closure drawing a group of 3500 sessions, and its batch Emacs grew past 19 GB in about a minute before a guard killed it.  Each row led to its section, and each section through its parent to the root section and every section of the buffer, printed again for each row; each row led to its tree and each tree to its group and all its trees; the model's tables of trees and rows led back to them all again: a row among 200 sessions printed as 20 million characters, and the model of 200 passed 1.5 GB within seconds.  The links up a drawing and to sections (a row's tree and section, a tree's group, a group's section) are held through =drover-link=, an uninterned symbol whose value is what it leads to and which prints as its name: each structure prints once, from where it is held, the model about 5 kB a session.

The remote layer did the same: each request asked of a peer, which its spyglass connection holds until answered, and each timer acting on a peer, held a closure leading to the peer, and from it to all its sessions and to its connection with every other request: with recaps of 50 of a host's 200 sessions asked and not yet answered, the connection printed past 4 MB.  Closures kept in timers, given to spyglass or to backends hold the peer, the subscriber or the remote state they act on through links too, and those that only name a peer, its label.  The indexes of transcripts, the queue of scheduled prompts, the index of sessions, the tables of the mode line's count and the recaps were found to print in proportion already: their entries hold keys and records, not what holds them.

Tests print whole, against a bound of 10 kB a session, everything drover keeps (=drover-test-kept=): the values of its variables, global and local to its buffers, its timers, the filters, sentinels and properties of its processes, with both lists drawn, older and archived sessions shown, every session expanded and its recap kept, the mode line counting (=drover-list-test-prints-in-proportion=); with another host's sessions received and this host's sent to it, a recap asked of 50 of them not answered yet (=drover-remote-test-prints-in-proportion=); with half the prompts scheduled being delivered (=drover-schedule-test-prints-in-proportion=); with the transcripts and rollouts of 100 conversations read.  What is held once a session, a row, a tree, a record, an entry of an index, a prompt or its delivery, must print within 20 kB whatever the sessions: one leading back to what holds it would print it all.

Spyglass holds each request it waits an answer for in its connection, and a timer for each whose closure leads back to the connection, and so to every other request: printed from the list of timers, that is the square of the requests pending, whatever drover's closures hold.  It is spyglass's to change.

** Structures made by another version

Drover keeps structures for as long as Emacs runs: the index of sessions, each list's model, rows and trees, the indexes of transcripts, the older and archived sessions fetched, the sessions the mode line counts.  =cl-defstruct= accessors read slots by position, and check only the type's name, which another version's structure shares.  So each long-lived structure holds in its first slot, =stamp=, whatever the version, the layouts of the types it is made of: =drover-layout= makes it from =drover--layouts=, where each file notes its types as it defines them (=drover-note-layout=), a type whose slots changed getting a new stamp, compared with =eq=.  Code reaching such a structure from a variable, a timer or a hook checks it first (=drover-layout-current-p=, =drover--index-current=, =drover-list--current-p=, =drover-transcript-index-current-p=, =drover--fetched-current=, =drover-attention--current-p=): a structure of other layouts, or one made before stamps, whose first slot is something else, is dropped and made anew, with one short message, =Drover: index of sessions made by another version of drover, made anew=, and views draw everything anew; a timer of an index of transcripts dropped does nothing more.  Reloading the same version changes no stamp.

A file loaded into an Emacs running an older drover-core would find what it needs at load time missing, =require= loading nothing already provided: each file loads =drover-core= anew when its =drover-core-generation= is older than the one the file needs.  A test loads drover d61bfdf, the version before stamps, lists 3000 sessions and draws them, then loads this one over it, its files in any order, and follows changes from timers: the longest message is the one telling the index was made anew; without stamps, it was the index printed, 900 kB.

That test kept only the last five messages, and checked that one of them told the index was made anew: as timers ran, more errors came, and it failed now and then.  It now checks that the two messages telling the index and the list were made anew are all there is, which found three faults loading this drover over another.
- The records backends made with the drover running lack the slots that came since, such as the host of a session: read past their end, every listing of the fake backend failed.  A record takes the slots it lacks, nil, as drover takes it in (=drover--whole-record=, in =drover--bound-record=).
- Accessors are inlined where code is compiled or loaded from its sources, by the compiler macros of their structures as defined then: the functions of =drover-list.el= before its structures, compiled or loaded where another version of drover runs, read the slots of that version's structures, the rows of a model at the place of its trees.  The list's structures now come first, and a test checks that each file defines its structures before the code calling their accessors.
- A slot the links replaced leaves the compiler macro of its accessor, which inlines a read of the slot now holding the link, on the name of the function following it: =drover-list.el= removes those compiler macros as it loads and compiles.

* One look, opencode.el's

The list, the mode-line count and the prompt drew sessions with drover's own glyphs, faces and animations, and opencode.el's mode line and pickers with theirs: the same icons in two options, faces of the same meaning defined twice, and drifting, drover's Needs you gold where opencode.el's was orange.  Drover now requires =opencode-look=, opencode.el's single definition of how sessions look, and draws the sessions of every backend with it: status icons, faces, names and animations, the icons of subagents and of the archive, the faces of where a session is, of agents, of an effort chosen or inherited, of the context and the prompt cache, and how ages and token counts read.  What only its list shows stays drover's: its proportional font (=drover-list=, =drover-list-header=), the headings of groups and secondary details (=drover-heading=, =drover-dim=), and the robot and faces of the mode-line count (=drover-attention-glyph=, =drover-attention-face=), as opencode.el has no list nor count.  =drover-status-order= takes its default from =opencode-session-statuses=, and stays an option, as it ranks sessions for drover's views.

Drover's former options, faces and functions are obsolete aliases of opencode.el's (=drover-ui.el=, =drover-list.el=).  An alias made over a variable bound already, as a configuration setting it before drover loaded, or an older drover reloaded, binds it, would lose its value: =drover--adopt-option= gives opencode.el's option the value first when it is the user's, other than the former default, and unbinds it.  It is in =drover-core=, whose generation, 2, has files needing it load the core anew over an older one.  Every file using the look requires =opencode-look= itself, so that one loaded over an older drover finds it.

Moving the formats of ages and token counts into opencode.el made the first drawing of =make bench= 30% slower, the bench loading opencode.el's sources uncompiled: =make bench= now compiles a copy of them, as installed, and measures what the user pays, the same as before to the noise.

* Measuring in pixels

Lists read better in a proportional font, so the views lay text out in pixels: columns align with =(space :align-to (X))=, and long text is cut by =drover-truncate-to-pixels=.  =drover-text-pixel-width= lays text out in a buffer of its own with the view's face remapping and the fonts of the view's window, because =string-pixel-width= ignores face remapping before Emacs 31.  On a text terminal a pixel is a character cell, so the same layout holds there and in batch tests.

The mode-line count of =drover-attention-mode= draws a glyph and a plain space before its count, and keeps the count off the glyph's ink only where the space does not, measured over the face =mode-line= in the selected frame's fonts (=drover-attention--measure=): the space becomes a stretch as wide as the ink reaches past the glyph's advance when that is wider than a space, and a stretch goes before the glyph when its ink reaches left of its start.  Measured in the fonts of the configuration it was written for, neither is needed: the robot emoji draws within its advance, and FiraCode Nerd Font's =nf-md-robot_excited_outline= draws ink from 0 to 1790 units of its 1950 per em for an advance of 1200, 590 past it, which the space after it, 1200 units, covers; a proportional mode-line font, whose space is narrower than a Nerd icon's overflow, would need the stretch.  The count is computed whenever sessions change, often during a turn, so the glyph is measured once per font and face, keyed by the frame and the fonts of the mode line, and measured anew when a font is set or a theme enabled (=after-setting-font-hook=, =enable-theme-functions=).

Layout measures advances, but a glyph's ink may reach past its advance: the Nerd Fonts but their Mono variants give an icon the advance of one cell and up to half a cell more ink (the robots of FiraCode Nerd Font draw 1790 units of ink for an advance of 1200), so text laid out right after an icon was drawn on it.  =drover-text-ink-extent= measures how far a string's ink reaches, from the bearings of each glyph (=font-get-glyphs=) in the font =font-at= picks for the window's frame, the fontset's fallback included; =font-at= merges a string's faces over the frame's default face, so the string names =default= last for the view's remapping of it to count.  The list draws each glyph in a cell (=drover-list--cell=) as wide as its ink or its advance, whichever is wider, padded with stretches: every status glyph and frame shares one cell, so that titles line up whatever the status, and so do the two subagent glyphs.  Batch tests have no fonts: a fake font gives some characters ink past their advance, and the tests check that nothing a line draws overlaps.

* Lines begin with an invisible character

Magit hides a collapsed section's body under an invisible overlay.  Emacs, though, handles a =display= property before invisibility where it stops, at the start of invisible text: a body beginning with an aligned space, =(space :align-to X)=, has that space drawn at the start of the next visible line, which then begins X pixels in.  Every line of the list but group headings begins with such a space, so collapsing a session moved the next session's line under its own title, and collapsing a group moved the next group's heading to the sessions' margin; expanding drew the body at the right place, now out of line with a moved heading.  Each line of a session's section begins instead with =drover-list--line-start=, an invisible character without a display property: a hidden body begins with it, Emacs skips the whole of it, and the next line starts at the left edge; shown, it takes no room.  The sidebar, which hides no line, begins its lines without it (=drover-list--line-prefix=): there it only placed the cursor, at the start of a session, before the margin's space.  Positions within a line, such as those of the prompt cache's bar, count from past it, and whether a line shows is told by its newline (=drover-list--line-shown-p=), its first character being always invisible.  The tests measure where lines are drawn with =window-text-pixel-size= from the start of the screen line, as the display finds it, collapsed bodies included.

* Keys: four sets in one menu

Every key belongs to one of four sets, and no key to two: session keys act on the session at point, prompt keys on the prompt the user writes, global keys anywhere, view keys on the settings drover's lists share.  Because they never collide, one menu, =drover-dispatch=, holds all four, and a key means the same everywhere.  Lists of sessions bind the session keys directly (=drover-session-map=, inherited by drover's views and added to other lists by =drover-session-keys-mode=); everything else goes through the menu, which the user binds to one global key.  A test reads every entry the menu defines, those an =:if= may leave out and those of included groups, and fails on a key two entries share (but =RET=, Send or Open, whose predicates are opposite) or on a key prefixing another.

The menu shows every entry that may apply where it is invoked, greying out those that do not now, and a group's title when the whole group does not; what cannot apply there is left out, so that the menu holds what the user may use: the view settings while none of drover's lists is in sight (=drover-dispatch-view-shown-p=, ~=u~ in a list of another front end showing its subagents itself), and the prompt keys editing or reading what a prompt buffer shows (=S-RET=, =i=, =k=, =/=, =@=, =y=, =t=, =T=, =O=) outside buffers defining prompt actions (=drover-dispatch-prompt-buffer-p=).  Both depend on where the menu opens, never on the session at point, so that moving in the list leaves the menu's entries in place.  What applies is computed once, when the menu opens (its scope, from =drover--context=), since finding the session at point may ask the backends for every session.  The groups are titled after what they do, Sessions, Prompt, Prompt runs, Input, Conversation, Session, View, Field, Columns and List, with no Global group: a title naming the set a key belongs to told the user nothing they could act on.

Other packages add their global commands to the menu relative to drover's keys, as Magit extensions do: more lists of sessions after =p=, before drover's search, =S=, the OpenCode backend's search of open buffers having made way for it (see [[*Searching sessions][Searching sessions]]); more ways to pick a session or prompt go after ='=, the Prompt group's last (its ="=, =N=, =E= and ='=), before the scheduled prompts of =#=, or after =b=.  These places are kept stable on purpose.

The menu closes on =C-g=, transient's key, on every key the user binds it to (=drover--dispatch-close-entries=, whichever opened it), but those of its own entries, which keep their command (=drover--dispatch-own-keys=, the keys of every entry read once, =drover--menu-keys=), and on =q=, a key of no set: drover's lists and reports quit on =q=, and the user reaching for it in the menu that opened over them means to close the menu.  Drover's other menus (=drover-view=, =drover-search-menu=, =drover-usage-menu=, =drover-prompt-options-menu=) include the same hidden group, =drover--menu-close=, rather than =transient-bind-q-to-quit=, which would change every transient of Emacs.

** Values beside their keys

Settings show their value beside the key that changes it, as Magit's menus do: infix objects whose =transient-format-value= reads the setting each time the menu is drawn, and whose command leaves the menu open (=transient= is t for infixes), so that changing one redraws the menu with the new value.  The view settings are =drover--setting= infixes; choices few enough to list show them all, the current one in =transient-value=, the others in =transient-inactive-value=; a value that does not apply is dimmed.  The agent, model, effort and directory entries are =drover--prompt-option= infixes over the prompt actions' own commands, so that their keys stay those the prompt's header names: they show what the action would change, found as =drover-prompt-target= finds its buffer, never calling =drover-default-prompt-buffer-function=, which may create a buffer.  In drover's prompt, its effective options, chosen highlighted and inherited dimmed as its header shows them; in a session's buffer, or a list on a session whose buffer is open, the session's, its model and effort as its backend's =:options= tells them when it can, since they change before the backend reports.  The column's title says whose they are, Prompt runs or Session runs.  Values are cut to a width (=drover--menu-value=), a directory keeping its end.  Send names where the prompt goes when =drover-dispatch-send-target-functions= tells it, a hook the prompt's target picker may answer.

** Laying out the menu

Transient lays a prefix's groups out as written: rows of columns, each row as high as its highest column.  With some seventy entries, the old menu took 24 lines at any width, plus the View menu, while most of a wide frame stayed empty.  The menu is now one group of class =drover--menu-flow=, whose =transient--insert-group= method lays its children out for the width of the menu's window (=drover--menu-width=, that of the window it will show in before it does, beside side windows such as the sidebar).  Each child is a column; a column without a title continues the one before it, and such a group may show its parts side by side or under each other (=drover--menu-block-layouts=).  Groups keep their order and fill columns from the top, as text fills a newspaper's, a column's width that of its widest group, and rows of such columns when the width is too narrow for one row to be lowest: =drover--menu-plan= finds the plan taking the fewest lines, then the fewest rows, by a binary search on the height for each run of groups (=drover--menu-row=, the narrowest columns of a height by dynamic programming, =drover--menu-arrange=) and dynamic programming over the rows.  It takes two to four milliseconds on Core, so the plan made for blocks of the same sizes is kept (=drover--menu-plans=, sixteen of them): a menu opened again where it opened before lays out at once.  A layout tells its size from the widths of its parts, and only the layout shown is inserted, a cell at a time (=drover--menu-pieces=, =drover--menu-insert=), no line made a string first: every possible layout's lines were made as strings, then the lines of the menu again.  Across 240 columns the menu takes eight to eleven lines, across 160 about fifteen, across 100 about twenty-five.

A plan computed afresh each time would move entries whenever a value's width changed, as the user changes a setting or moves in the list, the title of the List group following.  The prefix, of class =drover--menu-prefix=, keeps the plan it was drawn after, and redraws after it while it fits the window; a new menu, or a window grown too narrow, is planned anew.  Transient's single column mode, documentation mode and variable pitch alignment fall back to transient's own columns.

** The menu beside the list

The menu acts on the session the current buffer tells (=drover--context=): a list's row at point, a session buffer's own session.  A buffer telling none, such as =*drover*= or a file, would leave every session key greyed out; when drover's list shows in a window of the selected frame (the most recently used of several), the menu acts on that list instead: the scope records the session at that window's point and the window (=:window=).  A session buffer keeps acting on its own session, since its user means the conversation in front of them.  Global and prompt keys keep to the current buffer, so prompt predicates ignore a list shown elsewhere.

The view keys need no session: they change settings every list shares, and apply whenever one of drover's lists is in sight, in a window of any visible frame, a session buffer included (the scope's =:shown=, =drover-dispatch-view-shown-p=); with none in sight, a change would show nowhere, so they are left out.  Follow mode is a list's own: =-f= sets that of the list the menu acts on, else of the list shown on the selected frame (=drover--view-window=).  ~=u~ also applies in a list of another front end that shows its subagents itself (=drover-toggle-subagents-function=), whose mode the menu does not show.  Peeking keeps needing a list, and the session keys a session: from a session buffer they act on its session, not on the list in sight.

Commands need no change for this: the columns of the Session group carry a transient =:advice*=, =drover--dispatch-in-list=, which runs the command, interactive specification included, with the list's window selected, so that it reads the session at that window's point as if typed there.  Edit pending, =E= in the Prompt group, carries the same advice on its own entry.  Selection then returns where the user was, unless the command took them elsewhere, as opening a session does.  The View menu keeps the list's window as its scope, so that follow mode, the list's own, is set in the list.

While the menu acts on drover's list, here or beside, a List group moves its point: =C-n=, =C-p=, =M-n=, =M-p=, =M-<= and =M->= (none bound by transient, nor by another set), as suffixes that stay in the menu.  Their advice, =drover--dispatch-navigate=, runs them in the list's window between the list's own =pre-command-hook= and =post-command-hook= functions, which the command loop runs in the current buffer only, so that follow mode and Magit's highlight follow; it then reads the scope again from the same window, and the prefix's =:refresh-suffixes= redraws the menu: its title names the new session at point, and what applies to it is greyed out anew.  The list binds none of them: Magit's keys move there.

=RET= is the one key with two meanings, never shown twice: in the List group it opens the session at point, except in a buffer defining the =send= prompt action, where the List group leaves it out and the Input group shows Send; elsewhere the Input group leaves Send out.  A prompt lost to a mistaken =RET= costs more than reaching for =o=.  =C-u= stays transient's prefix argument, so =C-u RET= opens in another window.

Send also sends drover's prompt from a buffer that defines no =send= of its own, while =*drover*= holds more than blanks (=drover-prepared-prompt-function=, =drover-prompt-prepared-buffer=, cheap, as menus ask at every redraw): =drover--prompt-target= finds that buffer for =send=, and =drover--prompt-call= runs its action there, in its window if shown, else in the buffer, so the prompt need not show; the target chosen for it, or the picker, and its options go as from the prompt, and Send's value names the target.  Which =RET= wins then depends on where the user types.  From another buffer, the menu acting on a list in sight, =RET= sends (=drover-dispatch-list-return-p=): typing in a file beside the sidebar, the user means the prompt they prepared, not the session at the sidebar's point.  In the list itself, =RET= opens, as =RET= does there unprefixed, and Send moves to =M-RET=, shown only when =RET= opens, so that the two =RET= never show together and each key keeps one action.

** Opening sessions by number

The digits open a session by its number, =1= to =9=, =0= the last (=drover-list-open-numbered=), both in the lists, which bind them, and in the List group, so that from a file beside the sidebar =C-' 3= opens its third session without moving there.  They need no session at point, so they apply wherever one of drover's lists shows on the selected frame, a session's buffer included, where the menu acts on the buffer's own session (=drover-dispatch-numbers-p=): the list numbered is the one the menu acts on, else the one in sight (=drover--dispatch-numbers-window=), and the command runs in its window (=drover--dispatch-in-numbered-list=), so that a session opens from there as =RET= there opens it.  The List group shows then with that entry alone, its title naming no session; its moving keys keep to the list the menu acts on.  Working in a session's buffer beside the sidebar is where switching by number is wanted most: first shown only while the menu acted on a list, the digits did nothing there.  A number counts the sessions at the top of their trees (=drover-list--numbered-trees=, over the model's groups and trees, which are in the order drawn, in one pass for the ten digits), not subagents: a subagent appearing or ending would otherwise shift every number below its parent while the user reads them.  A subagent whose parent is not listed, archived, deleted or not loaded, is at the top of a tree of its own (=drover-tree=), yet comes and goes as any subagent does: counting trees alone numbered it, so the trees it tops are passed over too (=drover-list--numbered-p=).  Sessions of collapsed groups are not counted, as moving passes them over.  Point goes to the session's row, which the command opens with =drover-open-at-point=, so that it opens where =RET= there would, from the sidebar in the window where you work; a number among rows left for later draws its group first (=drover-list--draw-group=).  The command reads the digit from =last-command-event=, one command for ten keys, and asks for the number when run otherwise, by =M-x= or a click on its menu entry.  In the list, the digits replace Magit's =1= to =4=, which show sections down to a level and mean little in a list two levels deep; the sidebar folds nothing, and ignored them.

In the menu, ten entries would take ten lines.  The List group shows one, of class =drover--menu-digits=, on =1=, whose key shows as =1…9 0=; the nine others are entries of a hidden group of the menu, on the same command, under the same predicate and =:advice*=, which bind their keys without showing.  Transient tells the entries of one command apart by their key, so each runs with its own.

The list's numbers show only while the menu binds the digits: a column of them would take room from the titles for a moment's use.  Then the list they number, the one the menu acts on or else the one in sight, shows each number on its session's row, =1= to =9=, and =0= on the last unless it has one of those, in place of the status glyph (=drover-list-number-rows=, in the face =drover-list-number=, a key's).  An overlay displays the digit over the glyph's cell, which =drover-list--status-glyph= marks with the property =drover-list-status-cell=, its =before-string= and =after-string= padding it to the cell's width: Emacs ignores the display properties of the string an overlay displays, so that spaces padding the digit there are drawn a space wide, and move the title.  The cell holds the ten digits as it holds every status glyph and frame (=drover-list--metrics=), so that no title moves and nothing is laid out again.  The other places were worse: a digit before the glyph moved every title, and a margin narrows the window, which lays the sidebar out anew as the menu opens and again as it closes, what made opening the menu slow before.  The overlays show in the window the digits act on alone, by their =window= property.  The list places them again at the end of every drawing, whole, in place or of rows drawn later (=drover-list--draw-numbers=), touching only those whose row, digit or window changed, since each change of an overlay has Emacs lay out the lines of the windows showing the list.  A row left for later shows no number until drawn: drawing the rows below for the =0= of the last would draw most of the list as the menu opens.  The status glyph is hidden meanwhile; the title's colour, the age and the summary still tell the session.

Transient runs no hook as a menu refreshes, nor as a minibuffer read suspends it, and the prefix's =environment= slot, which wraps setup, refresh and redisplay, is experimental; but the list numbered changes with none of these.  =drover-dispatch= adds one function, =drover--dispatch-menu-changed=, which stays, to two hooks: =transient-setup-buffer-hook=, run as a menu's buffer is made, as it opens, resumes after =C-z= or comes back after a minibuffer read, and =transient-exit-hook=, run as a menu exits, another replacing it or not.  It brings the list showing numbers in line with the menu open (=drover--dispatch-number-rows=): the list numbered while =transient--prefix= is =drover-dispatch=, none otherwise, a first check that costs other menus nothing.  The command does so too once set up, its buffer having been made already when it replaced another menu.

** The view settings

The settings of the list have keys in Magit's families rather than keys of the session set: sorting, grouping, filtering and what shows take many values each, which one key per value would spread over the whole keyboard.  Options taking a value begin with ===, switches with =-=, as in Magit's menus.  The subagents, older and archived sessions shown are filters (~=u~, ~=O~, ~=z~), not of View: they keep sessions out as the filter does, the user finding them "really a type of filter"; =U=, once the list's own key for the subagents, went with them, a setting having no key of its own.  They were once a menu of their own, =V=, which hid the values the user wanted to see; they are now groups of =C-'= (=drover--view-columns=, a =transient-define-group=), and =V= in the list opens them alone, the same entries on the same keys.  The list shows none of them: its buffer tells sessions and how many each group holds, the menu the settings and their keys, the mode line a terse hint (=ungrouped, last activity ↓=, =by status=, =+subagents=, =filtered=); a hint naming keys in the buffer would go stale as soon as the user bound them otherwise, and repeat what the menu shows.  The subagent mode shows its three values, the current one highlighted, and cycles them as =drover-toggle-subagents= does.  Each field of =drover-list-fields= but the title has a switch, changing =drover-list-hidden-fields= for the session, a user option to keep the choice.

The settings of a field share a row of the Field table, a =drover--menu-table=: its name, its filter, an option, then its column, a switch, on the same letter (~=m~ and =-m=, ~=p~ and =-p= for the project, its column labelled Project, ~=v~ and =-v= for the provider, ~=d~ and =-d= for the last activity, its column the age), each key beside its value, as Magit shows them, the switch telling =shown= or =hidden=, since the row names the field.  Filters and columns were once groups of their own, Filter and Columns, in which the keys of a field lay apart and the menu took three lines more; the user asked for the keys of a field side by side.  The subagents, older and archived sessions shown head the table, as filters, their cells spanning the column of columns they leave empty, as do the last cells of other rows, so that a long value widens no column; ~=c~, under the filters, clears them.  The Columns group keeps the switches of the fields no filter takes, shown as Magit shows a switch's argument: highlighted while the field may show.  Each row is a =drover--menu-table-row= group whose suffixes are its cells, real infixes on their own keys, the Nth suffix of every row in the Nth column, so that a cell an =:if= leaves out, such as the host's filter while no other host is known, leaves its place empty; the table's title formats its lines, then each row formats as its whole line, so that the table lays out wherever a column of entries does, in transient's own columns too.  In =drover--menu-flow= it shows in two halves, side by side or one under the other, aligned alike, so that the planner may put it where room allows.

* The session at point, in lists and prompt buffers

Commands on a session take it as an argument and read it, interactively, from =drover-session-at-point-function=.  Lists set it to the row at point; a buffer belonging to one session, such as an OpenCode session buffer or an Org buffer where prompts are written, sets it to that session.  So the same command works from a list and from the conversation, and backends need no command of their own.

Parents and subagents need no backend operation: they are found among the sessions through =drover-session-parent=.  A parent the backend no longer lists is still opened by its identifier.

Answering a session answers its tree's requests: its own when it has some, else those of the subagent below it waiting the longest, at any depth (=drover-session-to-answer=, over the index's subagents), so that the menu's Answer applies on a parent whose subagent asks, and answers it there, from the parent's row or buffer.  It used to apply only to the session's own requests: a parent waiting on its subagent's question had to be left for the subagent's row or buffer, a background subagent's question never even marking the parent's buffer.  The backend answers the subagent's request as its own, so the tree is found once, by drover, whatever the backend.

* Prompt actions

Prompt buffers differ (a Comint buffer for OpenCode, drover's own Org buffer, =*drover*=), but the user's gestures are the same: send, attach, revert, choose the model.  A prompt buffer declares the actions it implements in =drover-prompt-actions=, each a command; drover's prompt commands look for the buffer an action applies to (=drover-prompt-target=): the current one; in a list, for the agent, model, effort, directory and last answer, the session's buffer; for the agent, model, effort and directory a default prompt buffer; and for the last answer the prompt buffer visited last.  The actions editing or reading the prompt itself (send, schedule, attach, slash, mention, revert, copy the block or open the link at point) apply only in the prompt buffer, since from a list the user sees neither its input nor its point.  An action applying to a buffer shown in a window runs in that window, so that it sees the point the user sees.

Compacting and forking exist both ways: in a prompt buffer they are prompt actions (forking at point), in a list backend operations on the whole session.

OpenCode session buffers bind =model= and =provider= to drover's logical-model and provider pickers, rather than OpenCode's provider-qualified model picker. They read the model and provider catalogs in the buffer's service binding, so a relayed buffer reads its owner's offerings, never the viewer's local engine source. =drover-selection-resolve= chooses the native offering, preferring the current provider when the model is available there; a supported explicit effort is translated to its native variant, otherwise the new model takes its default. =drover-read-model= with =required= omits the prompt's no-choice entry and preselects the current logical model. The actions switch the session immediately, without writing choices into drover's prompt; the menu's Provider value describes that same session.

* Earlier prompts quoted, withdrawn prompts edited in the prompt

Comint sends an earlier input again as soon as =RET= is pressed on it; opencode.el no longer does, and hands the region, else the line at point, anywhere in the transcript, to =opencode-old-input-function= instead, which knows nothing of drover.  The OpenCode backend sets it, when the user has not, to =drover-opencode-quote-old-input=, the way it sets =opencode-command-keys-function=, and resets it as it unloads: it quotes in the session buffer as =drover-prompt-dwim= does (=drover-prompt-add-context=), so that =RET= there does what =C-' "= does, the line or region quoted with a link to where it is, but quotes the text opencode.el picked, which leaves out what the transcript's overlays hide, the blocks of a collapsed group and the hidden prompt string before a prompt's first line: a region over a collapsed group quotes the group's line, not the blocks it hides, and a block's summary its line as it shows.  =C-' "= quotes the buffer's text, as in any buffer.  It first put the whole prompt in the prompt, set to go to its session (=drover-opencode-edit-old-input=), to be edited and sent again, which was not what the user had asked for: installing replaces that function too, as a value an earlier version set.

A withdrawn prompt, which the user means to edit and send again, still goes through =drover-opencode-edit-old-input=.  That calls =drover-prompt-edit-for=, which any front end may call: the text goes into =*drover*=, shown as =C-' '= shows it, beginning a prompt in the session's directory, or after a blank line following a draft, which stays, since the prompt never asks while it fills; and the session becomes the prompt's chosen session.

The chosen session is kept by its key and the title the header shows, which identify it whatever record its backend replaces it with as it reports, and with the record it was chosen as.  The header and the menu then show what that session runs once sent the prompt, as its entry in the picker does (=drover-prompt--entry-options=): its own model and variant as its backend tells them now (=:options=), the record found again by identifier when its backend has =:session=, the choices of the prompt applying over them; not what a new session would run, which it will not.  =drover-prompt-read-target=, which the send and scheduling ask where the prompt goes, answers with it, without the picker, while it is among the sessions the picker would offer, a live buffer taking prompts; otherwise it is forgotten, the echo area says so, and the picker asks.  It goes with the text it was chosen for: once that is sent (=drover-prompt-consume=, a region included), the prompt cleared, a prompt begun anew, or a click on its name in the header or =drover-prompt-forget-target=.  The menu's Send names it too, the prompt answering =drover-dispatch-send-target-functions= with its title.  The options chosen in the prompt apply to it as to any session the picker returns.  Attachments of the prompt used to stay as the text of their labels, the prompt being Org text, sent as text; they now go along.  A label carries its attachment as a text property, =drover-prompt-attachment=, whose value is =(BACKEND . DATA)=, the front end's own attachment (=drover-prompt-attachment-label=): text properties travel with the label through editing, killing and yanking, which an overlay would not, and Org's fontification leaves them, the face going through =font-lock-face=.  =drover-prompt-content= gathers the attachments of the text it sends, one per label, by identity, in order, and =drover-prompt--deliver= gives those of the session's backend to its =:send= as a fourth argument, only then, so that backends without attachments keep their three; the others' labels went as text, which one warning tells.  The OpenCode backend turns opencode.el's labels (=opencode-sent-attachment=) into these, and gives them back to =opencode-session-send= (=:attachments=).  Scheduling refuses a prompt with attachments, its queue keeping text, as opencode.el refuses to schedule input attaching files.

Withdrawing a pending prompt goes that way.  The service delivers a prompt sent while a turn runs at the next step or the turn's end; until then opencode.el's session buffer lists it as pending, and can withdraw it.  The menu's Edit pending prompt (=E=, =drover-edit-pending-prompt=) acts on the session at point, its buffer, a row of a list or of the sidebar, through the backend's =:edit-pending=, and shows how many prompts are pending beside its key, through =:pending-prompts=, greyed out without any.  opencode.el keeps a session's inbox in its buffer, not in the registry, which would have to list every session's inbox to know them: a session without a buffer has none to withdraw from Emacs, and every prompt Emacs sends goes through a buffer, drover's included.  Withdrawing needs no buffer shown, and its text could have gone to the session's input, unseen from a list; it goes to =*drover*= instead, with the session chosen and its attachments, wherever it was withdrawn from: the OpenCode backend sets =opencode-withdrawn-prompt-function= to =drover-opencode-edit-withdrawn= unless the user set it, which runs from the service's answer and so reports rather than signals.  opencode.el tells the withdrawal before calling it, so that the prompt's echo of where it goes is the last word.

* View settings

Grouping (=drover-group-by=), sorting (=drover-sort-by=, =drover-sort-descending=), filtering (=drover-filter=), by project, branch, agent, model or provider among others, the provider by its name (=provider-name=), its compact display serving a group's heading as an icon,, which subagents show (=drover-show-subagents=) and whether older sessions do (=drover-show-history=) are global: every view lists the same sessions the same way, and changing a setting redraws them all at once through =drover-changed-hook=.  Views draw =drover-view-groups=: the trees of =drover-view-trees=, grouped, then sorted within each group, so that groups keep their own order (statuses by urgency, last activity newest first, other values as their most urgent tree) whatever the sort.

Sorting never parts a subagent from its parent: the trees are sorted, then the subagents of each session among themselves.  Sessions without a value for the field come last either way, and ties keep the order of urgency, as =sort= is stable.

A filter keeps a tree when a session in it matches, with the sessions above each match, so a matching subagent shows under its parent.  Hidden subagents stay hidden unless they explain why their tree is listed: a matching subagent shows when no session above it matches, whatever the mode, =none= included, since its parent would otherwise be listed for no visible reason.  Filtering a project thus lists its sessions without every one of their subagents, while filtering on a status or a text shows the subagent that has it.  A subagent at the top of a tree of its own, its parent not listed, explains no parent: it shows as the mode says, matching or not (=drover--filter-trees= never counts a root among the sessions to show).  It used to show whenever it matched, as every root the filter kept was counted: a filter left on, such as one leaving out a host, matched every subagent of an archived session, so the idle ones showed whatever the mode said.  The search still finds such a subagent by its words.

By default, views are not grouped and sort by last activity, newest first: the user reads the list for what moved last, running sessions on top, and the order of urgency stays the mode line count's face and =drover-select='s for the sessions not needing the user; =drover-next= follows the view (see [[*Outside the list][Outside the list]]).  Grouping by status and sorting by urgency was the default before; the tests set it themselves (=drover-test-with-backend=), as most read groups of statuses.

** Last activity, and sessions running together

Sorted by last activity, sessions running turns together took the first place in turn, many times a second: every event of a turn makes its session's last activity now (OpenCode's =updated= changes at every step of a turn, agent-shell's last activity at every event of its turn, claude-code-ide's at every change of the terminal's status in a turn).  So the order is not by that time alone, but by =drover-session-activity=, (RUNNING . TIME): a running session, working or retrying (=drover-session-running-p=), is active now, newer than any other, and placed among the running by when its turn started, the record's =since=, which the events of its turn do not change; another is placed at its last activity, the time its age counts from (=drover-session-last-activity=): since its status began for one needing the user, as it has done nothing since, its last activity otherwise.  A session thus moves when its status does: a turn starting puts it first, a turn ending or a question first among those not running; nothing moves while turns stream.  The age of a running session is that of its last event, a few seconds, as it is active now; the order among running sessions, by their turns, is the one place where the order and the ages differ.

Placing a running session at the start of its turn among all the others, without putting it first, was the other way to keep it still: it would sink below the sessions ending turns meanwhile, while what runs is what the user watches, and the ages would have to tell how long each turn ran to agree with the order.

A tree is running when one of its sessions runs, placed at the earliest turn of its running sessions, so that a subagent starting under a running parent moves neither the parent nor the tree; otherwise at the latest time of its sessions (=drover-node-activity=, =drover--activity-join=).  The order of urgency within a status compares the same times, so working sessions keep their places there too, and so do groups placed by their most urgent tree; groups of last activity bucket that time, a running tree today (=drover-tree-activity-bucket=), so that their order follows the sort's.  Ascending, oldest first, the running sessions come last.

Times also move a little while the status does not, or does without the user's noticing: a finished turn read takes a session from done to idle, its time from the turn's end to its last step, a moment before; a rename moves an idle session's last activity; a front end not telling when a turn started has its running session placed at its last event.  A tolerance, =drover-sort-activity-tolerance=, 60 seconds by default, holds such moves: the time a session sorts by is the time kept for it while its activity stays within the tolerance of that, and the activity's otherwise, which is then kept (=drover--sort-time=).  Comparing times within a minute as equal would not be an order: a within a minute of b, b of c, a not of c, and a session's place would depend on the neighbours a sort compared it with, one drawn in place differing from one drawn whole.  The time kept is one number per session, compared exactly with the others', so the order stays total, ties going to the order of urgency, then to the order sessions were listed in, as for any field; the tolerance decides when a session's number moves, not how numbers compare.  Two sessions within a minute keep their order unless one of them moves by more than a minute, and a session never moves for less.

The time kept is the index's (=drover--activity-times=, by key), not a list's: the index notes it as it takes a record in (=drover--note-activity=), the only moment it can change, when the index also tells views that session changed, so that both lists, drawn whole or in place, read the same time; the index made anew keeps the times of the sessions it lists again, and forgets those gone.  A record not from the index, such as an older session's, is placed by the same rule against the time kept for its key, if any.  Changing the tolerance draws the lists whole (=drover-list--settings=).  The tests stream events of several running sessions, with and without the start of their turns, and check that none moves, both lists alike, that one moving past the tolerance moves in place, and the random changes of the tests drawing in place include such streams, ascending, ungrouped and grouped by activity, with and without a tolerance.

* Lists laid out by width

Drover has one view of sessions, the list of =drover-list.el=, in two buffers: the list of =drover-list=, in an ordinary window, and the sidebar of =drover-list-side=, in a side window, which may show at once, each drawn for its own width (see [[*Two lists, the sidebar and the other][Two lists]]).  From the sidebar, sessions open in the main window: the most recently used window outside side windows showing neither list, which the list's =drover-main-window-function= returns only while the list is in a side window; =o= opens them in another window than that one (see [[*Actions go through the backend][Actions go through the backend]]).

What a line shows is one function of the width and of the fields that have something to show (=drover-list--choose=), what a turn changes aside (see [[*Fields a turn does not change][Fields a turn does not change]]).  =drover-list-fields= is data: each field has a rank, the room it needs and the room it may take, and its place in the narrow layout.  Fields are taken by rank while their minimum widths fit, those of =drover-list-hidden-fields= never; columns are used when they include every field the narrow layout places, else the narrow layout, two lines per session, which places them without needing room of its own: the title and age on the first line, the background of that line for the prompt cache, what the session waits for on the second.  Because fields of lower rank show only after those of higher rank, a wider window never shows less.  Column widths then follow the content, and each column's name, up to each field's maximum.  On a line too narrow for that, room is given up in turn, each column down to the fewest pixels it needs (=drover-list--narrowest=): the fields without a maximum but of a long text, the summary; the names of the columns of short texts; the title; the other fields, in proportion to what they would lose.  The fields of a short text (=drover-list--whole-p=: the ages, the context and cache, a bar and a number, the changes, counts, the cost, an amount, and the provider, an icon) are never cut and need at least the room of what they show: an age cut reads as another age, a number cut misleads.  The harness is cut to its icon or not at all (=drover-list--compact-p=): its text marks its icon to keep (=drover-list-keep= at its start, =drover-list--kept-head=), its narrowest is the icon, it gives up its name in a pass of its own, after the names of short columns and before the title, and its column, once cut, is as wide as the icon, the rest of the line moving left rather than keep a blank where the name was; on the title's line of two, it shows its icon alone (=drover-list--compact=).  The model's column keeps the effort whole, its text marked to keep (=drover-list-keep=), and cuts the model's name; it needs at least an ellipsis and the effort.  Choosing the fields counts these same needs, so the columns chosen always fit.

Each pass shares the room missing in proportion to what each column may give, the pixels rounding leaves going to the largest remainders, so that no more is taken than is missing (=drover-list--give=).  The ages were once cut on wide lines that had room: every field without a maximum, the summary and the ages alike, gave up room in proportion, each at least a pixel, as each share was rounded up, and down to its =:min= of three characters, narrower than "11m" in a proportional font; a long summary of one session, which wanted more than the line, cut the ages of every row, while the rows without a summary showed blank space where its column was.

The priorities keep the summary, the last field the narrow layout places, before what a session runs: a field ranked before it would push the list into two lines while columns without that field would fit.  So the width at which columns begin does not move, and a window of about 75 columns shows the model and effort, context and provider beside the title, age, cache and summary.  The narrow layout places none of them as text: its line holds the title and age, and the cache already colours its background, so a second bar would read as one bar of two colours; the details and the tooltip tell them.  The context shows there as a pie alone (=:narrow icon=, =drover-list--context-pie=), filling by eighths as opencode.el's mode line does, which needs no room of a column's: a field placed so does not keep the list in two lines when columns leave it out (=drover-list--choose=), so the width at which columns begin stays where it was.

Without a right fringe, Emacs keeps the room of the glyph telling that a line is cut at the right edge of every line of a window truncating lines (=it->truncation_pixel_width=, =init_iterator=): the glyph of the display table's =truncation= slot, else =$=, in the default face as the buffer remaps it, the face =drover-list= there, whose =$= is a pixel wider than its average character in the user's variable-pitch font.  Lines reserved the room of =window-font-width=, the average character, as =window-max-chars-per-line= does: a line reaching the last pixel of the width drover gave it ended under the glyph, and Emacs drew =$= over its last icon.  Lines now leave the glyph's own width (=drover-list--truncation-width=), measured as text is; nothing on a frame without special glyphs.

In columns, the header line names each column, from the =:label= of its field: each name begins with a space aligned to its column, as cells do, so the names are aligned to the pixel whatever the header line's font; the names of columns aligned right are aligned right, measured over the face =header-line=.  Positions aligned to in the text count from past the line numbers, those of the header line from the text area's edge, so the header line is shifted by the line numbers' width.  It is computed with the layout, so it follows every redraw and width change, and is nil in two lines.

** Fields a turn does not change

Sending a prompt showed the model's column in the sidebar for a moment, between the prompt sent and the session's first answer.  The sidebar, of about 34 columns, was in two lines because a field the narrow layout places, the summary, did not fit in columns beside the title, the age and the cache.  The choice counted only the fields some row had something for, and the room before titles from the furthest title of the rows.  A send changed all of them at once: the question the prompt answered left with its summary, the cache had expired while the session waited, the subagents shown under a session at work, which push its titles further in, were not started yet.  With nothing for the summary and the cache, the title, the harness and the age fit in columns, and the model after them; the first answer brought a cache back, the subagents their room, and two lines again.  The full list changed too: its summary's column came and went as sessions needed the user, the room going to the model, the context or the project.

Whether a field shows is now decided by what does not change within a turn (=drover-list--has-p=): the summary counts for every row, since any session may come to need the user; the prompt cache for the rows that may show one, the top sessions of backends reporting caches (the backend's =:caches=, a function for OpenCode, whose service lists them only from the fork, =drover-list--caching-p=, the backends of the metrics' =:caching=, part of their stamp and of the settings, so that a change of it draws anew); and the title's room counts from the icon of a session alone (=drover-list--least-prefix=), not from the subagents at work nor their glyphs, so that the titles of subagents, further in, are cut more where room is short.  The fields shown then change with the width, the settings and the sessions listed, not with a turn.  A column kept for what comes and goes lends its room while no row has anything for it, its floor nought (=drover-list--column-widths=): the summary's, empty, gives the title back its room in a window of 80 columns.  Its width, and the widths of the others, still follow what they show, as the model's name changes; the fields and the layout do not.  Fields no session listed has anything for take no room, as before.  The host names this host too, in =drover-host-local=, so its column shows even when only local sessions are listed.

The host's icon marks another host only.  A local session keeps its host's name in the ordinary list, in the theme's success colour (=drover-host-local=), and shows no host in the sidebar.  Fields rendered as icons alone count their icon measures when choosing the layout (=drover-list--has-p=), so a sidebar of local sessions alone reserves no host column; its rows and measures still share with the ordinary list.

* Harnesses

What runs a session for the user, its harness, is drover's notion: the backend, which is the front end showing a session (opencode.el, claude-code-ide, agent-shell), or the CLI whose records a backend lists (=claude-code=, =codex=), and for a session of another host, its owner's backend, the record's =origin=, the proxy of the host telling nothing (=drover-session-harness=).  It is not the engine: agent-shell runs any engine, and the tooltip names the engine of a harness whose description does not (=drover-session-harness-description=).  =drover-harnesses= names and draws each, a drover option rather than opencode.el's look, since only drover knows harnesses: a name, short, an icon, Nerd Font glyphs, and a description; one not there is named by its backend's label, after =drover-harness-default-icon=.  A vendor's CLI shows its vendor's logo, Claude's for claude-code-ide and Claude Code's transcripts, OpenAI's for Codex: an entry may give a provider's identifier (=:provider=) rather than an icon, whose icon is the one =opencode-provider-icons= gives that provider when drawn, so that the harness's column and the provider's draw one logo alike, customized or not; each column says what the logo stands for.  Glyphs of the vendors' own, rather than terminals and scrolls, were first kept off the harnesses, lest a logo read as the provider; the columns tell them apart.  The look's other icons are opencode.el's, and the configuration checking that its font draws them reads opencode.el's options: it must read =drover-harnesses= and =drover-harness-default-icon= too, the provider icons it reads already.  The standard value of =drover-harnesses= before the logos, as loading over an older drover leaves it, takes the new one (=drover--former-harnesses=).

The list's column shows the icon alone, in a cell measured for its ink, as every icon (=drover-list--icon=), unnamed in the header line, the name in the icon's tooltip and the session's details (=drover-list--icon-alone-p=): it once showed the name after the icon, giving it up where room was short, and took the room of the longest name, Claude Code's, on lines that had little to spare; in two lines, the icon ends the title's line, after the age and the host of a session of another host, in a cell as wide as the widest icon of the rows (the layout's =:edges=, =drover-list--edges=, part of its key), a line without one keeping it empty.  Before it, each in a cell of its own, the host's icon, for a session of another host (=drover-host-icon=, =drover-list--host-icon=, after the host's name, which the line keeps but in the sidebar), and before that the context's pie: =drover-list--field-icon= tells what a field shows there, and a row's measures the width of each icon, so that a cell is as wide as the widest icon the rows show and kept while a row shows one.  The host's cell comes with the first session of another host listed, as its column does: a host's records stay listed, stale, while it is not connected, so it does not come and go with connections; the pie's with the first context size known.  Neither icon is in the rows' texts: a row's text of the host with an icon before its name, printed whole in every row and heading, took a list of 400 sessions past its printing bound (see [[*Structures print in proportion to what they hold][Structures print in proportion]]); the host's icons and the pies are made once for each host, and each eighth and face, as widths are measured, their tooltips functions reading the session at point.  It once stood flush right before the age, as the order of =drover-list-fields= places a =:narrow line= field: the ages, of two or three characters, moved it from line to line.  The sidebar's columns place it likewise, after the columns of short texts, the age and the cache, before the summary, whose texts of every width would move it (=drover-list--compact-after-whole=), the host's column before it; the list in an ordinary window keeps the order of =drover-list-fields=, the harness beside the title.  Its rank, after the summary's, keeps the width at which columns begin where it was but the icon's room: it is a field the narrow layout places, so columns hold it whenever they are used.  Views group, sort and filter by it as by a provider (=drover-groupings=, =drover-sort-fields=, the filter's =:harness=): a group is named after it, behind its icon, its sessions not repeating it, sorting reads its name, and the filter keeps a harness, chosen by name among those of the sessions known.  Its keys are =-H= and ~=H~, beside the host's =-h= and ~=h~.

The sidebar keeps its lines compact: it shows the host by its icon alone, in two lines and in columns (=drover-list--icon-alone-p=, the list folding nothing), without the host's name, nor since when it is not connected, which the list in an ordinary window keeps, in its column and in two lines beside the icon.  Rows are the same for both lists (see [[*Two lists, the sidebar and the other][Two lists]]): the host's text stays in them, and only what the sidebar draws of them, and measures for its layout, differs, the column of the host measured from the icon in the row's measures, not the text, with no name in the header line, which, cut to the icon, would draw an ellipsis.  So that the state is still in sight, the icon's tooltip names the host and tells how it stands (=drover-list--host-icon-help-echo=, =core — disconnected for 5m=, then the state line of the remote layer), and a host not connected draws its icon in =drover-host-disconnected=, which inherits =warning= but its weight: of the weight of the dimmed icon of a host connected, the icon keeps its width, and its column and cell theirs, as hosts come and go.  The icon of each host is made once for each of the two states as widths are measured, whether a session is stale being in its record, and so in the row's inputs, as its age is: a connection lost or regained draws the rows of its sessions anew, in place, and no field, cell nor column moves.

Rows hold the text of each field, and measures of each, by position (=drover-list--text-fields=): a list drawn by a drover with other fields, loaded over, has its summary of another length, which =drover-list--drop-stale= tells, and is drawn whole; the rows' stamp holds the fields and a digest of the harnesses, so that rows of other fields or icons are never reused.  A digest, as every row prints its stamp: the harnesses whole made a list's model print past its bound.  =drover-list-fields= of a former standard value, before the harness or before the context's pie, as loading over an older drover leaves it, takes the new one (=drover-list--former-fields=).  =drover-core-generation= is 11 since, the times of real activity having taken 10.

* Where sessions are

The colour of a title tells where its session is in Emacs (=drover-list--title-state=): no buffer, a buffer no window of a visible frame shows (=opencode-session-open=), a window of a visible frame (=opencode-session-shown=), the window the user works in (=opencode-session-active=): the selected window, or, while the list or the minibuffer is selected, the window selected before, the most recently used window of the frame showing no list.  It replaced a highlight of the whole heading of the session shown in the main window, an overlay in =highlight=, which in many themes underlines and recolours a whole line, and which assumed one window beside the list.  The faces inherit =font-lock-keyword-face=, =font-lock-type-face= and =font-lock-function-name-face=: themes make these siblings distinct from one another and from the default foreground, and no status takes them but Working's glyph, so that a title never reads as a status, as one in =success=, =warning= or =error= would.

Windows and the selection change far more often than sessions: each window change (=window-buffer-change-functions=, =window-selection-change-functions=) computes where the sessions drawn are (=drover-list--places=, one pass over the windows of visible frames) and gives a new face, in place, to the titles whose place changed (=drover-list--restyle-titles=), found by their property =drover-list-title=, the session's key, ellipsis included.  The list is drawn anew only when a face would change the width of a title, as a bold one would, since its line was laid out in the other face.  A buffer opening or closing is a change its backend reports, which redraws the list; killing a session buffer no window shows changes no window, so a =kill-buffer-hook= gives titles their faces once it is gone, after a lookup in a weak table of the buffers of sessions drawn, so that the temporary buffers Emacs kills all the time cost nothing.

* Selecting sessions

An active region selects the rows of sessions it touches, those shown, and nothing else: =drover-list--selected-sections= walks the region from its beginning to its end, both included, taking each session whose row it meets, skipping a group's heading, blank lines and the body of a collapsed group.  A group's heading selected the sessions of its group once, collapsed ones included, as a collapsed group's heading stands for them when moving: one =z= on the heading of Idle archived 2,202 sessions the user never saw.  To act on a whole group takes a command of its own.  So setting the mark on a session's line and moving a line down selects two sessions, wherever the region begins and ends on their lines, which quoting the region's text did not: it quoted the first line only; and a region from one group into another selects the rows of both it touches, not the headings between.  A region of some text within the lines of one session selects nothing, as Magit's within one section, so that its text can be copied; an empty one selects the session it is on, but as a click leaves it.  A region selecting nothing shows as a region does elsewhere, and the commands act on the session at point.

What is selected is what Magit highlights: Magit reads its selection from =magit-region-sections=, sections from the heading of one to the heading of a sibling, as it highlights them and decides to show the region as a region; around it, =drover-list--region-advice= returns drover's selection in its lists, and calls Magit's elsewhere.  It is added as a list is made, with the hooks the lists need (=drover-list--watch=), and removed with them once the last list goes, and by =drover-list-unload-function=.

The list tells its selection through =drover-selected-sessions-function=, as it tells the session at point; =drover-selected-sessions= falls back on the session at point.  Commands acting on several sessions read it: marking seen, interrupting, archiving, unarchiving and deleting, interrupting and deleting after one confirmation naming them, each acting on each session whatever happens to the others, in slices from a timer when they are many (see [[*Acting on thousands at once][Acting on thousands at once]]), and telling the outcome once, with what it noted, such as a buffer left open until its turn ends (=drover--act=), then ending the selection, which would otherwise select other sessions once these went.  Of several sessions, those the action does not apply to are left out (=drover--selected-for=): a region sweeping over sessions means those that run, for an interrupt.  A session alone is acted on as before, its backend telling what it cannot do.  Answering, renaming, opening and peeking keep to one session.  The menu, opened in the list, records the selection in its scope, greys out an action applying to none of it, and names how many sessions its List group acts on.

Copying, =kill-ring-save= remapped, copies the sessions' Org links (=drover-session-link=).  The link is that of the first link type whose store function knows the session at point, the session given as at point, which is how =org-store-link= stores it, drover's =agent-session= (see [[*Org links][Org links]]) or one of the user's; without one, the title.  The prompt's =drover-prompt-dwim= in drover's own lists, those setting =drover-view-p=, quotes the sessions with their links, how they stand and their last replies, fetched with =drover-recap= all at once, the quote going into the prompt once every reply arrived or =drover-prompt-quote-timeout= passed, so that a backend not answering cannot hang it.  Elsewhere it quotes the line at point or the region, in a session's buffer, which tells a session at point, and in the lists of other front ends, which bind the session keys (=drover-session-keys-mode=), alike: the user quotes there what is written, and selecting sessions to quote belongs to drover's lists.

The list redraws many times a second while a session works.  A redraw used to deactivate the mark, and a timer's change of the buffer ended the region at the user's next command, through =deactivate-mark=; redraws now bind it, and put the mark back on its session, as point is (=drover-list--anchor=).

* Prompt caches

A record may tell when the provider's prompt cache of the session expires and how long such a cache lasts (=cache-expires=, =cache-ttl=); =drover-session-cache-fraction= is what is left of its lifetime.  The list draws it without taking room in two lines: a line under the session's first line, from the left over that fraction.

Only for a session that is no subagent: a subagent's cache shows nowhere, neither bar, time left, tooltip nor detail, in either list and layout (=drover-list--cache-fraction=).  The user sends to the parent, never to a subagent, so only the parent's cache tells what their next turn costs; a subagent's bar under it read as one more cache the next turn might use.  A subagent's row thus has no cache, and a subagent's live cache alone neither takes a column nor keeps the cache timer running.

Both bars take the foreground of =opencode-cache-bar= (=success=): the short bar of columns fills with it, in inverse video (=drover-list--cache-fill=), the line of two lines is an underline of it at the descent (=drover-list--cache-line-face=), its colour read as the list is drawn, and drawn anew when a theme is enabled or disabled.  They were backgrounds, of a dark blue close to the highlight of the current section and the region, which hid them where the user looked: a background highlight replaces a background, but leaves an underline, and inverse video turns the highlight's background into the bar's text colour.  Every space of such a line is two characters, the first a stretch of no width, so that the bar may end at any pixel of a space, or between two characters of text.  As the cache runs out, a timer changes only the display properties of those characters and the bar's overlay, so nothing is drawn anew, and only where they read otherwise: a property put with the same value, or an overlay moved where it is, changes the buffer all the same, which has Emacs lay out its windows again (see [[*In the background][In the background]]).  It runs while a list shown has a live cache, Emacs having focus or not, and stops otherwise; it changes only the caches windows show, but forgets those that ran out wherever they are.

In columns, the time left is text, so that it copies with the line: the timer replaces it in place, in the properties it had, its section's included, when it reads otherwise.  It may change length, "1m" becoming "59s", so what is found again by position after it, the start of each cache drawn and the animated glyphs, is kept by markers.  They advance as text is inserted where they stand, as the starts of sections do: in the sidebar, whose lines have no invisible character before them, a session's line begins with its cache's start, and often with its glyph, right where a line drawn in place before it is inserted (a session whose turn begins moving above it).  Markers staying there followed the line inserted, whose next drawing, many a second while its turn ran, forgot them with its own marks: the session's cache line went, an hour before its cache expired, and its glyph stood still, until its own line was drawn again.  Its cache shows most while it is idle, when the user decides whether to send before the cache goes cold, and an idle line is seldom drawn again.  The overlay of a cache line is excluded likewise from text inserted at its start.  A list whose mode changes, as applying it again does, deletes those overlays (=drover-list--drop-caches=): the mode forgets the caches drawn, and the buffer kept their overlays, one per cache and application, empty at its start once erased.  Tooltips are functions (=drover-list--cache-help-echo=), which tell how the cache stands when they show rather than when the line was drawn; in two lines, the line's tooltip adds the cache to the session's.

* Animated glyphs

The glyph of a working or retrying session is animated: an animated glyph is two characters, the first displaying the current frame of =opencode-session-status-animations=, the second a stretch filling the rest of the status cell, as wide as the widest glyph or frame draws, so the proportional font never shifts what follows.  Each frame of a glyph differs little from the one before, so that they read as motion, as the phases of the moon do: a full hourglass between two outlined ones, or a robot alternating with its outline, read as a blink.  The frames are measured once per drawing (=drover-list--frames=); the frame shown at a time is the same for every glyph, from the clock (=opencode-session-status-frame-index=), so a redraw keeps the pace, and opencode.el's mode lines show the same frame at the same time.  A timer, =drover-list--frame-tick=, changes only the display of those two characters, where the frame changed, the glyph is not out of sight in a collapsed group, and a window shows it, every =opencode-session-status-animation-interval= seconds; it ticks in the middle of each frame (=opencode-session-status-frame-delay=), so a late or early tick neither repeats nor skips one.  It runs only while a list shown in a visible frame has an animated glyph, as the cache timer does, through the same =drover-list--keep-timer=, at the pace of =drover-list--frame-pace=: slower while Emacs has no focus (see [[*Pausing, and slowing without focus][Pausing, and slowing without focus]]).  A cache bar measures the text as shown at its tick, an animated glyph's frame included.

0.15 seconds by default: the eight phases of the moon turn in 1.2 seconds, which reads as busy, where half a second made a slow blink.  Each tick costs Emacs a layout of every line of the windows showing a glyph that changed, not of the changed lines alone (see [[*In the background][In the background]]), and only while one shows; a slower pace costs fewer, and =nil= keeps glyphs still.

* In the background

The list costs nothing while nothing changes but the clock, but for its animated glyphs, its prompt caches and its ages, which timers draw.  Profiled in the user's Emacs, 2519 sessions, the list and the sidebar shown, those timers and the redisplays they caused were the most of Emacs's processor time while the user did nothing.

** Finding the lists

The ticks found the lists with =match-buffers=, over every buffer, twice a tick, six or seven ticks a second, and so did the hooks running on every change of the selected window.  The lists are noted as they are made, killed or change mode (=drover-list--live=, =drover-list--forget=), and the windows showing them as windows change, lists draw and timers start or stop (=drover-list--find-windows=, from =window-buffer-change-functions= and =window-selection-change-functions=); a tick looks at no other buffer nor window, checking only that each window found still shows its list in a visible frame (=drover-list--showing=).  Loaded over a drover that kept none, the lists of that drover are found once.

** Pausing, and slowing without focus

Every timer of the lists pauses once no visible frame shows a list, and runs again as windows change: the glyphs then show the frame of the time, the ages are drawn when their tick was due, a second later when that passed.  A frame iconified stops the timers at their next tick, Emacs having focus or not; shown again, it runs them as windows change or the focus does.

The focus is Emacs's, not the list's frame's (=after-focus-change-function=, =frame-focus-state=: Emacs has it while any frame but the initial one of a daemon or batch Emacs has it, or may have it): a list in a frame of another screen keeps the full pace while the user works in another frame.  It is looked at once its events settled (=drover-list--focus-changed=, =drover-list--refocus=): moving between frames, Emacs may tell one lost focus before telling the other has it.

Once Emacs lost focus, a list may still show, on another screen or beside the application the user works in, and a working session is still worth seeing move.  The animated glyphs then move at the pace of =opencode-session-status-animation-unfocused-interval=, 1.35 s by default, opencode.el's option since its mode lines move at it too (drover's =drover-list-animation-unfocused-interval= is an obsolete alias), rounded up to a whole number of frames of =opencode-session-status-animation-interval= and never quicker (=drover-list--frame-pace=), so that each tick still falls in the middle of a frame, where a late or early tick shows the same one.  The frame shown is still the clock's, so every list and opencode.el's mode lines show the same frame at a time, and nothing jumps once focus is back: the frame of the time shows at once (=drover-list--refocus=), and the timer starts again at the full pace.  Sampled every seventh frame, as a second rounded to the nearest frame first did, the eight phases of the moon stepped back one phase a tick, and the clock's hand, of four frames, a quarter: the moon turned backwards.  A tick spanning one more than a multiple of an animation's frames shows its next frame, one less its frame before: the number of frames is the least, from the seconds asked up, that is one more than a multiple of the frames of every animation of =opencode-session-status-animations= (=opencode-session-status-forward-frames=, which =drover-list--frame-pace= and opencode.el's mode lines share through =opencode-session-status-frame-pace=), nine for the moon's eight and the clock's four, 1.35 s, the default, which a second rounds up to as well.  All the animations configured count, not those shown, so that the pace does not change as sessions change status.  When frame counts of no common multiple near, such as five, seven and nine, every 315 frames, put that number past three times the seconds asked, the tick spans the least number of frames up to there showing their next frame to the animations of the most frames together, the more frames an animation has the more it reads as turning one way; a two-frame animation reads the same either way.  Slow motion, which tells a session works without drawing the eye away from the application in front.  =nil= keeps the glyphs still, as they were before; a tick already due as the timer stops draws nothing.  A change of the pace, of focus or of =opencode-session-status-animation-interval=, starts the timer anew (=drover-list--frame-timer-pace=).

The cache timer keeps its pace, 5 s, and the age timer its minute.  A cache tick changes the buffer only where a bar or a time left reads otherwise, and costs a tenth of a millisecond when nothing does; when one does, the layout of the windows showing it, about 6 ms (see below), at most once in 5 s, about a tenth of a percent of a core, where the glyphs at a second cost two percent.  Slowing it to 15 s would save that tenth of a percent at most, and leave the time left of a cache, which the user reads to decide whether to send now, up to 15 s late; under an hour's cache, the short bar of five characters, about 40 pixels, moves a pixel every 90 s, so most ticks change nothing.  The minute's refresh costs a few milliseconds a minute, and keeps ages and branches right for a list read from another application.

** Redrawing as little as possible

Changing a buffer that the selected window does not show has Emacs redisplay every window showing it thoroughly: =bset_redisplay= sets =windows_or_buffers_changed=, after which =redisplay_window= takes the window's end as unknown and lays out every line of it again (=try_window=), not the changed ones alone (=try_window_id= gives up); with scroll bars, it lays them out once more to place the thumb.  A display property put on text and one on an overlay cost the same, and so does a property put with the value it had, or an overlay moved where it is.  So a tick changes only the glyphs and caches windows show (=drover-list--draw-frames= and =drover-list--draw-caches= with the ranges they show), and nothing that reads the same; a list scrolled away from its working sessions costs a tick a tenth of a millisecond, its redisplay changing nothing.  Reordering bidirectional text took a quarter of that layout, and does nothing to a list without right-to-left text, as most are: before its windows are redisplayed (=pre-redisplay-functions=), a list whose text changed is looked at, and its lines reordered for display only while it holds a strong right-to-left character or an RLE, RLO or RLI (=drover-list--reorder=); the display of characters changing, as frames do, it is not looked at again.  Without scroll bars, as the user has them, a frame of the animation with the sidebar beside the list, 42 lines of 204 columns and 57 of 34, costs 5.6 ms of redisplay, 7.7 ms when reordered; the window system then draws and composites the frame, which the processor time of a tick, about 13 ms, includes.

What such a layout costs is mostly the runs of text properties of the lines laid out, each a stop where redisplay looks at faces, display and invisibility, not their spaces displayed as stretches.  Measured on a copy of a user's sidebar, 64 lines of 35 columns holding about eleven display properties a line, a layout took 2.1 to 2.3 ms with them, 1.5 to 1.6 ms with none at all, and 1.8 ms with each pad of a glyph's cell drawn as part of the aligned space beside it (characters of a display property =eq= to one another are laid out as one stretch): the pads beside aligned spaces bear the tooltip of their glyph, which a stretch shows over all of its characters, so that sharing them moves tooltips, and a line whose text reaches past an alignment, as a font's metrics may make one, then draws the next glyph a pixel or two to the left.  So the cells keep their pads, and the frames keep their cost, one tick in nine of it while Emacs has no focus (=opencode-session-status-animation-unfocused-interval=).  Animations do not stop while Emacs has focus and no input came for minutes: Emacs cannot tell a user away from one watching a turn, and a screen locked or another application in front takes the focus.

With the glyphs still, the cache timer's six ticks in 30 s and the minute's refresh, which lists the sessions anew, add a few tenths of a percent and the allocation.  Focused, nothing changed but the pace's computation as timers are looked at: the difference is the noise of the machine.

At nine frames, 1.35 s, the default once the glyphs step forward (see [[*Pausing, and slowing without focus][Pausing, and slowing without focus]]), one run on a quieter machine, its focused phases at 6.2 to 7.3%: 0.89% of a core, 0.127 MB/s, 22 frame ticks in 30 s and 59 redisplays, against 0.19% with the glyphs still in the same run.

* Older and archived sessions

A backend follows some sessions live, its newest and unarchived; older ones it may fetch on demand (=:history=), and archived ones (=:archived=).  =drover-set-show-history= and =drover-set-show-archived= fetch them from every backend that can, and forget them when hidden; =g= in the list fetches them again, and a backend may fetch its own again, as the OpenCode backend does, once a burst of archiving, restoring or deleting events ended, or once its event stream reconnected.  Each fetch has a generation per kind and backend: an answer arriving after a later fetch of that kind from that backend started, or after its kind was hidden, is dropped.  =drover-known-sessions= merges them with the live sessions, a live record winning over an archived one, and an archived one over an older one; lists, =drover-find= and the subagents of a session see them, while the attention count, =drover-next= and =drover-select= keep to the live sessions, archived ones never among them.  A deleted session leaves the records fetched at once.

OpenCode's service archives a session alone: its subagents stay unarchived, listed with the sessions in use while their parent is not, which left them at the top of trees of their own, idle subagents shown whatever =drover-show-subagents= said.  They go with the archived session above them, at any depth (=drover-opencode--archived-above=): the backend's =:sessions= and =:session= leave them out, its =:history= too, and its =:archived= adds them, from the registry, so that the archived view shows them under it.  A session the registry tells archived or restored, or deleted, has the subagents below it told changed too (=drover-opencode--updated=, through =drover-opencode--hiding=, the sessions on their way up to it).  A parent the registry does not hold archives nothing: the subagent, at the top of its tree, shows as any subagent does.

Archived sessions show dimmed, after =opencode-archived-icon=, and grouped by status in a group of their own, last: their status is still the one their backend reports, but none of them needs the user.  They are fetched only when shown, as OpenCode lists them a page of a hundred at a time, every page asked for once the last arrived.

** Drover's own archive

Front ends without an archive, agent-shell and claude-code-ide, have their sessions archived by drover, the same way for every such backend (=drover-archive-session=): by conversation, (ENGINE . ENGINE-ID), so that it is kept whichever front end shows it and across Emacs sessions, where a terminal's token would not be.  A session whose conversation is not known yet cannot be archived.  Archived, the conversation leaves =drover-sessions=, whichever backend follows it; its backend's own record, from =drover-find=, tells it is archived, so that =z= restores it from its buffer too.  Drover keeps, besides when, what the list shows of it (=drover--archive-fields=): an archived terminal whose buffer is gone stays visible among the archived sessions, as the record of the backend listing what Claude Code recorded of it (see [[*Closed conversations][Closed conversations]]), else as a record of its own backend identified by the conversation, which needs no buffer to be deleted, forked or recapped.  Restored, a conversation must be listed again: by a front end following it, or by a backend listing it as its engine recorded it, live or among its older sessions (=drover--followed-p=, =drover--recorded-history=).  One that none lists, as the conversation of a shell gone whose engine records nothing drover reads, =drover-unarchive-session= refuses, a =user-error= saying why, and it stays archived and listed.

A backend whose archive does not take a session, as Codex's when its CLI is not found (=:supports=), has it archived by drover, as a backend without an archive (=drover-archivable-p=, =drover-archive-session=).

A conversation drover archived takes its subagents with it, at any depth, as OpenCode's archive does above.  A subagent has no conversation of its own to archive, as a Claude Code subagent, which the backend listing transcripts lists apart from the terminal following its conversation, or names its own, as Codex's: drover archived the conversation alone, and its subagents stayed among the sessions in use, at the top of trees of their own.  A subagent now goes with the conversation drover archived above it (=drover--archived-above=): each parent is looked for in the archive first, as the conversation the subagent's engine names, since an archived parent is listed nowhere, then through its record, found among the sessions listed, in the index, or asked of its backend's =:session=, and so on up; sessions of other hosts are their host's.  =drover--unarchived= leaves them out of the sessions in use and the older ones (=drover--archived-below=, tables of the sessions by key and by engine, a walk up from each subagent), and =drover-archived-sessions= lists them, archived when their conversation was, so that the archived view shows them under it, those its recording backends list among the older sessions too.  The index follows them without listing a backend anew: archiving reports the subagents below the conversation, found by their claims on their parents (=drover--index-going=), each looked at alone, which =drover--index-listed= then leaves out; it notes those it leaves out (=withheld=), which restoring or deleting the conversation reports, as they are listed nowhere else.  A subagent is restored with its conversation, not alone: =drover-unarchive-session= refuses it, naming the conversation, and =drover-unarchivable-p= is false for it, so that a backend's own =:unarchive=, as Codex's, never restores a subagent its own archive does not hold.

The archive is =archive.eld= in =drover-state-directory=, Lisp data as =models.eld= is, written whole through a temporary file renamed over it (=drover-write-data=), and read again whenever its modification time changed, so that another Emacs's archiving is seen; a malformed file is warned of once and ignored.  Taking changes in stats it once, and sessions are looked up in a table by conversation (=drover--archive-lookup=), which keeps the cost of a session hidden by drover to a hash lookup.  Archiving a selection writes it once, at the end (see [[*Acting on thousands at once][Acting on thousands at once]]).  This, the models remembered, and nothing else, is what drover itself keeps of sessions.

** Archiving closes the buffer

Archiving asks nothing, as the user is done with the session, and closes its buffer (=drover--close-archived=), through the backend's =:close=: what the buffer holds that the agent never got goes to the kill ring first (=drover-keep-unsent=), then the buffer is killed without asking (=drover-kill-buffer=).  A backend without =:close= keeps its buffers.  When the buffer closes depends on what it is, which =:runs-in-buffer= tells:

| Backend           | The buffer                       | Closes                                                                                    | =:close= keeps                                                                                                     |
|-------------------+----------------------------------+-------------------------------------------------------------------------------------------+--------------------------------------------------------------------------------------------------------------------|
| =opencode=        | shows a session the service runs | once the service confirmed the archive (=:archive-confirms=), a turn in progress going on | the input after the process mark: opencode.el keeps no draft                                                       |
| =agent-shell=     | runs the agent, over ACP         | once no turn runs (=:runs-in-buffer=)                                                     | the input after the process mark, =:pending-prompts= (a failed or cancelled turn leaves them), the viewport's text |
| =claude-code-ide= | runs the CLI, in a terminal      | once no turn runs (=:runs-in-buffer=)                                                     | the input box around the live cursor, between its rules: its text, typed, not the dimmed placeholder               |

A buffer running its agent in the middle of a turn, as =drover-session-active-p= tells of the backend's own record at the time (=drover-find=), would end that turn: it is kept in =drover--closing=, and =drover--close-pending=, on =drover-changed-hook= while some wait, closes it once its record tells no turn runs.  The hook runs on every change backends report, so the close does not depend on a list being shown, or open.  A record no longer archived, from =drover-unarchive-session= (which forgets it at once, =drover--close-cancel=) or another Emacs editing the archive, keeps its buffer, and a buffer killed meanwhile, or now showing another session, is forgotten.  A turn waiting for the user's answer is a turn in progress too: it cannot end before the answer, and killing its buffer would lose the turn's work, so the buffer stays for the answer, the report telling the session waits (=it waits for you=).  When a buffer closes, at once, once its turn ends or once its archive is confirmed, goes unsaid: reports said =Archived TITLE; its buffer closes once its turn ends=, then =Closed TITLE, archived, now that its turn ended=, the expected outcome told twice.  A report now notes only what the user would otherwise miss or must act on (=drover--archive-note=): unsent input in the kill ring, a turn waiting for them, a buffer that could not close; a close deferred says nothing, unless it kept unsent input (=The unsent input of TITLE, archived, is in the kill ring=) or failed, as a warning.  Deleting a session forgets its pending close: its backend closes its buffer itself.

A pending close is remembered in =closing.eld= of =drover-state-directory=, as Lisp data written whole (=drover-write-data=), versioned, each entry checked as it is read (=drover--closing-entry-p=), at most =drover--closing-limit= entries, none older than =drover--closing-days= days: drover's files loaded anew, or a buffer outliving its Emacs session, as a restored desktop's does, would otherwise keep a buffer open that archiving was to close.  An entry names its session by its key, its conversation and its buffer's name.  =drover-start= reads the file once per Emacs session (=drover--closing-restore=), and each entry waits for its backend to start (=drover--closing-resume=): a buffer found with all three, its session still archived, closes then if its turn ended, else waits as above; any other is forgotten, and a buffer named alike but showing another conversation stays open.  A file that does not read is warned of and taken as empty.

claude-code-ide's terminal keeps no draft drover could read but its screen: =drover-claude-code-ide-unsent-input= reads the input box the live cursor sits in, between its two rules, without its caret, indentation and the pill of the context attached, a line of the terminal per line, bounded (=drover-claude-code-ide--draft-lines=, =drover-claude-code-ide--draft-limit=).  An empty box shows a placeholder, dimmed, the cursor on its first character: text after the cursor's character all in faces, the cursor at the box's start, is that placeholder, whereas text typed shows in the terminal's default colours, so that a draft whose cursor went back to its start is still kept.  After a turn, Claude Code shows its suggestion of a next prompt the same way.  Both read the box through =drover-claude-code-ide--input-box=, so that the backend's =:blocker= lets a prompt be pasted over the placeholder or a suggestion, which it replaces, and never over a draft: a scheduled or remote prompt took a suggestion for a draft, waited, and went in after the user, tired of waiting, had sent it by hand.  Its refusal tells what it saw, the start of the cursor's line or of the box's text and whether it was dimmed, so that one names its cause.

Ghostel draws a terminal only while a window shows it: output arriving meanwhile waits, the buffer's text unchanged.  A Claude terminal started hidden, for a task, another host, Anvil, or a prompt with =drover-prompt-display-new= nil, never showed its input caret, and its first prompt went to the kill ring after 30 seconds.  So what reads a terminal's screen, its readiness, input box, footer and preview, first draws what a hidden Ghostel terminal holds back (=drover-claude-code-ide--render=), through =ghostel--commit-frame=, which Ghostel itself calls to draw a hidden terminal before its exit hooks run.  A terminal a window shows is left to Ghostel's own redraws.

The OpenCode backend's archive is the service's, which may refuse it, and closing at once lost the buffer of a session the service kept unarchived, with whatever the user had not sent.  A backend whose archive is confirmed later says so (=:archive-confirms=): its =:archive= takes THEN and ELSE, which opencode.el's =opencode-session-archive= calls once the service answered, and =drover--archive-confirmed= closes the buffer from THEN only, as =drover--close-archived= does.  The report of the action says =Archived TITLE= and no more, closing then telling only what it kept, such as unsent input, or a turn waiting for the user's answer, and a refusal is warned of on one line, its message bounded (=drover-bound-line=), the buffer left as it was.  Of several sessions, the job awaits the answers itself (=drover--archive-step=), closes the buffers in slices once they came, and its one report tells what closing kept and which archives were refused.  The archive awaited is kept by session (=drover--confirming=) with a token of its own, so that only the answer to the latest archive closes the buffer, and none once the session was restored or deleted meanwhile (=drover--close-cancel=); a buffer killed meanwhile has nothing to close.

=drover-kill-buffer= kills without asking: =kill-buffer-query-functions= is bound to nil in the buffer itself, where front ends ask through buffer-local values, as agent-shell's prompt queue does, which a global binding would leave asking.  What the queries protect the caller kept already: input and queued prompts in the kill ring, a process the session's front end tears down as when the user kills the buffer (agent-shell shuts its client down, claude-code-ide cleans its session up), a conversation its agent recorded.  Windows showing the buffer are left to =replace-buffer-in-windows=: a dedicated window goes, a side window shows a buffer it showed before or goes, another window shows its previous buffer; but while a list shows, =switch-to-prev-buffer-skip= skips drover's views shown in another window, so that a window where the session replaced the list does not show the list a second time.  A list's window never showed the session, so it keeps its list, and stays selected if it was.

Archived this way, a shell's or terminal's session stays in drover's archive with its buffer gone, where =drover-unarchive-session= refuses it (see above) until its conversation is resumed in its front end.

** Wrapping a session up

A session the user is done with leaves things behind: worktrees it added, folders of notes, a second clone.  =drover-wrap-up= (=Z=, =drover-wrap-up.el=) tells its agent that the user closes it, so that it removes what it created that does not belong where it is, then archives it, its buffer closing as archiving closes it.  =z=, which archived, toggles the archive since (=drover-archive-toggle=): it restores an archived session, of several all of them when all are archived, else archives those that are not.

The prompt goes first, since sending to an archived session restores it (see [[*A prompt restores the session it goes to][A prompt restores the session it goes to]]), and through the queue of scheduled prompts (=drover-schedule-deliver=, =:hidden=): never over a draft, resuming a closed conversation, out of every window, and with the engine's build agent applied as =<tab>= applies it (=drover-wrap-up-agent=), a plan agent asking before it deletes anything.  A session in a turn gets it once the turn ended (state =waiting-turn=), so that the mark, the job's =:sent-at=, dates the cleanup's turn alone, and a prompt queued behind a running turn is never taken for it.  Once the job is sent, the session is archived through =drover--archive-step=, which archives without closing: a terminal's or a shell's buffer closes only once the verdict is known, since =drover--close-archived= closes a buffer whose record does not tell a turn yet, which it would not, the prompt just typed, and closing it would end the agent before it cleaned anything; an OpenCode session's closes at once (=drover--archive-finish=), its turn going on in the service.  The record followed is found again after delivery among the live sessions, by conversation, as a front end resuming a closed conversation shows it under its own backend.

OpenCode's =:session= leaves archived sessions out, yet the registry keeps one while events concern it, as those of a turn going on: =:archived-session=, a backend operation, returns it, through =drover-find-archived=.  The service tells the archive a moment after it answered the request: a record not shown archived counts as restored, the wrap-up forgotten, once it was seen archived, or =drover-wrap-up--archive-grace= seconds after.  The turn ends as a goal's does (=drover-goal--ended-p=): out of a turn after one was seen since the mark, or with its status and activity both later than it, pending prompts counting as a turn, as Anvil counts them.

The session stays open, restored by =drover-unarchive-session= with a warning saying why, when the agent needs the user: waiting for a question or a permission, at once, since an archived session leaves the attention count and would wait unseen; making =drover-wrap-up-keyword= the first line of its last message; or ending that message with a question, as a goal pauses on one.  The keyword opens the message rather than ends it: =drover-recap= keeps the head of a reply (=drover--bound-recap=), and so does a host for its peers.  A turn failed or carrying an error, or a recap that could not be read, keeps it open too, its cleanup unknown; a recap failing is asked for again first, a few seconds apart (=drover-wrap-up--recap-attempts=), as OpenCode's service refused a connection the moment a cleanup's turn ended, in the first live run.  Otherwise a terminal's or a shell's buffer closes, as an archive closes it once its turn ended.

The prompt ends with what drover attributes to the session, from what engines record, a hint: the files its edits created (=:changes= of the scope =session=, the status =added=: Claude Code's =Write= of a new file, Codex's =Add File=, OpenCode's diff of its snapshots, which cover its working tree alone, so that its sessions tell none of these), still there, outside every repository and temporary directory; the highest directories holding only those, below the home directory, never the session's directory nor above it, looked into at most 200 entries deep without following links; and the worktrees of its repository added since it started, by the first entry of their HEAD's log, neither locked nor a task's nor one where another live session runs.  Commands, a clone or a =mkdir=, are not parsed: the agent knows them from its conversation.  Drover deletes nothing itself; the rules the user's harnesses enforce on deletion stay the rules, which =drover-wrap-up-removal-advice= may tell the agent about.

Wrap-ups under way are kept in =wrap-ups.eld= of =drover-state-directory=, written whole and removed with the last, a module of =drover--kept-modules=: as drover starts, one whose prompt was not queued is given up, one whose prompt waits in the queue goes on as it goes, a terminal's or a shell's cleanup ended with Emacs, which is told, the session staying archived, and an OpenCode session's is followed to its end.  Another host's session is wrapped up by its owner, through the action =wrap-up= (capability =wrap-up=, see =doc/remote.org=), which tells the peer that asked how it ended in a message =note= (=drover-remote-tell-peer=); =drover-wrap-up-p= lives in the core, cheap, since an owner tells the actions of every record it serves.

A linked worktree's =.git= file names its Git directory as its Git wrote it, MSYS2's as =/c/...= on Windows, which =drover--git-directory= read relative to the drive of the worktree; it reads it as Emacs names it now (=drover--native-file-name=), which the worktrees' times and the markers of tasks need.  Git for Windows, which Emacs runs there, reads such a worktree's =/c/...= the same way, and so lists it =prunable=, its gitdir pointing nowhere: in the first live run on Core the worktrees Claude Code's shell added, through MSYS2's Git, were left out of the hint.  =drover-task-git-parse-worktrees= takes a worktree so spelled whose directory holds its =.git= file for live (=drover-task-git--misread-p=), which the task sweep's verdicts need too.  =git worktree prune= run with Git for Windows still forgets such worktrees: a fan-out discarding an attempt prunes its checkout's.  The cure is Git's, not drover's: with =worktree.useRelativePaths= (Git 2.48) in the configuration both Gits read, a worktree records its links relative to each other, which both read alike, and =git worktree repair --relative-paths= converts those made before.

** A prompt restores the session it goes to

Sending to an archived session means the user is not done with it: it is restored first, then the prompt goes, whichever way it goes.  An OpenCode session opencode.el restores itself (=opencode-session-send= restores before it posts, a PATCH of the session); what drover archived, drover restores, through =drover-unarchive-to-send=, which does nothing for a session it did not archive, and refuses, on one line, =Could not restore TITLE from the archive: WHY=, a conversation no backend would list restored (=drover--unarchive-refusal=, which =drover-unarchive-session= tells too).  A refusal sends nothing: the prompt stays, its text in the kill ring.

- Drover's prompt offers the sessions it archived whose buffer is still open (=drover-archived-live-sessions=, as a turn's end or an answer awaited keeps one), and restores the one chosen once its checks passed, before the options are applied.
- A scheduled prompt finds such a buffer as any other (=drover-schedule--sessions=), so that waiting for the end of a turn waits for that session's turn, which ended at once had it been left out.  Delivery restores the conversation as it begins (=drover-archived-conversation=), when a backend lists it, which keeps a buffer archiving was to close once the turn ended; one listed by nothing yet is resumed, then restored as the prompt goes, a refusal failing it before =sending=, nothing sent.  A backend's =:submit= telling nothing was sent for sure, a second argument to ELSE, fails the prompt rather than leave it interrupted: the OpenCode backend's does so for a session that did not open or a restore refused.  Its =:submit= opens a session without a buffer, unseen, as its =:send= does, since archiving closed the buffer the delivery found.
- The OpenCode backend tells a refused restore from a refused prompt by the method of the request that failed, =patch=, rather than a message saying the session did not take the prompt.

Restored, a session leaves the archived sessions fetched at once (=drover-archived-left=), before the event of the service fetches them again: a backend whose restore is confirmed (=:unarchive-confirms=) is given THEN and ELSE by =drover-unarchive-session=, THEN forgetting the record, ELSE warning on one line, as for =:archive-confirms=; and the OpenCode backend forgets a session it fetched as archived (=drover-opencode--archived-ids=) once the registry, on =opencode-state-updated-functions=, holds it unarchived, as a prompt restored it.  =drover-core-generation= is 8 since.

Past 200 characters the two spellings hash apart, so drover looks in both and makes Emacs's (=drover-claude-code-native-directories=, =drover-claude-code-buckets=); drover reads a conversation's directory from its records rather than decode its bucket.  Codex's database is the CLI's to change, has changed schema many times (version 55 here) and is not kept by every Codex: drover reads the rollouts every Codex writes.

Claude Code titles a conversation from its first prompts, recording the title as =ai-title=, which its desktop app shows; =/rename= records the user's as =custom-title=.  Version 2.1.319, as the user approves a plan (=ExitPlanMode=), also has the model name the session in two to four words of kebab case, =fix-claude-permission-rules=, and records that name as =agent-name=, just after an =ai-title= holding it too, both appended again at every turn; the terminal's title shows the name, and the ghostel configuration named claude-code-ide's terminals after it, so that drover, which titled them by their buffers, and which took a conversation's newest =ai-title=, listed the name rather than the title.  A conversation's title is, as the desktop app shows it, its =custom-title=, else its newest =ai-title= naming none of its agents, else its newest agent's name, else its summary and prompts (=drover-claude-code-transcripts--title=): read from the newest back, an agent's name comes before each =ai-title= holding it.  A long session leaves its generated title far behind its tail, 2 to 35 MB back in 6 of 30 named transcripts here, beyond the head and the megabyte looked behind the tail: such a transcript is marked (=:title-unread=) and read whole in the background, one at a time, in the index's slices, its titles and names alone parsed (=drover-claude-code-transcripts--queue-titles=, =drover-transcript-read-lines=), 1.3 s for 45 MB, its title then replacing the name (=drover-transcript-update=).  A read of what was appended may end between an =ai-title= and the =agent-name= holding it: the title read is then found to be a name the next read, and the transcript is read whole again.

** An index of files

A user may have thousands of transcripts, some of megabytes, appended to while their conversations run.  =drover-transcript= keeps, by file, what an engine's reader read of it, and the file's size, modification time and inode: a file is read again only once one of them changed, by its head and tail, a window of 64 kB each, as the CLI's own picker reads, or, grown past its head, by what was appended since, at most a window; what the new records tell replaces what the old told, the head's members staying.  Records are found by their markers and parsed alone, and the members of a record too long for its window, as Codex's first one, are found without parsing it (=drover-transcript-sniff=), as the CLIs' own readers do.

A conversation's last activity is the time of its newest message, never its file's modification time: opening a conversation again, the CLIs append records of their own, some timed now, and the file changes though the conversation did nothing.  Claude Code appends its state again (=last-prompt=, =ai-title=, =mode=, =permission-mode=, =cost-state=, =file-history-snapshot=...), queue operations, notes (=isMeta=), a task's notification kept for the transcript only (=queueTranscriptOnly=), and a reply of its own making, =No response requested.=, for a prompt left without one (model =<synthetic>=, which its API errors also have, these ending a turn), and the summary a compaction leaves, which it writes of its own as a conversation sits idle (see [[*After a compaction][After a compaction]]): only prompts, replies and tool results count (=drover-claude-code-transcripts--message-p=).  Codex records its own =session_meta=, =turn_context=, =world_state=, counts of tokens, settings applied and messages of the developer role: only the items and events of a turn's exchange count (=drover-codex-rollouts--event-p=).  A tail holding no such record, as one of records longer than its window, attachments of 140 kB after a turn's reply, is looked behind, line by line whole, a window at a time, back to the head or to what was read before, a megabyte at most (=drover-transcript-look-before-tail=); then the head's newest message, or what was read before, stands.  A reader whose reading changes says so (=drover-transcript-index-version=): what an older one read and kept between Emacs sessions is read again.

The index looks at its files every =drover-transcript-scan-interval= seconds, in slices of 8 ms from timers, giving way to input; file notifications would tell less, as macOS's kqueue reports a directory's entries coming and going, not a file appended to, and a watch per file would take a descriptor per conversation.  Most looks check only the files changed in the last day, a file status each, and list a directory's names again only once its modification time tells files came or went; every eighth look, the first among them, checks every file, so that an old conversation resumed outside Emacs shows within two minutes.  A file a backend has reason to look at, such as the transcript of a conversation whose terminal just closed, is checked at once and read in the next slice (=drover-transcript-check=).  Emacs hashes a long string by sampling it, so file names alike but for a counter would collide in the index's tables; real identifiers are random, and the bench makes its own so.

What the index read is kept between Emacs sessions in =drover-state-directory=, =claude-code-transcripts.eld= and =codex-rollouts.eld=, at most every five minutes and as Emacs exits, so that an Emacs starting reads only what changed meanwhile.  It is a cache, checked against every file's status by the first look, and ignored, with one warning, when it does not read.  Backends find the file of a conversation by its identifier through the index (=drover-transcript-keyed-file=), which keys every entry it holds, those of the cache too: an Emacs starting reads, and so reports, only the files changed meanwhile, and a table the backends kept from what was reported left out every conversation that had not changed, which then listed but could not be found, nor opened from its line (=No session at point=), and dropped from the list once anything reported it changed.

** Front ends win

A conversation a front end follows, in a claude-code-ide terminal or an agent-shell shell, is that front end's session, which tells its status live; its record as recorded is not listed.  A backend listing what an engine records says so (=:recorded=, its engines), its session identifiers the engine's, and yields to any other backend's record of the same conversation (=drover-session-engine-key=): =drover--live-sessions= leaves its records of followed conversations out (=drover--unshadowed=), and the index never holds both, so that it stays incremental, which records of two backends to merge would not let it be.  The index admits a recorded backend's record only while no other backend follows its conversation (=drover--index-admit=); a front end's record gaining, losing or changing a conversation notes the engine keys, and once the changes reported are taken in, the recording backends' records of those keys are looked up again (=drover--index-settle=), in the same pass: a terminal resuming a closed conversation replaces its record in place, and closing it brings the record back, idle, nothing drawn anew.  A subagent of a recorded conversation finds its parent through the engine, under the front end's session.

A front end opening a conversation again, a terminal running =claude --resume= or a shell loading it, showed it active now: claude-code-ide counted the status the CLI tells as it starts, agent-shell every notification of the conversation replayed, and the session began as the terminal did.  The front end's session is the conversation's, so it takes the conversation's times as recorded (=:recorded-times= of the recording backends, =drover-recorded-times=): it began when the conversation did, and was last active at its newest message, or at the front end's own turn when later (=drover-followed-times=); a front end counts as activity only its turns, a terminal's statuses of a turn and its end, a shell's prompt, requests and turn's end.  The recorded times change as the transcript is read: a change reported for a recording backend's conversation takes the records of the front ends following it again (=drover--index-followers=), so that the index and the time it sorts the session by follow.

The front end's session takes the conversation's title as recorded too (=:recorded-title=, =drover-recorded-title=), the front end's own, a terminal's buffer name, standing only until the transcript records one.  claude-code-ide names its terminal after that title as it changes (=drover-claude-code-ide-name-after-title=, from =drover-changed-hook=), until the user names the buffer: the name drover gave is kept on the buffer (=drover-claude-code-ide--given-name=), a name differing from it is the user's, and ghostel's and vterm's naming after the terminal's title is turned off for the buffer.  Renaming the session types =/rename TITLE= in its terminal, once its turn ended and its input box is empty, as =/compact= is typed, so that the CLI records the title, which its desktop app and its =/resume= picker then show: 2.1.319 records it as =custom-title= and as the agent's name (=agent-name=), as =--name= does, and its terminal's title shows it; its transcript is looked at a second later (=drover-claude-code-transcripts-check=), and the buffer follows.

*** How a turn ended

The newest message of a conversation tells how its last turn ended (=drover-claude-code-transcripts--ending=, =drover-codex-rollouts--outcome=): a reply ending its turn, =done=; an error of the API, =failed=, its text the detail, which the summary shows, as OpenCode's error is; anything else =idle=.  For Claude Code, a reply ends its turn when it stopped for another reason than calling a tool (=stop_reason= not =tool_use=, =pause_turn= nor missing, as a reply cut by its terminal closing leaves it); an error is a record the CLI makes of it (=isApiErrorMessage=).  A prompt left without reply, a tool's result, the note of an interruption (=[Request interrupted by user]=) and the output of a command such as =/exit= (=<local-command-stdout>Bye!=, which ends 47 of the user's 119 transcripts, its wording varying) come after what the user saw: =idle=.  For Codex, a turn completed (=task_complete=), or ended by the agent's message, as rollouts of a Codex not recording completions end (=agent_message=, an assistant's =message= item, or =item_completed= of an =AgentMessage=), is =done=; an =error= event =failed=; =turn_aborted=, the user interrupting, or a turn cut amid its tools, =idle=.  A turn a program ran, Claude Code's =claude -p= or an SDK's script (entry points =sdk-cli=, =sdk-py=), or =codex exec=, is =idle=: its reply went to the program, as the automated probes among the user's transcripts show. A conversation a front end follows keeps the front end's status, live; one =claude agents= tells runs elsewhere, that status.  The record's =since= is the end of its turn, as OpenCode's =done= counts from there.

*** Seen

A turn ended is unseen until the user sees it, as OpenCode's is until its session is viewed.  Engines record no such thing, so drover notes, by conversation, the last time the user saw it (=drover-transcript-mark-seen=): marking it seen (=:mark-seen=, =drover-mark-seen= and =drover-mark-all-seen=), opening it, which resumes it in a front end, or a front end following it reporting it =idle= (=:recorded-seen=, from =drover--note-followed= as the index takes in a front end's record of this host): a terminal or shell is idle once its turn was seen, or ran none, so that a conversation the user read in a terminal, then closed, is not shown done again. The time noted is now, or the reply's when later, as a clock ahead of this one dates it; a front end's idle record notes it only when it changes something, a reply unseen or a file changed since read, so that a front end reporting the same conversation over and over writes nothing.

What the user saw is kept in =seen.eld= of =drover-state-directory=, written 30 seconds after a change and as Emacs exits, merged with what another Emacs wrote (the later time of each conversation), bounded: an entry per conversation still recorded, those whose files went forgotten after a look found every file, and =drover-transcript-seen-limit=, 20000, at most, those seen longest ago dropped. *** Context

A Claude Code reply records the API's usage: its prompt's tokens uncached (=input_tokens=), written into the cache (=cache_creation_input_tokens=) and read from it (=cache_read_input_tokens=), whose sum is the prompt the next request sends again, the context, as OpenCode counts a step's. *** Prompt cache

*** After a compaction

Claude Code compacts a conversation as the user types =/compact=, as its context fills up within a turn, and, in the versions seen here from 2.1.291, of its own as it sits idle (=idleCompaction=, on by default): at nine tenths of an hour's cache lifetime after the last request, 54 minutes, when the context holds 200000 tokens or more (=CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS=, 100000 at least), so that the summary is written from a cache still warm. * Searching sessions

=drover-search= (=S=, a global key) replaced the OpenCode backend's =S=, opencode.el's =opencode-consult-sessions=: =consult-line-multi= over the text of the OpenCode buffers open, synchronous, 113 to 432 ms on a common word, blind to closed and archived sessions, to the other harnesses and to other hosts.  It searches in tiers: what the records of sessions tell, in memory, as each key is typed; then what was said in the conversations, which backends search in the background once typing pauses.

** Candidates, scoped and ordered as the list

The search offers the sessions the list shows, scoped by the view settings the list shares, the user wanting "a search using the same transient filter keybindings as session listing": =drover-filter= (each member, its =:search= text too), the older and archived sessions while ~=O~ and ~=z~ show them, the subagents of =drover-show-subagents=.  As it starts it makes an entry of every session of the trees the filter keeps, in the order the list draws them (=drover-view-arrange=, its groups the completion UI's groups, parents before their subagents), each with a name unique among the candidates, its depth, whether the list shows it, and what words typed are looked for in, downcased: the title, the summary, the project, the branch, and the texts backends tell for searching (=:search-text=), those of the backends recording the session's engine too (=:recorded=), so that a terminal of claude-code-ide following a conversation matches by the prompts its transcript holds: its first and last prompt for Claude Code, the first for Codex, 300 characters each, as the index read them.  It takes 22 ms for the 2510 sessions of =make bench=, once.

A session matches when every word typed is in it, in any order and any case (=drover-search-entries=), as the filter's text matches, but by words; a subagent the list hides shows when it matches and no session above it does, at the top of a tree of its own or not, so that a match is never hidden by the subagent setting and a matching parent does not bring every subagent of its.  The list shows such a subagent under a filter only below a parent it lists: a filter narrows a view, where a search looks for a session.  Nothing typed offers what the list shows.  Each key costs 0.3 to 1.2 ms over the 2510 sessions, annotations of a page included, measured as Vertico asks: the completion style, then the affixation of the 20 candidates shown; highlighting every candidate rather than those shown, for a UI without lazy highlighting, up to 4.4 ms for 921 candidates.  Matching allocates nothing but its result: a closure per session, as =seq-every-p= made, cost 40,000 words a key, and in the heap a whole =make bench= grew, garbage collections took a key to 50 ms.

The candidates work with any completion UI.  The table matches the text typed as a whole, which no prefix or substring style would understand, so it comes with a completion style of its own, =drover-search=, in =completion-styles-alist=: its all-completions takes the table's candidates as they are, highlighting the words typed, lazily where the UI asks for it (=completion-lazy-hilit=); its try-completion completes only to the one candidate a text matches.  The search binds =completion-styles= to that style alone, and puts it first for its category, =drover-session=, in =completion-category-overrides=: with the user's styles after it, a style finding nothing fell back on the next, which asked the table for other texts than the one typed, restarting the backends' search, and cost 3.5 ms more a key.  The category being =drover-session=, as =drover-select='s, Embark's actions for it apply.  The annotations are an affixation, computed for the candidates shown only: before the name the status's glyph, the harness's icon and an arrow for a subagent; after it, padded to columns measured once, the project and branch, the host of another host's session, the age, and the snippet of a match of what was said, else the summary, each bounded.

RET opens the session chosen as RET in the list (=drover-open=, its current record from =drover-find=); a text typed rather than chosen opens its first candidate, so that the default completion UI, which does not select, opens what it shows first.  =C-l= shows its row in the list (=drover-list-reveal=: the list shown on the frame, else =drover-list='s, its collapsed group expanded), and tells when the list does not show it.

** The menu of what it searches

=C-'=, the key the user binds the menu to and that drover's menus close on, and whatever key runs =drover-dispatch= (=[remap drover-dispatch]=), leave the minibuffer for =drover-search-menu=, keeping the text typed as the menu's scope: the Field table of the view settings (~=u~, ~=O~, ~=z~, then ~=p~ to ~=c~), their filters alone, the very infixes of =drover-dispatch=, on the same keys, so that a key means one thing in both, as the tests check.  =RET=, or the key that opened the menu again, searches again with the text, in the new scope, which the prompt names (the filter, then =+subagents= or =-subagents= but for the active ones, =+older=, =+archived=), as any key of =drover-dispatch= closes that menu.  The minibuffer is left rather than the menu opened inside it, which transient does not do reliably, and rather than a menu before every search, which would cost a key each time for a setting seldom changed.  The settings are the list's: the list follows them, which a search scope of its own would leave diverging from what the user sees.

Every filter picker reads alike (=drover--read-filter=): its input starts with the names of the value now, so that =RET= keeps it, editing changes it and deleting one of several (statuses, hosts, through =completing-read-multiple=) drops it; an empty answer clears the filter, and so does =(any)=, the first candidate, offered first through the table's =display-sort-function=, the value now right after it. While the minibuffer reads, the sessions changing (=drover-changed-hook=) take their new records and texts in place, the candidates keeping their places under the user's eyes; sessions coming or going, or everything changing, as older sessions arriving, make the candidates anew a second later (=drover-search-rebuild-delay=), 22 ms at most once a second.

** Backends searching what was said

A backend searches what was said in its sessions with =:search=, a function of the text, a scope and a callback, returning a function that cancels, or nil when it searches nothing (as the OpenCode backend before opencode.el offers its search).  The scope tells the filter, whether older and archived sessions show, the most matches taken and =:wanted=, a function of a match telling whether its session is among the candidates, so that a backend searches only those: Codex's archived rollouts are searched only while archived sessions show, Claude Code's transcripts not at all under a filter on another harness.  The callback takes lists of matches, then =done= or =(:failure MESSAGE)=; a match names its session by =:key=, its =drover-session-key=, or by =:engine= and =:id=, with =:host= for another host's, and tells a =:snippet= and a =:position=.  Matches by engine key merge into the session drover lists for the conversation, whichever front end follows it.

The search asks every backend =drover-search-delay= seconds after the last key, a quarter of a second, once the text has =drover-search-text-minimum= characters, three: each key typed cancels the run in progress, whose answers, numbered by a generation, are then dropped, and keeps of what it found the matches whose snippets still hold the text, so that typing further does not blank them.  A run takes =drover-search-text-limit= matches at most, 200, then cancels the backends.  A session matched by several keeps the first snippet, counting the others; a match naming a session the search does not offer is counted as out of scope, which the minibuffer tells before the input with how many sessions were found in text and the backends that failed; matches arriving are shown a tenth of a second later, gathered (=drover--refresh-completion=, which Vertico, Icomplete and =*Completions*= follow).  A backend failing, by signalling or by its callback, is told once, a bounded line, and not asked again in that search.  The callbacks hold the search through a link (=drover-link=), so that they print as a name, and every function the backends call back runs in =drover-with-reporting=.  =drover-search-text= runs the same search without the minibuffer, calling back once every backend finished, for checks and the tests.

** Transcripts and rollouts, with ripgrep

Claude Code's and Codex's backends search their files with ripgrep (=drover-transcript-search=), the files of the conversations the scope wants, as their index knows them, the newest first, as many as fit in a command line (200 kB of names, 24 kB on Windows), then the next ones, a run of ripgrep after another, until the search took its matches: on Windows a user's 553 transcripts take three runs.  Their lines run to megabytes, API requests recorded whole, attachments, tool outputs: Emacs must never read one, nor match in one.  Ripgrep's =--json= gives each matching line whole whatever =--max-columns= says; its PCRE2 engine, needed for lookarounds that would keep a match within a message's text, gave up on such lines (=match limit exceeded=).  Its default engine matches in linear time: the expression finds what begins the text of a prompt or reply, the role and content of a message for Claude Code (=role= then =content=, a string or a first block of text), the =user_message= and =agent_message= events and the user and assistant messages of a turn's items for Codex, then the first match of the text within that JSON string, escapes taken whole, and captures 60 characters around it, which =--only-matching --replace '${s}'= prints alone: tool calls, their results, thinking, the requests recorded and the engines' own records begin otherwise and are never matched.  A file gives one line at most, the session showing one snippet; each line is the file, a null, the line number and the snippet, decoded from JSON in Emacs (=drover-transcript-decode-json=) and bounded.  The words typed match across blanks and escaped line breaks, case ignored.  Over the 120 transcripts of fixtures of =make bench-search=, some of megabytes, a search takes 30 ms to its last match; over the user's 118 transcripts, 52 MB, ripgrep took 40 ms.

Ripgrep runs as a process of Emacs's own, with a filter and a sentinel, not through =drover-command-run=, whose commands give their output once ended and in files: matches stream, and a run typed past is killed at once.  Starting a process cost seconds on a managed Mac whose security agents held every execution (see [[*Commands without waiting][Commands without waiting]]); the NAS watcher at fault gone, starts are cheap again, ripgrep is small, and one starts per pause in typing, per backend.  The longest any function of the search runs on the main thread, starting ripgrep included, is about a millisecond, and a timer ticking every millisecond waits 3 ms at most.  Without ripgrep (=drover-transcript-ripgrep=), the backends search nothing and say so once in the session.

A match carries its line in the file as =:position=.  Opening a conversation resumes it at its end, as RET in the list: neither claude-code-ide's terminal nor agent-shell's shell shows a position of a conversation they load, so a backend operation placing it will come with a front end able to.

** OpenCode, and other hosts

The OpenCode backend's =:search= calls opencode.el's =opencode-search=, a route of the service of the fork searching the prompts and visible replies of its sessions with full-text indexes (=drover-opencode--search=).  Its query is words a message must all hold, which the backend gives the text typed as, quotes and stars dropped so that no text typed is invalid, the last word a prefix as typing is in progress: OpenCode's messages match by words, where ripgrep matches transcripts by the phrase.  The scope narrows it: unarchived sessions alone unless archived sessions show (=:archived nil=), the project of the filter when one project of the service bears its name (=:project=, the filter naming projects by name); the rest the search's =:wanted= does after, a match naming a session the search does not offer counted out of scope.  It asks one page, the 100 best matches first, which suffices since a session shows one snippet; the snippet comes with the service's highlights, which the annotation replaces with its own.  A service without the route answers =unsupported=, remembered by opencode.el per service: the backend then searches nothing and tells nothing, as a service older than 2.2.5 does until restarted on it; a refusal or failure is a failure, told once.  Without =opencode-search=, an opencode.el before it, nothing is searched.  The backend of a peer, =remote:NAME=, searches the same way, asking the peer over the channel to search its own sessions with its own backends and naming them by their keys here (=drover-remote--search=, see =doc/remote.org=, Searching what was said there): the scope tells it the sessions of that backend the search offers (=:sessions=), which the peer searches alone; nothing in the search assumes a backend is local.

** Facts and totals

Every source becomes facts, a session's tokens on a day through a provider and model, with the cost its engine recorded, made once per change of the usage (=drover-usage--generation=): 3,261 for the user's usage, in 1.4 ms. * Engines

A backend is a front end showing sessions (opencode.el, agent-shell, claude-code-ide); an engine is the agent program a session runs (=opencode=, =claude-code=, =codex=, =gemini-cli=, the names agent-shell gives its configurations and the =agent-session:= Org links use).  The two are independent: agent-shell runs any engine, and an OpenCode conversation may show in opencode.el and in agent-shell at once.  Engines own what a new session would run, so the prompt asks them, not the backends: their models, their startup defaults, their agents, and when they last took a prompt.

** Sessions know their engine

A =drover-session= record carries =engine= and =engine-id=, the engine's own identifier of the conversation, nil while unknown.  The OpenCode backend's =id= is the engine's; agent-shell and claude-code-ide use a token of the buffer as =id=, stable while it lives, and put the engine's identifier in =engine-id= once known.  Org links, scheduling and model compatibility read these two slots instead of looking at major modes.

Records of different backends with the same non-nil =(engine . engine-id)= (=drover-session-engine-key=) are one session.  Wherever drover gathers sessions, =drover-sessions= and =drover-known-sessions=, it keeps the records of one backend: the one whose buffer for the conversation the user selected last, since that is where the user follows it, else the one registered first; the others are dropped, silently.  A subagent whose parent's record was dropped this way still finds its parent, through the engine identifier of the record kept.  A live record wins over an older one of any backend.  Records of one backend stay distinct sessions whatever their keys, since a front end may well show one conversation twice.  =drover-find= still returns a backend's own record, from that backend alone, so a buffer can always tell its session; =drover-find-engine-session= finds the one drover lists.  Registration order is the order of =drover--backends= reversed, as a backend registered again keeps its place.

** The registry

=drover-register-engine= takes a =:label=, =:defaults= (a function of a directory and a callback delivering the engine's defaults data, at most once), =:volatile= (the defaults are cheap local state, read again whenever the prompt gains context or a picker opens; otherwise they are read when the prompt starts or changes directory), =:resolve= (from the defaults and the explicit agent, model and variant to what a new session runs), =:agents=, =:last-used=, =:model-resets-variant=, =:directory= (where a conversation ran, for links), and, for clones between hosts (see =doc/remote.org=), =:export= (the files of a conversation and how its records spell its directory), =:import= (making the files received a conversation of this host, in a directory) and =:record-directory= (how its records spell a directory of this host).  Every property is optional: an engine without =:resolve= runs the choices as they are.  =drover-engines= lists them in =drover-engine-order= (OpenCode, Claude Code, Codex, Gemini), others after; =drover-last-used-engine= is the engine whose =:last-used= is latest, a failure counting as unused.  =drover-agent-names= is the union of the engines' agents in that order, so OpenCode's come first and Claude Code's plan and build are offered without OpenCode.

** Models

A =drover-model= describes a concrete offering: its provider (when provider-qualified), native identifier and display name, variants as =(SYMBOL . PLIST)= (=:effort=, the effort the variant sends, when known), default variant, whether those are known (=variants-known=), names front ends take besides its identifier (=aliases=) and engines able to name it.  =drover-model-id-for= gives the identifier an engine takes, and, given the backend it goes to, that front end's alias.  A name an engine can take does not prove its catalog offers it: the prompt resolves selections against the destination's catalog before applying them.

=drover-model-catalogs= keeps source records apart by engine.  =drover-selection.el= groups them into logical, provider-independent model choices; provider and effort are separate choices.  Recognized vendor identifiers group across serving providers, editions and context suffixes stay distinct, and opaque identifiers remain provider-qualified unless =drover-selection-model-aliases= explicitly maps them.  Display names never establish identity.  A logical choice's efforts are a picker union only: resolution uses one offering's native identifier, aliases, variants, defaults and remembered provenance.  Thus remembered Codex Astra and OpenCode's OpenAI Astra appear once, while Codex's =ultra= never becomes an OpenCode effort.

Logical identity is canonical, rather than a provider's spelling: Copilot's =claude-opus-5.5=, the gateways' =claude-opus-5-5= and Claude Code's resolved =opus= refer to one choice. Vendor-scoped normalization handles Claude's version separators and family/version order, Bedrock's namespace and first deployment revision, and known publisher namespaces including Fireworks' model paths. It preserves speed editions, context suffixes, snapshots and other revisions. Canonicalization runs when reading saved logical choices too, so a prompt or schedule picked before a reload still resolves. Source records and outbound model references keep the native ID and front-end alias. Tests cover the mixed provider catalog through both prompt and local/relayed session actions, native-ID round trips across spellings, and distinct editions with identical display names.

=drover-selection-resolve= returns native options and effective settings, or an incompatibility reason.  It prefers the destination's current/default provider when no provider was chosen, preserves its model for a provider-only choice, translates efforts through the offering's =:effort= metadata, and checks what an existing session can change.  Both new and existing candidates use this resolver, as do annotations and sending.  Free-typed completion matches the harness name of a new-session entry or an existing session's name; an existing session's harness remains an annotation, not searchable text.  Remote destinations resolve against their owner's catalogs.

Models come from sources registered per engine with a depth (=drover-register-model-source=).  =drover-models= asks each engine, in =drover-model-engine-order= (Claude Code, Codex, Gemini, OpenCode), its sources from the lowest depth until one answers, then keeps the first report of each provider and identifier.  One source per engine answers because two sources of one engine list different models: a live shell those its agent offers, the CLI's catalog every model of the account; what they list of one model they name alike (see [[*One model, whatever names it][One model, whatever names it]]).  Sources are what runs: live sessions, and OpenCode's service; drover asks no vendor API and reads no credential.

*** One model, whatever names it

Sources name a Claude model differently: agent-shell's Claude agent lists aliases (=default=, =opus=, =opus[1m]=, =sonnet=), the CLI's catalog and transcripts full identifiers (=claude-opus-5-5=).  Keeping each source's names, the picker showed Opus twice, and the memory flipped between names as one front end or the other answered.  So a model's identity is the identifier the CLI resolves its name to (=drover-claude-code--resolve-model=: the environment's =ANTHROPIC_DEFAULT_<FAMILY>_MODEL=, the catalog's =provider_alias_targets=, a cloud's own target first, then the catalog's model of the family; =default= the default the catalog's state serves; a context suffix such as =[1m]= kept), and the name a front end takes is kept apart, as =((ENGINE . BACKEND) . NAME)= in =aliases=.  agent-shell is sent the alias its agent lists, which it validates against its options; claude-code-ide the identifier, which the CLI's =--model= and =/model= take as well as an alias.  =default= names whichever model is the default: a model another value names too is known by that value, which keeps naming it once the default changes; a =default= no catalog resolves is left out, as the pickers' first candidate stands for it.  Without the catalog, an alias is the only name known, and stays the identity until the catalog comes.

*** Sources answering late

Sources answer at once: =drover-models= runs in commands and pickers, which must not wait.  A source whose models arrive or change later, such as a shell whose session starts, calls =drover-models-changed= with its engine, which remembers what the engine's live sources answer now, then runs =drover-models-changed-hook=.  agent-shell's backend calls it after the events that bring a shell's models or thought levels (=init-session=, =init-model=, =init-config-options=, =config-option-update=, =session-selected=, =session-restored=), when it starts following a shell already running, and once a killed shell is gone; claude-code-ide's when a terminal starts and when its conversation is known, by which time the CLI refreshed a stale catalog.

=drover-read-model= listens to the hook while it reads: its completion table reads the candidates whenever asked, the hook collects them anew, and =drover--refresh-completion= has the minibuffer's UI show them, through =drover-completion-refresh-functions= (the =*Completions*= list, Icomplete and Fido, Vertico; Vertico computes candidates again only for new input, so its input is marked as changed, as Consult does).

*** Remembered models

A source registered /live/ answers for running sessions.  When one answers, its models are remembered for the engine (=drover--remember-models=), and the memory answers for the engine at =drover-model-memory-depth= (100): after every source registered today, before any deeper one.  So a live answer always wins and replaces the memory, which stands in once the sessions are gone, in the next Emacs session too: the list is empty only before an engine's first live session.  The answer replaces which models are remembered, not what is known of each: a model takes from its remembered record, of the same provider and identifier (=drover-model-key=), the variants it does not know and the aliases of other front ends (=drover--complete-models=, =drover-model-merge=), and the answer so completed is what =drover-models= returns, so the variants of each model accumulate as sessions switch models.  An alias a model of the answer takes leaves the others, as =opus= moves to a newer Opus.  Without =drover-remember-models=, that is kept for the Emacs session only, and the memory never stands in.  OpenCode's catalog is not live: it is the service's, per directory, and keeps its place before the shells.  A remembered model carries =remembered=, the time a live session offered it, which the picker's annotation shows as "remembered from DATE"; =drover-remember-models= nil neither reads nor writes.

The memory is =models.eld= in =drover-state-directory= (=locate-user-emacs-file= "drover/", or no-littering's =var/drover/= when no-littering is loaded first), Lisp data: =(:version 2 :engines ((ENGINE :time TIME :models (PLIST...))...))=, each model a plist of the slots pickers show (=drover--model-data=).  Version 1 had no aliases, and gave every model the variants of the one a session ran: its models are read with unknown variants (=drover--model-data-upgrade=), and the next live answer writes version 2.  It is written whole to a temporary file in that directory, then renamed over the old one, so a reader never sees half a file; only when an engine's models differ from those remembered, or were remembered another day, so that the day shown stays true without a write at every answer.  It is read when first needed and again whenever its modification time changed, so another Emacs's writes are seen, and merged into before writing.  A file that does not parse, of another version or with a malformed entry is ignored with one warning per Emacs session, and replaced by the next live answer; a failed write is warned of once, and the models stay in memory for the session.  =drover-forget-models= deletes it.

** Options

The prompt passes choices as plists: =(:agent :model :provider :variant :selection t)=, each choice nil when not made. The logical model is a provider-free =drover-model=; a plist without =:selection= still names a concrete, provider-pinned offering. Resolution produces native =(:agent :model :variant)= options for the backend. /Start options/, given to =:create=, add =:title= and =:defaults=; /effective/ options describe what the destination runs; /display/ options mark chosen values; /entry/ options label picker candidates. Scheduled prompts persist the independent choices and resolve them afresh at delivery. A running session keeps settings the user left unspecified, subject to its engine's model-switch defaults.

** Local state

Engines read their local state with the helpers of =drover-model=: =drover-read-json= and =drover-read-json-cached= (kept until the file changes), =drover-merge-settings=, =drover-json-object-p=, =drover-file-mtime=, =drover-getenv=, =drover-model-anthropic-key=.  opencode.el has the same for its own use, privately; the Claude Code engine must work without opencode.el.  =drover-git-branch= reads a directory's branch from =HEAD= without running Git, for backends listing sessions often, kept until the next refresh of the sessions or =drover-branch-ttl= seconds, then read again only once =HEAD='s status changed (see [[*The index of sessions][The index of sessions]]); the OpenCode backend reads its branches with it too, rather than with opencode.el's =opencode-git-branch=, which reads =HEAD= again every =opencode-git-branch-ttl= seconds and finds the worktree anew each time, so that a refresh compares what its records hold with what drover read.  =drover-git-default-branch= reads the repository's default branch the same way, from the =HEAD= a remote records (=refs/remotes/origin/HEAD=, else another remote's), in the common Git directory linked worktrees share: the list asks for it as it draws, to grey the default branch out in the branch's column, as it greys a model's default effort, which =main= and =master= stand for when the remotes record none (=drover-session-default-branch-p=).  The column once left the default branch out, so that a column of =main= would not repeat it on most lines; the details then told it, and an empty cell could not say whether a session had no branch or the default one.

* The prompt

=drover-prompt.el= is the prompt: one Org buffer, =*drover*= (=drover-prompt-buffer-name=), in =drover-prompt-mode=, shown in a bottom side window.  =drover-prompt-dwim= (menu key ="=) opens it from where the user works, with a link to the line at point and the region quoted in a code block, or adds such context to it, an Org heading's line as any other: one key, one action.  =drover-prompt-org-task= (=N=, apt in Org buffers but the prompt; =n= starts the heading's task, see [[*Tasks][Tasks]]) starts a prompt for the Org task point is in, the heading found with the buffer widened, so that it works from anywhere in a folded or narrowed entry.  =drover-prompt-toggle= (='=) shows or hides it.  It is drover's default prompt buffer (=drover-default-prompt-buffer-function=), so the agent, model, effort and directory keys choose what the next prompt runs from any buffer.  Its mode defines the prompt actions =send=, =schedule= (see [[*Scheduled prompts][Scheduled prompts]]), =clear=, =attach=, =copy-block=, =open-link=, =agent=, =model=, =effort= and =directory=; others are added from =drover-prompt-mode-hook=.  =clear= erases the text, region or not, and closes the prompt's window as =drover-prompt-toggle= hides it, the last window of a frame staying; the buffer and the choices made stay, for the next prompt.

The prompt knows no backend and no engine by name.  It sends through optional backend operations and resolves what a new session runs through the engines.

Context quoted from a session's own buffer, the session at point whose buffer it is (not a list of another front end, whose row tells a session too), names the session by its Org link (=drover-session-link=), else its title, instead of =From buffer NAME line N=.  The buffer of a session is named after its title, which read as the subject of the prompt: OpenCode titled new sessions after the session quoted rather than after what was asked.  Its line numbers belonged to a rendering the agent cannot open, where the link opens the conversation.

It was OpenCode's alone, the command naming the agent; a Claude session on another host showed no =<tab>= though its owner could switch it, as neither the engine nor the proxy of a peer's sessions offered it.

** Sending

=drover-prompt-submit= sends the region when active, else the whole buffer (=drover-prompt-content=), after putting the Org text in the kill ring.  The target, read by =drover-prompt-read-target=, is a running session with a live buffer, or an installed new-session target, able to honor all explicit choices.  To a running session: resolve options (=drover-prompt-options-for=), run =:check=, then =:apply-options= and =:send= only on success.  To a new one: resolve its offering, require the feature, then =:create= with native start options and =:send= in THEN.  The prompt stays while options or creation are pending, with another submission refused.  Successful delivery consumes it only if its text is unchanged; cancellation, incompatible settings or a failed switch leave it available to retry.

** Defaults

The prompt holds each engine's defaults data for its directory (=drover-prompt--defaults=).  Non-volatile engines are asked when the prompt starts or changes directory, a generation per engine dropping stale answers and answers for another directory; volatile ones whenever the prompt gains context or the picker opens, after the command.  The header shows what a new session of the last used engine would run (=drover-prompt-effective-options=), or of the first engine able to run a chosen model it cannot, unless the prompt goes to a chosen session; chosen settings in =opencode-setting-chosen=, inherited ones in =opencode-setting-inherited=, the faces of a variant chosen or inherited in opencode.el's mode line.

OpenCode's default model is opencode.el's last pick, =opencode-last-model=, which opencode.el's own new sessions start on, so that both front ends agree.  It used to be the model of the last prompt sent from Emacs, to whatever session: on 2026-11-03 a session was started on Copilot's Opus 5.5 at 16:11, a reply went to an older session running the AI gateway's Opus 5.5 at 16:12, and the next prompt defaulted to the gateway, though no one chose it; replies, scheduled prompts and the Slack investigations all moved it.  Subagents never did, the service starting them without Emacs, nor do the sessions drover lists or the models it remembers (=models.eld=), which only feed the pickers.  The last pick is now the model chosen last for a session: a session switched to it (=opencode-switch-model=, from drover's prompt applying a model or opencode.el's model and variant commands, or an agent pinning it) or created on it (=opencode-session-create= given a model, as drover's prompt does with a model or effort chosen).  A last pick the catalog lacks, its provider down or removed, is skipped, the agent's pin or the service's default applying instead, in drover's header as in the session created, and kept, to apply again once the catalog lists it; before the catalog arrives nothing proves it missing.  A catalog the service still lists while the provider fails at run time proves nothing either: the session is created on it and its prompts fail, as they would in opencode.el.

** For the configuration

Maintenance and the windows a scheduled prompt shows in stay in the user's configuration; it reaches scheduling through =drover-schedule-define-trigger=, =drover-schedule-fire=, =drover-schedule-waiting-count= and =drover-schedule-display-function=, and the prompt and sessions through =drover-prompt-content=, =drover-prompt-consume=, =drover-prompt-read-target= (=:existing-only=, =:options-menu=), =drover-prompt-explicit-options=, =drover-prompt-options-for=, =drover-prompt-apply-options=, =drover-buffer-session=, =drover-find-engine-session=, =drover-session-engine= and =drover-session-engine-id=.  What follows a send, such as burying the buffer of the session the prompt went to, it does from =drover-handed-off-functions= (see [[*Sessions handed their turn][Sessions handed their turn]]), which the prompt's own send runs, not the other sends, from a timer once the command ended: the prompt's window goes as the send consumes it, and a new session's front end shows it as it starts, which a function run in the command would undo or precede.

* Reviewing a session's changes

=drover-review= (=R=) shows what a session changed, in a buffer of Magit's sections, and turns comments on its lines into one prompt for the agent.  The list's recap already named the files a turn changed and counted their lines; a review shows the lines, and asks nothing of the session itself.

** What it shows, and from where

A review has three scopes: the last turn, the whole session, and the working tree against the commit the session started from.  The first two are what the session did, as its engine recorded it; the third is what the tree holds now, the session's commits included, which is what matters in a worktree once the agent has committed or the user has edited after it.

| Scope        | Source                                                                                                                                                       | Why                                                                                                                                                                                   |
|--------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| turn         | the engine's =:changes= (=drover-register-engine=): OpenCode's =opencode-session-diff=, Claude Code's =drover-claude-code-changes=, Codex's =drover-codex-changes= | engines know a turn; Git does not: OpenCode diffs the snapshots its service took, files outside Git included; Claude Code records each tool's patch with line numbers; Codex the patches it applied |
| session      | the same, every turn                                                                                                                                         | OpenCode diffs from the first prompt's turn to the newest's (=from=, =to=), refusing a range spanning a move of the session, which the review tells                                     |
| working tree | Git, run through =drover-command= (=drover-review--git=)                                                                                                     | any session with a directory here, whatever its engine; the commits since its start, what is not committed, and the files not tracked yet, which a turn's agent often makes             |

Claude Code and Codex record what each tool did, not the state of a file before the session: the whole session shows each edit's hunks one after the other, in the order made, each numbered as the file was then (=drover-transcript-changes=), a file's edits gathered in the place of its first.  Reconstructing one diff from the first state to the last would need the file as it was, which only Git or the file system holds, and their texts no longer match once the user or another session edited: the working tree is the scope for that.  Claude Code's transcript gives each edit's =structuredPatch= and each file written whole; its subagents' transcripts, under =ID/subagents/=, count too, those since the newest prompt for the last turn.  Codex records the =apply_patch= call, in its own format, without line numbers, and, as it applies it, a =patch_apply_end= event (or an =item_completed= =FileChange=) with each file's unified diff, numbered: that wins over the call it tells of, by =call_id=, and a patch that failed or was declined changed nothing.  Transcripts and rollouts are read whole, in slices of a few milliseconds from timers (=drover-transcript-read-lines=), only the lines naming a key parsed, each decoded once whole, so that a character cut between two reads decodes; the last turn is looked for in the last 8 MB first.

The commit a working tree is compared with is where HEAD was as the session was created: Git's reflog of the worktree knows it (=HEAD@{@TIME}=), for any session, however old, whatever front end ran it, without drover recording anything.  A reflog not reaching that far gives its oldest entry, the review saying so; without a creation time or a reflog, the commit the branch forked from origin's default branch (=git merge-base HEAD refs/remotes/origin/HEAD=); else HEAD, and the review tells it shows what is not committed alone.  Files Git does not track are read here, 200 of 2 MB in all at most, binary ones named only.  The diff is Git's, with renames found, prefixes and quoting fixed whatever the user's configuration (=--src-prefix=, =core.quotePath=false=).

A session of another host is reviewed by its host: the proxy's =:review= asks the owner, which fetches with its own engines and Git (=drover-remote--on-review=) and sends 2 MB of patches at most, the files past that with their counts; the viewer checks and bounds every value again (=drover-remote--decode-review=).  The capability =review= tells a peer can; an older one is told so, on the review's line.  Its files are on the owner: =RET= visits nothing there.

Whatever the source, a review is bounded where it is taken in (=drover-review--bound=): 2000 files, 8 MB of patches, the files past them with counts alone, names and notes to lines; a line of a diff shows 1000 characters at most.

** One view, Magit's sections

The review buffer is =drover-review-mode=, of =magit-section=, which drover requires: a file per section, a hunk per section within it, so that Magit's keys fold and move, in =diff-mode='s faces.  Magit's own diff buffer was the alternative: it shows Git's diffs only, while a turn's changes are OpenCode's snapshots or a transcript's patches, and it refreshes itself after every Magit command, erasing the comments drawn in it.  One renderer draws every source alike, a peer's too; =M= opens the working tree in Magit, whose =k= discards a hunk with its own confirmation, and =P= shows the review as one patch in =diff-mode=.  Reverting a hunk from the review is left to those: OpenCode reverts a whole turn (=t= in its buffer), not a hunk, and a hunk of a turn may no longer apply to a tree edited since.

Each line of a hunk carries its kind and its numbers on both sides (=drover-review-line=), which comments and visiting read.  A file's lines are appended to the hunk drawn last, hunks to the file drawn last, the ends of the sections moved, =drover-review-chunk-lines= lines between two looks at the clock, for =drover-review-slice= seconds a slice, the first in the command and the others from a timer (=drover-review--draw-some=): a diff of any size shows its first screens at once and never holds Emacs long.  Sections are held through =drover-link=, so that what the review keeps prints in proportion to its diff.

** Comments, and the prompt they make

A comment is on a line, or on the lines of a region, of one hunk; it keeps the file, the side its lines are numbered on, new unless all are removed lines, their first and last numbers, the lines themselves and their hunk's heading, so that it is shown, and sent, without the review that made it.  It is shown under its last line, after an overlay's =after-string=, and marked in the fringe; drawn anew, as on another scope, it goes where its last line reads the same with the same number, else where its lines read the same in a row (lines moved), else in a section at the end, under the lines it quotes.  Comments are kept by conversation (=drover-review-key=, its engine key), so that they follow it from one front end to another, in =review.eld=, written two seconds after a change and as Emacs exits, the 200 sessions commented on last.

=C-c C-c= composes one prompt (=drover-review-compose=): a line telling the changes and how many comments on how many files, then each file, in the review's order, its comments by line, each telling its lines, quoting them under their hunk's heading in a diff block, then its text; the note on the whole review last.  The heading first keeps the block's lines as they are: Org removes a block's common indentation, which a block of context lines alone, each beginning with a space, would lose.  The prompt goes to =*drover*=, set to go to the session (=drover-prompt-edit-for=), to be read, edited and sent as any prompt; =C-u= sends it at once, as the prompt sends (=drover-prompt-send-to=).  The comments sent are marked so, dimmed, and leave the next prompt; drover cannot know whether the prompt left in =*drover*= was sent, and a comment marked sent is kept a week rather than forgotten, so nothing written is lost: editing it makes it pending again.

* Org links

=drover-links.el= defines the link type =agent-session=: =agent-session:ENGINE/ID= names a conversation, not a buffer nor a front end, by the engine running it and the engine's own identifier (=drover-links-conversation=), which outlive the buffer, the front end and Emacs; a front end showing the conversation is found again by its key, =drover-session-engine-key=.  The configuration this came from had it as =val/agent-session/…=, keyed on major modes; drover's sessions tell their engine, so =org-store-link= stores a link from the session at point of any buffer, a session's own or a list's row, through =drover-session-at-point=.  Only the conversations of engines telling where they ran (=:directory=, see [[*The registry][The registry]]) have links: following one resumes the conversation in its directory, which no other record keeps once the buffer is gone.  Claude Code tells it from the bucket of its transcript, Codex from the =session_meta= record a rollout begins with, read up to a megabyte, OpenCode from the service, later; Gemini CLI from nothing, and its sessions have no link.

Following a link shows the conversation through =drover-open= where drover finds it in a live buffer, of any front end; otherwise a front end resumes it, through the registry of resumers (=drover-resume-with=): those of =drover-links-front-ends= for the engine that are installed, loaded or not, then any other registered, asking which when several can and =drover-links-ask-front-end= is set, the one =drover-resume-front-ends= prefers offered first.  Choosing a front end not loaded loads drover's backend for it, which loads the front end.  A resumer may find a conversation by its identifier alone (=:by-id=), as opencode.el opens a session by asking the service, and give its buffer later (=:async=, THEN and ELSE); the others get the directory the engine tells, the link then resuming once it is told, a failure in the command a =user-error=, one later a warning.  =drover-links-front-end-types= registers more link types, each opening in one front end without asking, and reading a bare identifier as a conversation of one engine: the links the configuration stored before, =claude-code:ID=, =claude-code-ide:ID=, =agent-shell:[ENGINE/]ID= and =opencode:ID=, keep opening as they did.  Org registers the types as =ol= loads (an autoloaded =drover-links-register=), so a link opens before drover's files are loaded.

** Hosts

Sessions will run on other machines.  A link may name its host, =agent-session://HOST/ENGINE/ID=, the authority of a URI: an engine's name never begins with a slash, so a path with a host is never read as one without, and every link stored so far, without a host, names a conversation of this machine, as it did.  =drover-links-parse= returns =(:engine :id :host)=, =:host= nil for this machine; links with a host are read, and refused when followed, until sessions carry a =host= slot: then =drover-links-conversation= gives the session's host, a key of conversations becomes (HOST ENGINE . ID), and following a link finds the session of that host, resuming it through the host's front ends.  A scheduled prompt stores its conversation as such a link (=:link=), so its records need no change either: one with a host is kept, and fails when delivered, telling why, until hosts are reached.

* Scheduled prompts

=drover-schedule.el= sends a prompt to an existing conversation later.  It came from the user's configuration, where it named front ends by their major modes and a restart of OpenCode or Emacs by the configuration's maintenance actions; in drover it names backends, and events the configuration defines.

** When

The time is read locally (=drover-schedule-parse-time=), never by a model, so that what is scheduled is what was read: =in N UNIT=, days and weeks keeping the time of day across a change of daylight saving time, minutes and hours elapsing; a day, a time, or both; =tonight=.  Anything else is nil rather than a guess, and a time a day does not have, skipped by the spring change, is refused.  The reader (=drover-schedule-read-when=) shows what the input resolves to as it is typed, refuses and reads again what is not a time or is past, and takes =RET= as what was typed, never a candidate it completes to (=vertico-preselect=).  Besides times, a prompt may wait for the end of its session's turn, offered first while the session works or retries, or for an event the configuration defines (=drover-schedule-define-trigger=): =after LABEL= is offered and read, its :request asks for the event and returns a key, and =drover-schedule-fire= with that key sends the prompts waiting for it, or cancels them when the event will not happen; the last prompt cancelled or sent at once withdraws the request (:release).  The configuration this came from defines the restarts of Emacs and of the OpenCode service, through its maintenance actions.

A prompt waiting for a turn gets its time once the turn ended, on =drover-changed-hook=: when its session leaves =drover-active-statuses=, a question pending being part of the turn; when drover no longer lists it, at once for a backend whose buffers run their agents (=:runs-in-buffer=), whose turn ended with the buffer, and for a service's session once the backend lists every session the service runs (=:ready=), as the service may still run the turn after Emacs restarted.  A backend not loaded tells nothing, and the prompt waits.

** The queue

The prompts are plists in =scheduled-prompts.eld= of =drover-state-directory=, written whole through a temporary file (=drover-write-data=) before every change takes effect: a prompt not saved is not scheduled, and a status is saved before the step it announces.  A file that does not read is never written over: the queue stays unread, scheduling refuses, and =drover-schedule-restore= tells it on one line.  Version 2 names a prompt's backend and stores its model as data (=drover--model-data=), so that a model reads whatever its structure becomes; version 1, the configuration's, named front ends (=ide= for claude-code-ide) and printed models whole: =drover-schedule-former-files= takes such a file in once, its prompts joining the queue unless one of the same identifier is there, then renames it =.migrated=, and a model that no longer reads is dropped, the prompt kept.  The queue itself, with its timers and the deliveries in progress, is a structure with a layout stamp (=drover-schedule--state=): one made by another version is dropped, its timers cancelled, and read again from the file.

Restoring arms the pending prompts' timers, catching up those that fell due while Emacs was away (it does not wake the computer), and checks the prompts waiting for a turn at once.  A prompt Emacs stopped while opening its session is pending again; one it stopped while submitting is interrupted, since whether it went out cannot be known, and is retried only when the user says so.

** Delivery

A prompt due finds the live buffer of its conversation in its backend, with a running process, by the key of its conversation, never by its directory; without one, its backend resumes the conversation (=drover-resume-with=) in the directory recorded.  =drover-schedule-display-function= gives the window it shows in, a new frame by default; the configuration tears a visible buffer off into its own frame.  It then waits, polling, until the buffer takes the prompt without touching what the user typed: the buffer shows the conversation, its process runs, and its backend's =:blocker= says nothing, an empty input box for a Claude terminal, an initialized idle shell with nothing typed for agent-shell, a loaded and connected buffer for OpenCode, which sends past a draft.  The prompt's explicit agent, model and effort are applied as a send applies them (=drover-prompt-apply-options=), then the backend's =:submit= hands the prompt over and tells whether the front end took it: a terminal is pasted the prompt, then pressed return a moment later, a shell inserts and submits it, OpenCode sends it literally, shown once delivered and consenting to drop stale thinking, since no one is there to be asked.  One delivery at a time goes to a conversation; each callback is scoped to its delivery, so that one cancelled or timed out ignores what comes back late; =drover-schedule-wait-seconds= bounds the wait, the failure telling what the buffer was still waiting for.

* Other hosts

=drover-remote.el= is the first step of =doc/remote.org=: peers list each other's sessions, and since its second step act on them through their owners (see =doc/remote.org=, The second milestone, as built).  Records gain three slots, last: =host=, the owner's name, =origin=, the owner's backend, and =stale=, when the owner was last heard from while it is not connected; =drover-core-generation= is 4, 5 since the refresh of changed branches joined it (the list asks a full refresh, the proxies count on a refresh reading no branch of theirs), 6 since records gained a fourth slot, =default-branch=, and the record's new layout has the index and lists made anew once.  A session of another host runs in a directory of that host, which this host's file system is never asked about: the owner sends the default branch of its repository as it reads it (=default-branch=, from =drover-git-default-branch=), which the list's branch column greys out, =drover-default-branches= standing for it when the owner knows none (=drover-session-default-branch-p=); the owner names the files a turn changed relative to the session's directory, and the viewer shows them as received; commands starting a session or a prompt there (=drover-new-session=, quoting a session into the prompt, the prompt's targets) take =default-directory= rather than another host's directory (=drover-session-local-directory=), whose details show it unabbreviated.  The branch, the titles' places (no buffer of a proxy), recaps, previews and the minute's refresh already kept off this host's files.  A peer's sessions are a backend, =remote:NAME=, its records' identifiers the owner's keys, so that their keys here, =(remote:NAME BACKEND . ID)=, and their parents resolve as any backend's; their engine keys name the host, =(HOST ENGINE . ID)=, so that a conversation of another host is never merged with one of this host, nor archived in this host's archive.  Records travel as JSON on spyglass's channel =drover=, parsed and never read, every value checked and bounded as it arrives (=drover-remote-decode-record=): what does not fit is dropped, names are interned only when short symbols, faces go through spyglass's sanitizers, times are moved by the connection's clock offset.

The owner numbers changes.  It follows =drover-changed-hook=, noting for each session changed the record served, the index's, and its parent's key, compared by =eq=, then =equal= for a record copied as the index was made anew, and gives it a revision when it differs; a session gone leaves a tombstone, the last 4096 kept.  Nothing is noted while no peer subscribes: the next subscription compares every session first.  A subscribing peer tells the epoch and revision it holds: the owner sends the sessions whose revisions are newer, and the tombstones, as an update, or a snapshot.  A batch goes in messages of 100 records, serialized for 4 ms at most, at most four messages unacknowledged; the next update starts once the last was acknowledged whole, so that a session changing a thousand times while its peer lags is sent once.  The viewer applies messages from a timer, 8 ms at a time, acknowledging each, and reports what changed, every change, a branch the owner read included: the proxy says so (=:reports-changes=), so that the minute's refresh neither lists a peer's sessions again nor reads the branch of their directories, which are on the owner (=drover--index-unreported= passes over a record with a host); =g= lists them again from what was received.  With 2511 sessions of a peer held, the minute's refresh takes 0.2 ms, where listing them again, as it did before, takes 4.3 ms.  Past 200 sessions changed at once, they are listed again, which the index takes in 9 ms for 2511 where one by one cost 80 ms.  A snapshot keeps the records held while it arrives and drops at its end those it did not list.

Either host may dial.  Each greets on every connection with its name and Emacs instance; of two live connections of one Emacs, both keep the one dialed by the host whose name sorts first, the loser's dialer closing it and standing by, and of two Emacs claiming one host, the second is refused while the first is connected.  A peer whose stream ends goes stale at once (spyglass's heartbeats, 5 s, drop a silent one after 20); a peer turning the mode off, or dropping this host from its configuration, says =bye=, and its sessions go.  A refusal closes the connection a second after telling why: closed at once, the peer writing meanwhile lost the reason unread.

A greeting is answered with one only when it asks for it, =ask= being JSON's true: the false of JSON parses to =:false=, which is not nil, and every greeting answered the last, about 11,000 a second between two idle Emacs, re-electing the connection and arming its heartbeat each time.  It also left a write in flight at every moment, so that dropping a stream, as =make bench-remote= does to measure resynchronizations, always caught one: spyglass told =Sending failed: Process spyglass no longer connected to pipe= three times a run.  Spyglass's errors on drover's connections come to =drover-remote--spyglass-error=: a write failing finds its stream gone, or drops it, spyglass dropping a stream whose write failed since part of a frame may be on it, which nothing can follow; the stream's end follows and is what the list and =drover-remote-status= tell, so the failure is counted, not reported, nor kept as the peer's last error, and drover breaks no stream itself, as it once did through =spyglass-connection-drop-stream=, which spyglass keeps for tests (=spyglass-reconnect= being the way for an application that finds a peer unresponsive by its own measure, which drover needs not: its heartbeat is spyglass's, and a gap in updates resubscribes on the stream as it is); another error is that last error, as failing to connect is; one after which the stream stays open =drover-remote--error-grace= seconds later is unexpected, warned of once per =drover-error-interval=.  What a broken stream lost is asked again once connected anew (=drover-remote--resume=): the subscription from the revision held, the requests not answered (recaps, previews), until =drover-remote-request-timeout=, the keys to prefetch, and the older and archived sessions while lists show them, which come in several messages.

The list gains the field =host=, whose column shows only when a session of another host is listed, the host's label then, and its age while stale (=core 5m=, the row's inputs carrying that age); a stale session's title is dimmed and its glyph still; grouped by =host=, this host comes first, then the peers in the order configured (=drover-host-rank=), a group saying when its host is not connected.  =drover-surfaced-sessions= and the mode-line count leave stale sessions out.  These depend on the remote layer through variables of the core it sets (=drover-hosts-function=, =drover-host-label-function=, =drover-host-state-function=, =drover-links-remote-function=), so that the core, lists and links load without spyglass, as does =drover-remote.el= itself, which declares what it uses of spyglass and loads it as the mode starts.

=make bench-remote= measures it (=test/drover-remote-bench.el=); in batch, the probe a timer every 5 ms late, the times including =drover-refresh-delay= (0.1 s) and, for a resynchronization, spyglass's first reconnection delay (0.2 s) and, through SSH, the registration read again:

* Commands without waiting

Backends run CLIs from timers and from commands: =claude agents --json= every =drover-claude-code-agents-interval= seconds while a list shows, =codex archive=, =unarchive= and =delete=.  A process Emacs starts costs its main thread the whole start, however asynchronous the process is afterwards: on macOS, =posix_spawn= returns once the program was executed, and the security agents of a managed Mac (Endpoint Security clients) hold each execution until they allowed it, longer the larger the program.  Measured in a running Emacs on such a Mac, =make-process= of Claude Code's CLI, an executable of 310 MB, took 1 to 8.5 seconds every time, and of =curl= up to 2.5 seconds now and then, where a batch Emacs took a few milliseconds: pauses of a second every 30 seconds, whose profile shows no Lisp at work.

So =drover-command-run= has a shell, the runner, start the commands: started once, with the environment of its time, it reads a line per command, quoted with =shell-quote-argument=, and answers a line as each command starts, its process, and as it ends, its status; each runs in the runner's background, its output and errors in files of a private directory, of which drover reads =drover-command-output-limit= bytes at most.  Emacs writes and reads lines on a pipe, never waiting; the callback, run in =drover-with-reporting=, gets =(:exit STATUS :output STRING :errors STRING :truncated BOOL)=, or =(:failure MESSAGE)= when the command ran out of =drover-command-timeout= seconds, whose process is then stopped, or when the runner ended.  Callers keep the identifier it returns, to run one command at a time (=drover-command-live-p=) and to cancel it (=drover-command-cancel=).  Once =process-environment= changed, the next command starts a new runner, the old one ending once its commands ended.  An argument the runner's lines cannot carry, a newline, or a system without a POSIX shell (=drover-command-shell=, nil on Windows), starts the command as a process of Emacs's own, as before.

Requests to the OpenCode service start a process too, opencode.el's =curl=: the OpenCode backend takes the project a =project.updated= event sends whole in place of the one of its identifier, rather than fetching the projects again on every such event, and draws sessions again only when what names them changed; it fetches them when it never did, during a fetch, after an event without a whole project, and on reconnecting.

The tests make every start of a process take a second, as such a Mac does (=drover-test-with-slow-starts=), and check, with a timer ticking every hundredth of a second, that a command sleeping two seconds, run again and again, makes Emacs wait less than 50 ms and runs once at a time.

* Agents, through Anvil

=drover-anvil.el= gives agents the sessions the user has: Anvil, the MCP server running in the user's Emacs, serves its tools to any MCP client, OpenCode's sessions among them.  They list (=drover-sessions=), read (=drover-session=: the record, the recap of the last turn, what pending requests ask), start (=drover-session-create=), prompt (=drover-session-send=), wait on (=drover-session-wait=), answer (=drover-session-answer=), interrupt (=drover-session-interrupt=) and archive (=drover-session-archive=) sessions, by keys of their own, =BACKEND/ID=, a proxy's =remote:HOST/BACKEND/ID=.  They act through what the user's commands act through, the backends' operations, never a front end: =:submit= for prompts, as scheduled prompts are delivered, after =:blocker= for a session whose buffer is live, =:create= with =:hidden= and =:send= for new sessions, =:requests= and =:answer=, which the peers' proxies have too, so that a session of another host is prompted and answered as one of this host, by its owner, =drover--call-confirming= and =drover--archive-step= as bulk actions do.  Nothing shows a window (=display-buffer-overriding-action= is =display-buffer-no-window= meanwhile, and new sessions start hidden), and nothing asks: =inhibit-interaction= makes a question signal, which the agent reads as the tool's error, and no dialog box is used (=drover-quietly=, see [[*Asking nobody][Asking nobody]]).

** What agents may do

The user says what agents may do, action by action (=drover-anvil-permissions=): on any session, on those of the caller's project, on those the caller started, or never.  The caller is the session whose agent calls, named by its client in the call's =_meta= (OpenCode's =ai.opencode/sessionID=, which Anvil hands its handlers as =anvil-server-request-meta=); =drover-anvil-callers= reads it.  The project of a session is the main worktree of the repository of its directory, so that sessions of the worktrees of a repository share it, and directories the user names (=drover-anvil-scratch-directories=) belong to every project; a session of another host is in none, its directory being that host's.  By default agents read every session and wait on any, which changes nothing; start and prompt sessions of their own project, as they would edit its files; interrupt, archive and answer the questions of the sessions they started, which they are responsible for; and answer no permission, which is the user's to grant.  A caller its client does not name is held to what applies to any session.

A tool never acts on the caller nor on a session above it: their turns wait for the caller's, so interrupting one ends the caller's own work, and waiting for one waits for itself.  Nor does a session wait for one waiting for it, through the tools, at any depth.  Every call is logged (=drover-anvil-log-file=, in the state directory by default), and an action that cannot be is not taken: the log is the account of what agents did.

** Waiting without Emacs waiting

A turn ends minutes later, a recap after a request; Emacs must not wait for either, nor hold the MCP client's call in a loop reading processes, which would freeze it.  What ends later is a job, polled: its function looks at the index, cheap, and settles it.  Anvil's stdio bridge holds a call whose handler returns =anvil-server-defer= and polls it, each poll returning at once, while it answers the client's other calls: the agent's call waits, Emacs does not.  A client that cannot wait gets the job, whose answer =drover-job= returns once there.

A wait ends once the session runs no turn and has no prompt pending (=drover-pending-prompts=), and its status began after the prompt it waits for: the last one sent through the tools, or the time the agent gives, so that a session still idle from before the prompt is not taken for done, nor a turn ended between two polls missed.  Waiting for the user (a permission, a question) ends it too, what is asked fetched with it.

** Bounded

What the tools answer is bounded as drover bounds what it takes in: titles and lines to a line, texts as =drover-bound-text= cuts them, lists to =drover-anvil-list-limit= sessions, requests and fields to a few.  Records hold nothing of the credentials of hosts or services, nor do the tools add any.

* Tasks

A task is an Org heading worked on by agents in a place of its own: a worktree on a branch of its own, the main checkout, or a folder (=drover-task.el=).  Phase 3 of the design the user approved; its research compared Conductor, Claude Code, Codex, Cursor, Superset, Emdash, Vibe Kanban, Sculptor, Claude Squad, roost and others, and kept what survives their churn: Git's worktrees, =.worktreeinclude=, a branch per task, =gh= for pull requests.

** The heading is the task, and drover keeps no index

A task's state is its heading: drover reads it when it needs it, by ID, and keeps what it read in memory until the heading's buffer changes (=drover-task-org-fresh-p=, a buffer's modification tick), never on disk.  Headings move (ejira refiles them to keep its hierarchy) and change ID (ejira makes an issue's key its ID once the issue is created, the ID before kept as =ORIG_ID=), so a heading is found by either, in the file =org-id-locations= names, visited if need be, then in the Org buffers visiting files; never by =org-id-find=, which reads every Org file when an ID is unknown, a minute with the user's 101 agenda files and the NAS.  A heading still not found is looked for with ripgrep, from a process, in the files the ID locations and the agenda name (=drover-task-org-find=).

What drover writes is what ejira leaves alone: properties beginning with =DROVER_=, which ejira's hashes leave out and its pulls never delete, and notes in the LOGBOOK drawer, which is metadata, outside the description it pushes.  Never a child heading: ejira takes a TODO child of an issue for a new issue, a plain one for part of its description, one under =Comments= for a comment.  A file saved after drover wrote it, when it had no unsaved change, is saved with =ejira-push-on-save= nil, as a change ejira counts and does not review; a buffer the user was editing keeps both, saved by the user.  Done, on the user's word, is the normal Org way, =org-todo=, saved as any save: ejira's review then offers the issue's transition, drover never talks to Jira.  The copy of a tracked task file in a linked worktree (secateur's =todo.org= is tracked) is never opened nor written: ejira would take it for a second copy of the same issues.

The repository of a heading is a name, =DROVER_REPO=, inherited, the same on every host, never a path (secateur's =todo.org= is tracked in a shared repository); =drover-task-repositories= maps it to each host's checkout and its settings: where worktrees go (secateur's are siblings, =../secateur-TOPIC=, as its AGENTS.md has it), the branch prefix, how work finishes, the setup, the checks, the teardown.  Without it, the repository of the Org file; without one, a folder the heading links; else the user is asked, and offered to save =DROVER_REPO=.  Paths compare canonically (=drover-task-canonical=): =~/Documents= and =~/local= are one directory on the user's Mac, through aliases, and Git on Windows spells =c:/Users= =/c/Users=.

** Which task a session serves

The heading-to-session link is the session's first prompt, which links the heading (=[[id:…]]=, or =[…](id:…)= once Markdown): tasks start sessions so, and =drover-prompt-org-task= did.  First prompts come from where the engines record them: the transcripts and rollouts the Claude Code and Codex backends index (their =:search-text=), and OpenCode's database, read only, the first user message of each session written since the last read, back 60 days the first time, those holding =id:= alone (=drover-task--oc-read=, 0.2 s over the user's 8 GB database, once a minute while a list shows).  A session running in a worktree a task made serves it too: the worktree's Git directory holds a file, =drover-task=, naming the task, which Git removes with the worktree; it tells the task of every session there, subagents' and those started by hand, and tells a sweep drover's worktrees from others.  That file is Git's metadata, not drover's state.  The one thing drover keeps of tasks is the sessions the user linked by hand (=drover-task-link-session=), the newest 1000, by conversation.

Views ask through =drover-session-task-function=, which =drover-task-mode= sets: a session's task as a plist of its ID, title, project and face, answered at once from memory; a heading not read yet is read while Emacs is idle, a few at a time, and views drawn anew once.  A row's inputs hold the task, so that a row changes as its task does.  The project is the heading's Org category, the file's name unless =#+CATEGORY:= or =:CATEGORY:= say: views show it in place of the backend's project (=drover-session-view-project=), group and filter by it, and group by task (=task= in =drover-groupings=).

** Colours of projects

The Project column shows a task's project in its colour, after a pill (=drover-project-icon=) kept whole where room is short: the field shows its pill alone in two lines and in the sidebar, in a cell of the line's end (=:narrow icon=, an iconic field as the host's and the context's), so that pills line up and no title moves.  The colours are the theme's (=drover-task-palette.el=): the foregrounds of standard faces, Font Lock's and ANSI's first, then every colour the enabled themes' settings name, those of enough chroma, far enough in lightness from the default background and from one another in OKLab; past them, colours made in the palette's median lightness and chroma, along the golden angle from its first hue, each apart from the others.  A project keeps its slot, the first free when first seen, kept with when it was last seen in =task-projects.eld=, the newest 500, so that another theme colours each project anew, never reshuffling them; a theme enabled or disabled makes the palette anew and redraws views.

** Starting

=drover-task-start= (=n=) on a heading starts its task, or continues it once its heading names a place: a session of it opens, or another starts there, or, the setup having failed, the setup runs again first, or, the worktree gone, it is made again from its branch.  Starting resolves the repository and how it works, names the task after the heading, its Jira key first, and makes its place in steps run one after the other from processes (=drover-task-git-steps=, through =drover-command-run=, so that no step waits): the target fetched from origin within =drover-task-fetch-timeout=, never prompting, else HEAD; the base resolved and recorded; free names found; the worktree added on a new branch, locked with a reason naming the task, its marker written; the heading's =DROVER_= properties and note written then, so that a failing setup leaves a task that knows its worktree; uncommitted changes carried, with =C-u=; the ignored files =.worktreeinclude= names copied, as Claude Code and Codex copy them, only those Git ignores on the task's branch, macOS's =cp -c= cloning them on APFS; submodules; the setup, visibly, in =*drover task: TITLE*=.  Then a session starts there, of the prompt's first new session (=drover-task-harness=), titled after the heading, its first prompt linking it.  A task models attempts, numbered properties (=DROVER_WORKTREE_2=…), of which phase 3 makes one.

** Finishing

=drover-task-finish= (=F=) asks what it must before anything runs, waited for in the command (the worktree's status, a pull request's state): the uncommitted files that would be lost, named once, and whether to mark the heading done.  Then, as the repository says: =merge=, its branch merged into the target in the main checkout (=--no-ff=, =Merge BRANCH: TITLE (KEY)=, as secateur's merges read); =merge-push=, the target fast-forwarded to origin's first, merged, checked with =:checks= from that merged state, then pushed, a failing check pushing nothing and keeping the worktree; =pr=, the branch pushed and a pull request opened with =gh=, the task cleaned up when finished again once its pull request is merged, a squashed branch deleted then only if its tip is the pull request's head.  Conflicts are looked for first, with =git merge-tree=, and stop it.  Cleaning up: a snapshot as =refs/drover/snapshots/BRANCH=, the branch's commit, or with uncommitted changes a commit of every file through a temporary index, the branch's commit its parent; the teardown; the worktree unlocked and removed, forced only once the user agreed and the snapshot is kept; the branch deleted with =-d=, kept unless merged; the task's sessions archived; its =DROVER_= properties of the place removed, a note telling what was done; the heading marked done if the user said so.  =drover-task-sweep= (=W=) lists worktrees, deleting none.

** Other hosts

A task belongs to the host running its sessions, =DROVER_HOST=.  Another host starts it in its own checkout, named alike in its =drover-task-repositories=, and finishes it, through the request =task= of the remote layer, for peers telling the capability =task=, as their access allows: =act= starts, =full= finishes (see remote.org, [[file:remote.org::*Tasks of other hosts, as built][Tasks of other hosts]]).  The heading stays on the host asking.  Moving a task between hosts is for later.
