* Backends describe, drover arranges

A backend owns its sessions and their state; drover asks it for =drover-session= records whenever it draws, and never caches them beyond one redraw.  The record is a snapshot with one status, so every view ranks and groups sessions the same way, through =drover-sort=, =drover-tree=, =drover-group-trees-by-status= and =drover-group-trees-by-project=.

Backends report changes with =drover-backend-changed=.  A turn streams many events, so changes are coalesced: =drover-changed-hook= runs once the backends have been quiet for =drover-refresh-delay= seconds, and views redraw from it.

* One status per session

| Status     | Meaning                                                     |
|------------+-------------------------------------------------------------|
| =waiting=  | A permission request or question waits for the user         |
| =failed=   | A turn failed while the user was not looking at the session |
| =done=     | A turn ended while the user was not looking at the session  |
| =retrying= | The running turn waits to retry a failed request            |
| =working=  | A turn runs                                                 |
| =idle=     | Nothing to do                                               |

The first three need the user (=drover-attention-statuses=).  Among them, the session waiting longest comes first: =since= is when the status began.  Seen and unseen are the backend's to track: for OpenCode, the service records when a client viewed a session, so a turn read in any client is no longer =done=.

* Actions go through the backend

Every action takes a session and calls the matching function its backend registered; an action the backend lacks is a =user-error=, and views can test =drover-supports-p= to hide it.  A backend may also tell which buffer shows a session (=:buffer=, read through =drover-session-buffer=), so views can mark the session the user is looking at.

* Starting backends

=drover-start= runs each backend's =:start= once, and from then on starts every backend as it registers: a front end loaded after drover started, such as opencode.el loaded lazily, joins without another call.  Views and the attention mode call it when they open, so the first view opened starts everything.

* Subagents under their parents

=drover-tree= nests each subagent under its parent, and every view draws trees.  A tree ranks by the most urgent status within it, so a parent whose subagent waits for the user is listed with the sessions that need the user, its subagent beneath it.  =drover-tree-visible= drops the subtrees of subagents to hide and ranks each tree again by what remains, so a hidden subagent never places its parent in a group its own icon does not explain.  Subagents whose parent is not listed are trees of their own, and so is each cycle of parents, so no session disappears; trees and siblings that rank alike keep the backend's order.

* Measuring in pixels

Lists read better in a proportional font, so the views lay text out in pixels: columns align with =(space :align-to (X))=, and long text is cut by =drover-truncate-to-pixels=.  =drover-text-pixel-width= lays text out in a buffer of its own with the view's face remapping and the fonts of the view's window, because =string-pixel-width= ignores face remapping before Emacs 31.  On a text terminal a pixel is a character cell, so the same layout holds there and in batch tests.

* Keys: three sets in one menu

Every key belongs to one of three sets, and no key to two: session keys act on the session at point, prompt keys on the prompt the user writes, global keys anywhere.  Because they never collide, one menu, =drover-dispatch=, holds all three, and a key means the same everywhere.  Lists of sessions bind the session keys directly (=drover-session-map=, inherited by drover's views and added to other lists by =drover-session-keys-mode=); everything else goes through the menu, which the user binds to one global key.

The menu shows every entry wherever it is invoked, greying out those that do not apply, so its layout never moves and keys are learnt by position.  What applies is computed once, when the menu opens (its scope, from =drover--context=), since finding the session at point may ask the backends for every session.

Other packages add their global commands to the menu relative to drover's keys, as Magit extensions do: the OpenCode backend inserts its session lists before =3=.

* The session at point, in lists and prompt buffers

Commands on a session take it as an argument and read it, interactively, from =drover-session-at-point-function=.  Lists set it to the row at point; a buffer belonging to one session, such as an OpenCode session buffer or an Org buffer where prompts are written, sets it to that session.  So the same command works from a list and from the conversation, and backends need no command of their own.

Parents and subagents need no backend operation: they are found among the sessions through =drover-session-parent=.  A parent the backend no longer lists is still opened by its identifier.

* Prompt actions

Prompt buffers differ (a Comint buffer for OpenCode, an Org buffer in the user's configuration), but the user's gestures are the same: send, attach, revert, choose the model.  A prompt buffer declares the actions it implements in =drover-prompt-actions=, each a command; drover's prompt commands look for the buffer an action applies to (=drover-prompt-target=): the current one, in a list the session's buffer, for the agent, model, effort and directory a default prompt buffer, and for the last answer the prompt buffer visited last.  An action applying to a buffer shown in a window runs in that window, so that it sees the point the user sees.

Compacting and forking exist both ways: in a prompt buffer they are prompt actions (forking at point), in a list backend operations on the whole session.

* View settings

Grouping (=drover-group-by=), filtering (=drover-filter=) and whether subagents show (=drover-show-children=) are global: every view lists the same sessions the same way, and changing a setting redraws them all at once through =drover-changed-hook=.  Views draw =drover-view-trees=.

A filter keeps a tree when a session in it matches, with the sessions above each match, so a matching subagent shows under its parent.  Hidden subagents stay hidden unless they explain why their tree is listed: a matching subagent shows when no session above it matches.  Filtering a project thus lists its sessions without every one of their subagents, while filtering on a status or a text shows the subagent that has it.
