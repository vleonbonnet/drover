# AGENTS.md - drover

Emacs package gathering the sessions of coding agent front ends (opencode.el first) into one place: attention tracking, one list of sessions, and actions on any session.

## Rules

- Never evaluate code in the user's running Emacs to test this package (no `emacsclient`, no Emacs MCP evaluation). Every test runs in a separate `emacs -Q --batch` process (`make test`).
- Never start a graphical Emacs yourself (`Emacs.app/Contents/MacOS/Emacs`, `emacs` without `--batch`, `open -a Emacs`), for tests, benchmarks, experiments or screenshots: on macOS it comes in front of the user's windows and takes the keyboard. `make test` never starts one; only the benchmarks given `EMACS_GUI` do (`bench`, `bench-bulk`, `bench-search`, `bench-idle`), one graphical Emacs a run, through `test/gui-emacs.sh`: on macOS through `open -g -j -n`, neither activated nor shown, its frames visible to Emacs but off screen, transparent and refusing focus (`test/gui-emacs.el`), under `GUI_TIMEOUT` (600 s) and a 2 GB guard, its status and output returned.
- Test economically. While working, run the test file you change in batch: `make test-one FILE=test/drover-list-test.el` (`SELECTOR=regexp` for some of its tests), seconds where `make test` takes about 20 s: each test file runs alone in a batch Emacs of its own, the longest files' tests shared by several (`TEST_SHARDS`), eight at once (`JOBS`), so that no test may count on another file, or on another test having run before it. Run `make compile lint test` once before merging, not after every edit. Run a benchmark only for performance work, and its graphical run (`EMACS_GUI`; `make bench` about a minute, covering bulk and search, `make bench-idle` about four) only when what you measure depends on redisplay or a graphical frame, once, never in a loop nor alongside another graphical run.
- Never start, stop or restart the user's OpenCode service, nor start or change a Claude Code or Codex session: tests write their transcripts and rollouts in throwaway homes (`test/drover-transcript-fixtures.el`), and run scripts of their own for the CLIs. Tests use the fake backend in `test/drover-test-helpers.el`, or stub the opencode.el functions they call.
- `make compile` must stay free of warnings, and `make lint` (checkdoc) clean.
- Backends are authoritative: drover renders what backends report and keeps only interface state (point, expanded sections, the last session visited, what each list drew and which sessions changed while it was hidden), the records of live sessions as backends last reported them (the index, current through their reports and listed anew now and then), the older and archived sessions a backend fetched, while they are shown, the recaps of expanded sessions' last turns, until those sessions change, and the records other hosts sent of their own sessions, as last received, in memory only.
- The list scales to thousands of sessions: a change draws only what it changes, in place (`drover-list--follow`), and must stay the list a drawing anew draws, which the tests check; `make bench` times it. In `drover-state-directory` it keeps only the models live sessions offered, the conversations it archived for backends without an archive of their own, the prompts scheduled for later (`drover-schedule`), the buffers of archived sessions to close once their turns end (`drover--closing-save`), when the user last saw each conversation engines record, bounded to those still recorded (`drover-transcript-seen-save`), where the clones this host received come from, the newest 1000 (`drover-remote--clone-note`), and, as a cache checked against the files, what it read of the transcripts and rollouts engines record (`drover-transcript`).
- An action on several sessions never acts on them all in the command: it runs as a job, in slices of a few milliseconds from a timer, a few requests in flight at most, reported once (`drover--bulk-start`); `make bench-bulk` times it over thousands of sessions.
- Byte code must not depend on optional front ends (agent-shell, claude-code-ide): their backends declare what they use and load the front end as they activate; `make compile` checks that the byte code compiled with the required packages alone is the same.
- The list's buffer shows sessions and the counts of their groups, not settings nor keys, nor a summary line: the menu shows those, each setting's value beside its key, the mode line hints at them and counts what needs the user.
- Drover has one view of sessions, the list of `drover-list.el`, in two buffers that may show at once, the list of an ordinary window and the sidebar of a side window, each with its own point, sections and layout, the sidebar folding none of its sections (`drover-list-sidebar-mode`), the view settings shared; improve it rather than adding another. A change costs each list only what its own lines need: what does not depend on the layout (trees, rows, widths, recaps) is made once for both, and a hidden list draws nothing until shown. It uses the faces and glyphs of `drover-ui.el` (strings in faces through `drover-face`, so font lock keeps them) and the commands of `drover-keys.el`; it sets `drover-view-p` and `drover-session-at-point-function`, draws `drover-view-groups` (grouped by `drover-group-by`, sorted by `drover-sort-by`), and inherits `drover-session-map` in its keymap. What a line shows is decided from the window's width and `drover-list-fields`, not by special cases.
- One key, one action: a key of `drover-session-map` means the same in every list, and no key belongs to two of the sets of `drover-dispatch` (session, prompt, global, view), nor prefixes another; `drover-keys-test-dispatch-keys-unique` checks every entry, shown or not. Its List group (moving in drover's list, here or beside) uses keys of no set, but RET, which opens there and sends in prompt buffers, and from other buffers while drover's prompt holds a prompt to send (Send then on M-RET in the list itself): the menu shows one RET at a time. The list binds only standard keys of its own (RET, C-o, q, copying, as `kill-ring-save` remapped, and Magit's n, p, TAB), and the sidebar a click opening as RET does (mouse-1, no drag, double clicks doing no more). View settings are infixes of the View, Filter and Columns groups (`drover--view-columns`, shared by `drover-dispatch` and the View menu, `drover-view`, V in lists), on Magit's families of keys, `=` for options, `-` for switches, not keys of their own; they apply whenever one of drover's lists is in sight. Every setting of the menu shows its value beside its key, and leaves the menu open. Groups are titled after what they do, never after the set of their keys; the menu's layout is `drover--menu-flow`'s, never fixed rows. The places other packages extend `drover-dispatch` from (after b and ', after p, after O) stay stable.
- Comments are sparse and explain why, not what. Docstrings are complete sentences; the first line stands alone.
- Errors never flood. Every function drover runs out of a command (timers, idle timers, process filters and sentinels, callbacks it gives front ends and services, functions on the hooks of Emacs or of other packages, `kill-emacs-hook` included, file notifications) runs its body in `drover-with-reporting`, and a hook drover runs for others runs through `drover-run-hook-reporting`: one line, the data printed briefly (`drover-error-string`), the same error at most once in `drover-error-interval` seconds; nothing out of a command may reach Emacs's own reporting, which prints an error's data whole. Messages and warnings go through `drover-message` and `drover-warn`, bounded, and an error's text through `drover-error-message`, never `error-message-string` nor `%S` of an error. Drover signals no error carrying a structure: check a structure (`drover-layout-current-p`) rather than let an accessor signal with it.
- Text from outside is bounded where drover takes it in: records through `drover--bound-record` (a title to its first line and `drover-line-limit` characters, a detail or request to `drover-text-lines` lines and `drover-text-limit` characters), recaps and previews in `drover-recap` and `drover-preview`, what a reader reads of a file with `drover-transcript-text` and `drover-transcript-string-prefix` (a line longer than a window is read from its start). Nothing unbounded reaches pixel measurement (`drover-text-pixel-width` measures `drover-measure-limit` characters at most), `message`, a tooltip (`drover-bound-lines`), the echo area or the mode line. The tests feed lines of 500 kB.
- Structures print in proportion to what they hold, since Emacs prints values whole (an error's data, `format`, a value evaluated): neither a structure nor a closure drover keeps (in a timer, a request given to spyglass, a callback) holds directly what leads back up to what holds it or to sections, but through `drover-link`: a drawing's links (a row's tree and section, a tree's group, a group's section), the peers and subscribers and the remote state its timers and requests act on. The `*-test-prints-in-proportion` tests print whole everything drover keeps (`drover-test-kept`: its variables, global and local, timers, processes) against a bound a session, and what is held once a session against a bound whatever the sessions.
- Long-lived structures (the index, each list's model, the indexes of transcripts, the queue of scheduled prompts) hold first a slot `stamp`, `drover-layout` of the types they are made of, and are checked with `drover-layout-current-p` where code reaches them from a variable, timer or hook: one made by another version of drover is dropped and made anew, with `drover-stale-layout`. A file defining a type of them calls `drover-note-layout` after it. A file needing definitions of `drover-core` that an older one lacks at load time raises `drover-core-generation` and the check after its requires, so that it loads into an Emacs running an older drover. A file defines its structures before the code calling their accessors, which compiling or loading its sources inlines (`drover-robustness-test-structures-before-use`); an accessor that becomes a function removes the compiler macro its structure left; records of an older layout are completed as drover takes them in (`drover--whole-record`).
- Org links (`drover-links`) name conversations, `agent-session:ENGINE/ID`, never buffers nor front ends: a link stored once opens for good. Link shapes already stored, the user's front-end types included, keep opening as they did; a host, when sessions get one, is an optional authority (`//HOST/`), so that links without one keep naming this machine's conversations.
- Each host is the authority over the sessions it runs (`drover-remote.el`, `doc/remote.org`): it serves its own backends' sessions only (`drover-remote--local-p`), never a record with a `host`, so that nothing loops between hosts. What a peer sends is JSON spyglass parses, never `read`, every value checked and bounded in `drover-remote-decode-record`; nothing a peer sends is interned but short symbols. A peer's actions on this host's sessions are requests the owner performs through its own backends, never prompting nor taking a window, checked against that peer's `:access` on every request whatever the peer greyed out, each identified and performed once (`drover-remote--on-act`); what is new in the protocol is told in the greeting's capabilities, so that a peer running an older drover keeps working, read only.  A peer's OpenCode sessions open in full opencode.el buffers through its owner, which relays each request to its own service with its own credentials, never sent, checked against the peer's access (`drover-remote--oc-refusal`); the OpenCode backend follows the local service alone, ignoring opencode.el's hooks run for another service and running its operations for the local one whatever buffer is current (`drover-opencode--here`). A clone of a conversation is made by the host that will own it: it asks the owner for the conversation's files in pieces, as data, never `read`, every name and size checked (`drover-remote--clone-description`), its engine placing them (`:import`), and takes clones only from peers it grants `full` access (`drover-remote--on-clone`). A new session on a peer is the owner's to start, through its own backend's `:create` in no window, for a peer of `act` or `full` access, in a directory of its that exists, the peer completing directories on names the owner lists alone, never files nor contents, and choosing among the agents and models the owner tells (`drover-remote--on-new`, `drover-remote--on-ls`, `drover-remote--on-catalogs`); the prompt reaches it through `drover-prompt-remote-functions`. A search of what was said in a peer's sessions is the owner's, run with its own backends over the sessions the viewer names, its matches bounded and decoded as records are (`drover-remote--on-search`, `drover-remote--decode-match`). The core, lists and links never require spyglass nor `drover-remote`: they reach it through the variables it sets (`drover-hosts-function`, `drover-host-label-function`, `drover-host-state-function`, `drover-links-remote-function`), and `drover-remote.el` declares what it uses of spyglass and loads it as the mode starts.
- The tests of the remote layer need `SPYGLASS_EL`, a spyglass with channels and `spyglass-reconnect` (which drops a stream whose write failed), and start a second batch Emacs (`test/drover-remote-agent.el`) through 127.0.0.1, SIGPIPE ignored (the Makefile's `trap '' PIPE`). On Core, only `make bench-remote REMOTE=core SSH=myssh REMOTE_EMACS=/ucrt64/bin/emacs`, which runs batch Emacs in a temporary directory removed after; never Core's running Emacs.
- Scheduled prompts are delivered through backend operations (`:blocker`, `:submit`, `:ready`) and resumers (`drover-resume-with`), never by naming a front end in `drover-schedule.el`; a queue file that does not read is never written over, and a prompt is saved before it is armed.
- A prompt sent to an archived session, from the prompt or scheduled, restores it first: what drover archived through `drover-unarchive-to-send`, what a backend archived through the backend (opencode.el restores as it sends); one that cannot be restored is sent nothing, and one bounded line says why.
